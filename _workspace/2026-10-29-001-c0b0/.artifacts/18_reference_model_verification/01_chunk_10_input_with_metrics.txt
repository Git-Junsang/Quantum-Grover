## 장르·레지스터와 보존 조건

학부생용 기술 해설서(report). 본문은 친근한 존댓말(합니다/입니다, 일부 해요체 설명), 수식 풀이·표·요약은 압축형입니다. 문장 격식을 올리지 않습니다. 영어 용어와 영어 토큰은 번역·삭제·교체·대소문자 변경하지 않습니다. glossary 기준은 `documents/design_references/22_appendix_glossary_and_retired_specs.md` §22.2입니다. 수치·수식·code·제목·link·직접 인용·기존 콜아웃/이모지·문단 구조는 보존합니다. 실제 주장, 부정/긍정, 인과, 조건, 확신도도 보존합니다. 보고서용 서식 축약·영어 순화 규칙은 적용하지 않습니다. 본문에 사실을 추가하거나 현행 설계와 대조해 기술 내용을 고치지 않습니다.

## 정량 근거

입력의 정량 블록을 확인했습니다. risk_band는 low이고, 장문 파일의 heavy 권고는 문서 길이에서 나옵니다. 영어 기술 term 반복은 장르상 필수이므로 lexical_diversity의 낮은 값만으로 수정하지 않습니다. 아래 수치는 탐지 보조이며 개별 문맥과 함께 판단합니다.

## 겨냥 순서의 지배 패턴

1. **D-14·D-5 — 시험·설계를 사람처럼 서술하는 표현**: "규칙이 여기서 처음 일합니다", "종료 규칙이 일해야", "FSM이 매달리지 않고", "이 발판 위", "circuit은 … 조용히 틀립니다", "끝까지 정직하게 계산" 등이 직접적인 동작 설명을 흐립니다. 조건과 보장 수준을 보존하고 구체적인 서술로 정리합니다.

2. **A-18·A-7 — 장문·have 직역**: 정량 relative_clause_nesting=7, have_make_literal_count=1. 도입의 두 근거, 18.2절 ladder, 18.4절 예제, 18.7절 checkpoint 경로, 18.8절 비교 조건의 문장을 검토합니다. "오류를 갖고" 등 소유 직역과 여러 층의 수식을 겹친 문장만 국소 수정합니다.

3. **D-8·C-8 — 핵심 강조·부정 대구의 반복**: "이 목록에서 얻을 교훈은 목록 그 자체가 아니라 태도", "주는 것은 속도가 아니라", "묻는 것은", "근사적으로 같은 정도가 아니라" 등이 반복됩니다. equivalence와 distribution, algorithm과 circuit, bit-exact와 오차 허용 구분처럼 기술적으로 필요한 대조는 반드시 보존합니다.

4. **D-2·F-1 — 과한 중요성·평가 표현**: "공짜가 아닙니다", "영원히 일치하지 않고", "이보다 좋은 출발점은 없습니다", "실행된 적 없는 code가 옳을 probability는 낮습니다" 등 단정·평가의 수사만 줄입니다. 원문 사실이나 기준을 새로 해석하지 않습니다.

5. **J-2·J-3·C-11 — 대시·따옴표·쉼표로 끊긴 설명**: 연속된 대시 부연과 수사형 따옴표를 확인합니다. 표·목록의 교육적 구조와 기존 콜아웃·강조를 보존하고 산문에서 불필요한 쉼표·감싸는 표현만 정리합니다.

## 18.9 toolchain과 directory

마지막으로 이 verification이 실제로 어디서 도는지를 정리합니다.

이 project 환경에는 필요한 도구가 **전부 local에** 있습니다 — RTL simulator `verilator`(cycle-accurate C++ model)와 `iverilog`, commercial simulator Questa, synthesis·implementation·bitstream을 내는 Vivado, RISC-V firmware를 빌드하는 GCC, 그리고 SoC 전체를 생성하는 RVX. 화면이 없는 환경이라 waveform viewer와 Vivado GUI는 띄울 수 없고, Vivado는 batch mode로만 씁니다. waveform 대신 testbench가 값을 file로 떨어뜨리고 script가 대조합니다.

작업 순서는 verification ladder를 따릅니다. 1단과 2단은 Python이라 어디서든 돌고, 3단 regression은 verilator로 몇 초에서 몇십 분이며, 그다음이 synthesis·timing closure·resource benchmark, 마지막이 board입니다. 순서를 뒤집으면 synthesis 한 번에 수십 분을 쓰면서 simulation으로 5분이면 잡을 버그를 찾게 됩니다. 두 simulator는 역할이 다릅니다. `verilator` 는 빨라서 250·500 workloads testbench 같은 긴 regression을 맡고, Six-Stage Ablation의 2,500회 campaign은 `iverilog` 로 돌았습니다. reference model이 Python이므로 simulator harness가 결과를 file로 떨어뜨려 대조하는 형태가 자연스럽습니다.

directory는 이렇게 나뉩니다.

| 경로 | 담는 것 |
|---|---|
| `hardware_bram/src/` | RTL — Bus Interface(CSR · DMA Engine)와 Accelerator Core |
| `hardware_bram/testbench/` | Verilog testbench와 C++ harness |
| `hardware_bram/sim/` | regression 진입점 `Makefile` 과 runner·보고 script |
| `hardware_bram/results/` · `hardware_bram/configurations/*/results/` | simulation campaign 결과 묶음 (configuration 사이 비교 · configuration별) |
| `software/reference_model_develop/models/` | 2단 reference model (Q1.22 bit-exact · checkpoint policy) |
| `software/pc_grover_develop/` | 1단 기준 (NumPy · Qiskit) 과 C++ implementation |
| `software/reference_model_data/` | 2단이 만든 test vector · expected result · 비교 결과 |
| `software/testbench_data/` | testbench · 실험이 읽는 입력 dataset |
| `software/reference_model_develop/` · `software/reference_model_data/` | Common500 비교 실험과 그 결과 |

reference model이 `hardware_bram/` 이 아니라 `software/` 에 있는 것이 의도적입니다. 같은 reference model을 BRAM Variant와 DRAM Variant가 **함께** 쓰기 때문입니다 — DRAM Variant는 같은 stimulus를 BRAM Variant에도 걸어 search의 BBHT trajectory가 같은지 대조하고, 그 기준이 되는 의미 규약은 두 variant 어디에도 속하지 않습니다. regression을 실제로 돌리는 명령과, 저장소 상황에 따라 먼저 되살려야 할 file은 [toolchain 사용법](../design_references/02_development_environment_and_toolchain.md)에 있습니다.
