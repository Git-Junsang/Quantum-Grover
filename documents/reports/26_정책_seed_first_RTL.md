# 실험 26. seed-first 정책 탐색 RTL과 M2/M3 K/H 비교 (진행 중)

> [← 실험 25](25_M3_K5_자원_속도_검토.md) · [실험 보고서 index](index.md)

> **진행 중.** RTL 기능 검증과 RTL 사이클 측정은 끝났지만, Arty 100T 구현 타이밍이 아직
> 통과하지 못했고 정책 최적화 전(prune0) K/H 전 범위 측정이 돌고 있습니다. 아래 결론은
> 이 두 가지가 끝나면 다시 확인해야 합니다.

| 확인한 것 | 근거의 축 | 상태 |
|---|---|---|
| 실험 24 의 full-horizon bound + seed-first exact DFS 를 RTL 로 구현했고, 선택 결과가 exhaustive 정책과 같다 | 정책 단독 RTL, K3/K4 × H1..8 | 확인 |
| 정책 계산이 K3H3 에서 56 %, K4H8 에서 93 % 줄었다 (모드 6) | 정책 단독 RTL | 확인 |
| M3 K3H3 전체 사이클이 4,680,014 → 4,566,996 (−2.41 %) | 통합 bench500, RTL 사이클 | 확인 |
| 최적화 후 최적 셀은 M3 에서 K3H3, M2 에서 K4H4 | 통합 bench500 | 확인 |
| M2 는 어떤 K/H 로도 M3 K3H3 을 이기지 못한다 | 통합 실측 + 모델 하한 | 확인 |
| M3 + 모드 6 이 Arty 100T 에 100 MHz 로 들어간다 | Vivado 구현 | **미확인** (1차 WNS −0.302) |

## 목적

실험 24 는 full-horizon admissible lower bound 와 seed-first exact DFS 를 SW 로 계산하고 사이클
모델로 효과를 예측했습니다. 이 실험은 그 탐색을 정책 RTL 에 넣어 실제 사이클과 결과 동일성을
확인하고, 측정 경로 M3 위에서 K/H 를 다시 고르는 것이 목적입니다.

## 구현

`grover_policy.v` 에 두 모드를 더했습니다. 기존 모드 0~4 는 그대로입니다.

| 모드 | 내용 |
|---|---|
| 5 | 프레임마다 SCAN(모든 자식의 bound) → seed(가장 작은 bound) 를 정확히 평가 → canonical 순서로 돌며 `즉시비용 + bound ≥ 최선` 이면 가지치기 |
| 6 | 5 + 현재 요청의 legal action 이 하나뿐이면 하위 탐색 없이 결정. 그때 `root_cost` 는 정확한 비용 대신 하한(Main IP 는 이 값을 읽지 않음) |

bound 는 universe 값을 정렬 순위로 바꾼 비트마스크 위에서 계산합니다. 요청 하나가 레지스터 한
단이고, 각 단은 "임계 순위 이하", "최상위 비트", "그 위 구간" 같은 비트 연산뿐이라 값 비교기나
max 트리가 없습니다. 순위는 BUILD 의 capture → resolve → commit 단계에서 증분으로 유지해 BUILD
사이클을 늘리지 않았습니다. 이 모드를 쓰는 모델은 `hardware_bram_K3H3_E4_M3_S6`
(M3 + `POLICY_EXACT_PRUNE=6`) 입니다.

## 결과

### 정책 단독

| 셀 | 기존 DFS (모드 0) | 2단계 prune (모드 4) | 모드 5 | 모드 6 |
|---|---:|---:|---:|---:|
| K3H3 | 1,183,308 | 933,966 | 700,076 | 525,037 |
| K4H4 | 2,841,616 | 1,985,090 | 1,136,391 | 816,610 |
| K4H8 | 21,593,720 | 18,354,629 | 2,539,529 | 1,521,059 |

실험 24 의 모델은 RTL 보다 낙관적이었습니다(K3H3 예측 590,569 대 모드 5 실측 700,076). 모델에
SCAN · seed · canonical 각 패스의 고정 지연이 빠져 있기 때문입니다.

### 통합 (M3, M2)

정책 계산의 대부분은 Grover 실행 뒤에 숨기 때문에 전체 사이클에는 stall 만큼만 드러납니다.

| K3H3 | 정책 단독 | stall | 전체 |
|---|---:|---:|---:|
| M3 prune0 | 1,183,308 | 152,458 | 4,680,014 |
| M3 모드 6 | 525,037 | 39,440 | 4,566,996 |
| M2 prune0 | 1,183,308 | 98,273 | 5,255,084 |
| M2 모드 6 | 525,037 | 38,280 | 5,195,091 |

- M3 에서는 H 를 키우면 stall 이 반복 절감보다 빨리 늘어 K3H3 이 최적입니다(K4H3 은 +0.02 %,
  K4H4 는 +0.28 % 느려 사실상 동률). M2 는 숨길 시간이 길어 K4H4 가 최적입니다.
- M3 가 줄인 고정 부분(약 63만 사이클)이 K/H 로 줄일 수 있는 반복(최대 약 24만 사이클)보다
  커서, M2 는 어떤 K/H 로도 M3 K3H3 을 이기지 못합니다.

셀별 표, 모델, 40셀 히트맵, 자원 무제한 가정의 K1..10 × H1..10 추정은
[K/H 묶음](../../hardware_bram/results/2026-10-27_kh_sweep_m2_m3/evidence.md) 에 있습니다.

### 구현

OOC 배치·배선(100 MHz)은 정책 단독 K3H3 · K4H8 과 Main IP M3 모두 통과했습니다(Main IP
+0.068 ns, LUT +1,011). Arty 100T 전체 SoC 1차 구현은 slice 99.07 %, WNS −0.302 ns 로
실패했습니다. 실패 88 경로 중 68 개가 memo BRAM 출력에서 탐색 제어 레지스터의 enable 로 가는
경로였고, 탐색 제어 블록을 memo hit/miss 분기 앞으로 옮겨 없앴습니다(사이클 동일 확인).
2차 구현이 진행 중입니다. 근거는 [정책 RTL 묶음](../../hardware_bram/results/2026-10-27_policy_seed_first/evidence.md)
과 [S6 구현 묶음](../../hardware_bram/models/hardware_bram_K3H3_E4_M3_S6/vivado/vivado_bbht_grover_k3h3_e4_m3_s6/2026-10-27_arty100t_build/evidence.md).

## 남은 일

1. Arty 100T 2차 구현 확인. 실패하면 `ExtraNetDelay_high` 배치 지시어, 그래도 실패하면 M3 prune0 유지
2. prune0 K3/K4 × H1..8 통합 측정(M2, M3) 완료 후 네 구성 비교표 갱신
3. K4H4 memo 압축 검토. 모델로는 K4H4 stall 의 절반 가까이가 memo 초기화이고, 압축하면
   K3H3 보다 약 1.8 % 빨라질 것으로 추정
4. 기술문서 11장 · 5장 모델 표 · CLAUDE.md 모델 목록 · 실험 보고서 index 반영
5. 실험 22~24 도구(`kh_sweep.py` 등)와 이 실험의 분석 스크립트를 저장소 경로로 정리
