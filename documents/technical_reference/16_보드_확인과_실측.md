# 16장. 보드 확인과 실측

> [← 15장 검증 체계](15_검증_체계.md) · [17장 합성 · 구현 · 비트스트림 →](17_합성_구현_비트스트림.md)

---

보드 검증은 시뮬레이션에서 확인할 수 없는 물리 UART와 실제 실행 경로를 다룹니다. 성능
측정과 기능 확인에 사용한 보드 세션이 다르므로 결과를 인용할 때 측정 범위를 구분해야
합니다.

---

## 16.1 보드 실측의 두 묶음

| 날짜 | 무엇 | 성능 인용 |
|---|---|:-:|
| 2026-09-08 | 500 워크로드 세 구성 (Normal · K4/H4 · M2) + ORCA 기준선 | 정본 |
| 2026-09-17 | 통신 계층 교체판 비트스트림의 콘솔 명령 왕복 | 아니오 |

성능 세 축은 전부 2026-09-08 묶음에서 나옵니다([1장 1.5절](01_프로젝트_개요.md)).
2026-09-17은 "교체판이 실물에서 도는가" 를 본 것이고 워크로드가 하나뿐입니다.

## 16.2 2026-09-08: 500 워크로드 정본

| 항목 | 값 |
|---|---|
| 비트스트림 | 2026-09-07 빌드 (Vivado 2024.2) |
| 앱 | `bbht_paper_bench.elf` |
| 워크로드 | M = 1/4/16/64/256 × 시드 100 = 500 |
| 조건 | `EQ`(12345), 데이터 16,384칸, 샷 상한 100 |

| 구성 | 총 시간 | 배수 |
|---|---:|---:|
| Normal | 425,502 us | — |
| K3/H3-E4-M2 | 55,798 us | 7.626x |
| ORCA 1코어 순수 SW | 6,496,338,005 us | (M2 대비 116,426x) |

같은 칩, 워크로드, 시드를 사용한 ORCA 기준선이 직접 비교 가능한 대조군입니다. 배수가
십만 단위인 것은 P = 32 병렬과 클럭 2배 때문이지 알고리즘 우위가 아닙니다.

실물은 [`bitstream/2026-09-08_k3h3_e4_m2/`](../../hardware_bram/bitstream/2026-09-08_k3h3_e4_m2/evidence.md)
에 비트스트림과 두 ELF, 해시가 같이 있습니다.

## 16.3 2026-09-17: 통신 계층 교체판 콘솔 세션

2026-09-16에 통신 계층을 교체해 생성한 비트스트림을 Arty A7-100T에 기록하고, 호스트
PC에서 UART를 통해 `bbht_console`을 제어했습니다.

| 항목 | 값 |
|---|---|
| 비트스트림 | sha256 `1b67a070…52adc61` |
| 앱 | `bbht_console.sram.hex` (UART 판, sha256 `51e1684c…2e7cf3`) |
| 적재 | Olimex ARM-USB-TINY-H JTAG로 SRAM에 |
| 호스트 | Windows 11, `bbht_cli.py --port COM6` (115200 8N1) |
| 워크로드 | M = 4, 시드 0 (SoC 시뮬과 같은 것) |

### 결과

selftest 7/7, RUN · STAT · ENUM 결과 줄 26개가 SoC 시뮬 트랜스크립트와 글자 그대로
일치합니다.

| 실행 | idx | trials | l | iters | cyc |
|---|--:|--:|--:|--:|--:|
| Normal (`BURST=0`) | 8685 | 21 | 119 | 119 | 41,310 |
| 체크포인트 첫째 | 8685 | 21 | 119 | 38 | 20,935 |
| 체크포인트 둘째 | 8685 | 21 | 119 | 38 | 17,847 |
| `ENUM` | 8685 → 2852 → 507 → 4724 | | | | 280,494 |

정책 엔진 통계(`policy_cyc` · `memo_hit` · `max_latency` 등)까지 시뮬과 같습니다.

근거는 [board_console](../../hardware_bram/vivado/vivado_bbht_grover_fpga/2026-09-17_board_console/evidence.md),
실물과 굽기·적재 묶음은
[bitstream/2026-09-17_comm_layer_rebuild](../../hardware_bram/bitstream/2026-09-17_comm_layer_rebuild/evidence.md)
입니다.

### 처음 검증된 경로

호스트 → 보드 수신 경로입니다. `read_line()`의 UART 판과 `bbht_cli.py`의 시리얼
트랜스포트는 SoC 시뮬에서 한 번도 돌지 않았습니다(스크립트 모드는 명령을 컴파일 시점
배열에서 읽습니다). 이 층에서만 나올 수 있는 문제가 실제로 하나 있었습니다.

- COM 포트를 열 때 DTR/RTS가 켜지면 SoC가 리셋됩니다. 앱이 JTAG로 올린 SRAM
  이미지뿐이라, 기본 설정으로 포트를 열면 그 뒤로 에코조차 오지 않고(`ERR HOST_TIMEOUT`)
  앱을 다시 적재해야 돌아옵니다. 한 핸들로 열어 둔 채로는 OpenOCD 종료 뒤에도 계속
  응답하고, 닫았다 다시 열면 멈추는 것으로 좁혔습니다. `SerialTransport`가 열기 전에
  둘을 내리도록 고쳤습니다.
- Windows에서 `--script` · `--log` 파일을 cp949로 열어 한글 주석에서 죽던 것을 UTF-8로
  고쳤습니다.

## 16.4 굽고 올리는 절차

```bash
# 1. 비트스트림 (Vivado 배치 모드, 헤드리스 가능)
vivado -mode batch -source program_fpga.tcl

# 2. 앱 (JTAG 어댑터가 붙은 PC에서. Windows 면 usbipd로 WSL에 넘긴 뒤)
cp /opt/rvx/local_setup/ocd/openocd_rvp ocd/
cp bbht_console.sram.hex ocd/
ocd/ocd_keep.sh &          # 붙여 둔 채 유지

# 3. 호스트에서 명령
python3 software/host/bbht_cli.py --port /dev/ttyUSB1 selftest
```

`ocd/`는 RVX가 `imp` 폴더에 내주는 OCD 환경이 `/opt/rvx` 절대경로를 읽어서 다른 PC에서
못 쓰기 때문에, 필요한 tcl을 상대경로로 모아 둔 묶음입니다.

| 파일 | 역할 |
|---|---|
| `arty-100t.cfg` | OpenOCD 설정. Olimex ARM-USB-TINY-H, 10 MHz, JTAG tap `rvp.noc` |
| `run_bbht_console.tcl` | 플랫폼 리셋 → SRAM에 write → `set_all_ready` |
| `set_ocd_env.tcl` | `arch/` · `rvx_env/`를 상대경로로 읽도록 수정한 버전 |
| `load_app.sh` | 올리고 빠져나옴 |
| `ocd_keep.sh` | 올린 뒤 OpenOCD를 붙여 둔 채 유지 |

OpenOCD를 종료하면 어댑터 분리 과정에서 플랫폼이 리셋되어 SRAM의 앱이 사라집니다. 아직
SPI 플래시 부팅을 지원하지 않으므로 보드 RESET 버튼을 눌러도 앱을 다시 적재해야 합니다.

`openocd_rvp` 실행 파일(12 MB)은 저장소에 두지 않았습니다. `/opt/rvx/local_setup/ocd/`
사본과 sha256이 같으므로 해당 실행 파일을 복사해 사용합니다.

## 16.5 측정 결과 해석 시 주의 사항

`us=`는 실경과 시간이 아닙니다. 펌웨어가 `bbht_cycles_to_us(cycle_count)`로 사이클에서
환산한 값(100 MHz 기준)이므로 시뮬레이션에서도 같은 값이 나옵니다. 이 묶음은 실경과
시간의 근거로 사용하지 않습니다.

체크포인트 사이클은 보드 500런 표와 직접 비교할 수 없습니다. 콘솔의 체크포인트 두 줄은
사이클이 서로 다른데(20,935 vs 17,847) 두 값 모두 시뮬과 같습니다. 리셋 뒤 첫 탐색만
memo 청소를 치르기 때문입니다([11장 11.5절](11_체크포인트와_정책_엔진.md)). 논리 네 축은
같아야 하고, 사이클은 직전에 무엇을 돌렸는지와 함께 보아야 합니다.

## 16.6 남은 검증 항목

| 무엇 | 왜 남았나 |
|---|---|
| 교체판의 실경과 시간 | 콘솔은 사이클 환산값만 냅니다. 보드 타이머를 읽도록 펌웨어를 고쳐야 합니다 |
| 교체판의 500 워크로드 보드 실측 | 콘솔로 돌린 것은 M = 4 시드 0 하나뿐입니다 |
| 보드에서 `LT` · `GT` · `RANGE` | 보드 세션은 `EQ` 하나만 돌렸습니다. 셋 다 같은 비트스트림에 런타임 경로로 들어가 있고([9장 9.2절](09_연산_경로와_E4.md)) 1층 회귀에서 통과하지만, 실물에서는 아직입니다 |
| SoC 경로의 M = 16 나머지 39시드와 M = 64 · 256 | 시뮬 시간 제한. 같은 구성의 verilator `bench500`은 500/500 통과했습니다 |
| 3,279 사이클 차이 473건 전부의 재현 | 한 워크로드로 원인을 확인했습니다. 나머지 21건이 제각각인 이유도 미확인 |
| 두 빌드의 비트스트림 해시 비교 | Vivado 판이 달라 원리상 불가능합니다 |
| DRAM 갈래의 물리 바인딩 | MIG/AXI와 RVX 설치가 없습니다 |
| SPI 플래시 부팅 | 보드 RESET이나 포트 재열기 뒤에는 앱을 다시 적재해야 합니다 |

보드에서 나머지 세 술어를 실행하는 데는 콘솔 명령만 필요합니다. 예를 들어
`SET MODE=RANGE A=1000 B=1300`을 입력하면 비트스트림이나 앱을 다시 적재하지 않아도 됩니다.
