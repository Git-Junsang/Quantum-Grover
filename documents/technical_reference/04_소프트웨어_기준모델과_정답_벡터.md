# 4장. 소프트웨어 기준모델과 정답 벡터

> [← 3장 Grover와 BBHT 알고리즘](03_Grover와_BBHT_알고리즘.md) · [5장 하드웨어 아키텍처 개요 →](05_하드웨어_아키텍처_개요.md)

---

RTL을 검증하려면 구현과 독립된 기준값이 필요합니다. [`software/`](../../software/)는 이
기준값을 생성하며 BRAM과 DRAM 구현이 함께 사용합니다. 특정 하드웨어 구현에만 필요한
코드는 각 하드웨어 디렉터리에서 관리합니다.

여기서는 모델의 구성과 용도를 중심으로 설명합니다. 폴더별 상세 내용은
[소프트웨어_기준모델과_Common500.md](../design_references/소프트웨어_기준모델과_Common500.md)
입니다.

## 4.1 세 계층의 기준 모델

| 계층 | 위치 | 무엇을 |
|---|---|---|
| Float64 상태벡터 | [`models/numpy_model/`](../../software/models/numpy_model/) | 알고리즘이 맞는지. 고정소수점 영향이 없는 기준 |
| Qiskit Aer | [`models/qiskit_model/`](../../software/models/qiskit_model/) | 같은 회로를 독립 구현으로 확인 |
| Q1.22 bit-exact | [`models/rtl_reference_model/`](../../software/models/rtl_reference_model/) | RTL과 같은 수가 나오는지 |

공통 설정과 데이터셋은 [`models/common/`](../../software/models/common/)에 있습니다.
[`final_hardware_contract.py`](../../software/models/common/final_hardware_contract.py)가
CSR 오프셋 · 입력 범위 · 실행 모드 · 체크포인트 상수를 담고,
`benchmark_dataset.py`가 M 별 공식 데이터셋과 오라클 타겟 마스크를 만듭니다.

### RTL 기준 모델의 범위

| 재현함 | 재현 안 함 |
|---|---|
| Q1.22 산술 (포화·round-even 포함) | `cycle_count` |
| J-LFSR과 7스텝 점프 타이밍 | 정책 풀이 지연 |
| 측정 난수(xorshift64)와 정수 CDF | plan FIFO 대기 |
| K3/H3 정책의 결정 규칙 | E4 · M2의 사이클 효과 |
| 물리 반복 수 `actual_grover_iterations` | |

오른쪽 항목은 하드웨어 타이밍에 해당하므로 기준 모델의 범위에서 제외했습니다. 정책 지연과
파이프라인 대기까지 모델링하면 RTL과 독립된 검증이라는 의미가 약해집니다. 사이클 수는
RTL 시뮬레이션이나 보드 측정 결과에서 인용해야 합니다.

모델은 CSR 모드 이름(`CKPT_SINGLE` 등) 대신 정책 이름으로 부릅니다. `RUN_MODES`에
`K3H3_*` · `K3H3_E4_M2_*` · `K4H4_*` · `K4H8_*`가 있고 `CKPT_*`는 없습니다.
`checkpoint_bbht_model.py`는 `mode="K4H8"`을 옛 K4/H4 정책으로,
`"K3H3_E4_M2"`를 K3/H3으로 옮겨 받습니다. 이름이 갈라진 이유는
[1장 1.4절](01_프로젝트_개요.md)에 있습니다.

`DRAM_ALL_J`도 정책 모델로 들어 있습니다. [18장](18_부록_DRAM_갈래와_용어집.md)의 갈래를
알고리즘 수준에서 비교하려는 것이고, DRAM 전송 지연은 모델링하지 않았습니다. Common500
결과와 보드 실측에는 들어 있지 않습니다.

## 4.2 Common500 비교 실험

보드와 같은 500개 워크로드를 8종의 백엔드에서 실행해 총 4,000행의 결과를 생성합니다.

| 축 | 값 |
|---|---|
| M (타겟 수) | 1, 4, 16, 64, 256 |
| 시드 | M마다 공식 로스터 100쌍 |
| 워크로드 | 총 500 |
| 소프트웨어 backend | NumPy, Qiskit Aer, Fixed Normal, K4/H4, K3/H3 |
| FPGA backend | Normal, K4/H4, K3/H3-E4-M2 (보드 실측 CSV) |

보드 쪽 세 열은 2026-09-08 보드 실측과 같은 워크로드이고, 원본 CSV는 고치지 않고
합쳤습니다.

### 정합성 결과

비교는 짝을 지어 합니다. NumPy·Qiskit은 float64 측정이라 Q1.22 쪽과 궤적이 같을
이유가 없으므로 둘끼리만 맞대고, 고정소수점 모델은 같은 정책의 보드 구성과 맞댑니다.

| 검사 | 비교 필드 | 결과 |
|---|---|---:|
| NumPy ↔ Qiskit | `result_index` · `trial_count` · `L_BBHT` | 500/500 |
| Fixed Normal ↔ 보드 Normal | 위 셋 + `actual_grover_iterations` | 500/500 |
| K4/H4 모델 ↔ 보드 K4/H4 | 논리 셋 / 물리 반복 | 500/500 / 500/500 |
| K3/H3 모델 ↔ 보드 K3/H3-E4-M2 | 논리 셋 / 물리 반복 | 500/500 / 500/500 |
| 보드 세 구성끼리 | 논리 셋 | 500/500 |

검증 기준은 두 가지입니다. 체크포인트 사용 여부가 논리 결과를 바꾸지 않아야 하며, 같은
정책을 사용한 모델과 보드는 물리 반복 수도 같아야 합니다. 두 기준 모두 500/500건
일치했습니다.

보고서는 [`common500_validation_report.md`](../../software/results/common500_final/common500_validation_report.md)
이고 원시 결과·표·그래프가 같은 폴더에 있습니다.

### 시간은 측정 경계가 서로 다릅니다

| backend | 무엇을 쟀나 |
|---|---|
| NumPy | 상태벡터 계산 코어만 |
| Qiskit | Aer 실행만 (회로 build · transpile은 별도 열) |
| 고정소수점 모델들 | 파이썬 벽시계 |
| FPGA | 보드의 명령 발행부터 결과까지. DMA 적재 제외 |

FPGA 구성끼리의 배수만 성능 주장에 씁니다. 서버 소프트웨어와 보드의 절대시간 비율은
플랫폼과 측정 경계가 달라 참고값입니다. 같은 칩 위의 정당한 대조군은 ORCA 1코어
기준선이고, 그 배수에 붙여야 할 단서는 [1장 1.5절](01_프로젝트_개요.md)에 있습니다.

## 4.3 RTL 정답 벡터

시뮬레이션 회귀가 직접 물고 가는 기대값입니다.
[`software/rtl_vectors/`](../../software/rtl_vectors/).

### requested-j bit-exact 256케이스

`requested_j_bit_exact/requested_j_bit_exact_256_cases.zip`: 방향성 28개(`dir_*`),
앵커 1개(`anchor_*`), 무작위 227개(`rnd_*`).

| 파일 | 내용 |
|---|---|
| `config.json` | 술어 · 임계값 · 데이터 개수 · `j_target`과 프로파일 |
| `data_signed16.hex` · `data_ahb_words.hex` · `data_memory_image.hex` | 같은 데이터셋의 세 표현 |
| `target_mask_p32.hex` | 오라클 타겟 마스크 |
| `initial_amp.hex` | 초기 Q1.22 진폭 |
| `iter_###_*.hex` | 반복별 중간값 (FULL trace 56케이스만) |
| `expected_final_amp.hex` · `expected_core.json` | 최종 진폭과 결과 · 물리 반복 · 포화 횟수 |

이 벡터의 검증 범위는 수동 코어 산술로 한정됩니다. `expected_core.json`의 `scope`가 `MANUAL_CORE_BIT_EXACT`
이고, 자동 BBHT의 J 난수 · 측정 난수 · 정책 텔레메트리 · `cycle_count`는 이 벡터의
주장에서 빠져 있습니다(`excluded_from_claim`). 즉 "j를 지정했을 때 산술이 맞는가"
까지가 이 벡터의 역할입니다.

### 열거 두 방식

| 폴더 | 뜻 |
|---|---|
| `enumeration/software_reload/` | 찾은 값을 비타겟으로 바꾸고 데이터셋을 다시 적재 |
| `enumeration/projected_mask_mem/` | 하드웨어 found-mask 방식 (최종 RTL이 채택) |

두 방식에 같은 다섯 케이스가 있고, 케이스마다 `expected_result.json`과 라운드별 마스크
전후 파일을 비교합니다. 마스크 워드는 `row = index>>5`, `bit = index&31`입니다.

`q16_eq_m2`는 폐기된 Q16 확장의 기록이므로 Q14 보드 구현의 검증 근거로 사용하지 않습니다.

## 4.4 벤치 워크로드 생성기

[`rtl_vectors/tools/dump_bench_workload.py`](../../software/rtl_vectors/tools/dump_bench_workload.py)
가 `bench250` · `bench500` 자극을 만듭니다. `--seeds 50|100`으로 두 규모를 냅니다.

데이터셋을 다시 계산하지 않고 `experiments/.../inputs/`에서 복사하며, 돌 때마다 해시 ·
로스터 · 부분집합 관계를 스스로 검사합니다. 250 워크로드가 500의 부분집합이라는 것도
여기서 확인됩니다.
