## 1. 한 장으로 보는 전체 구조

```
 [호스트 PC]                                        Python + pyserial
     │  ASCII 라인 명령 / 결과.  명령과 결과만 오갑니다 — 배열은 절대 이 길로 안 갑니다
     │  USB-UART (FT2232, 115200 8N1 가정 — Phase 0 확인 항목)
 ────┼──────────────────────────────────────────────────────────────── SoC 경계
     ▼
 [RISC-V rvc_orca]  app/grover_search/main.c        파싱 · 정책 · 표시
     │  ① 제어 경로: APB 슬레이브, 워드 단위, 실행 전후에만
     │                                              ┌──────────────────────┐
     ├──────────── APB ─────────────► grover_mmio ─►│                      │
     │                                (CSR)         │   grover_top (IP)    │
 [시스템 SRAM]                                       │                      │
     │  ② 데이터 경로: AHB 마스터, 버스트, 64 KB    │  shot FSM            │
     ◄─────────── AHB INCR16 ──────── ahb_master ◄──┤  cache_ctrl          │
                                                    │  ctrl_fsm            │
                                                    │  32레인 데이터패스   │
                                                    │  amp/data/mask BRAM  │
                                                    └──────────────────────┘
```

구조를 지탱하는 원칙이 셋입니다. 나머지는 전부 여기서 따라 나옵니다.

**원칙 1 — UART로는 명령과 결과만 오갑니다.** $n=15$ 데이터 배열은 64 KB이고, 115200 8N1(바이트당 10비트)로 보내면 655,360 ÷ 115,200 = 약 5.7초입니다. 탐색 자체가 3.7 ms이므로 데이터를 넣는 데 탐색의 1,500배를 쓰게 됩니다. ASCII 16진수로 보내면 두 배인 11초고, 그동안 같은 UART로 `printf` 도 못 나갑니다. 그래서 데이터는 온칩 생성기나 AHB DMA로 넣고, UART에는 몇십 바이트짜리 명령과 결과만 흘립니다 ([17.6절](../study_references/17_RVX_SoC_통합.md#176-호스트-uart-프로토콜)).

**원칙 2 — 상태는 하드웨어가 소유합니다.** `j_cur`(지금 `amp_mem` 에 실려 있는 반복 횟수)과 `cache_valid` 는 하드웨어 레지스터이고, 소프트웨어에는 사본을 두지 않습니다. 펌웨어가 샷을 모는 모드에서도 마찬가지입니다 — 앱은 자기가 무엇을 **요청했는지**만 알고, 실제로 몇 회를 돌았는지는 하드웨어에 물어봅니다. 같은 상태가 두 곳에 있으면 반드시 어긋나고, 어긋난 결과가 크래시가 아니라 "그럴듯한 오답"으로 나옵니다 ([16.7절](../study_references/16_반복제어와_재개캐시.md#167-무효화는-하드웨어가-한다) · [17.7절](../study_references/17_RVX_SoC_통합.md#177-하드웨어와-펌웨어의-경계)).

**원칙 3 — 제어 경로와 데이터 경로는 다른 버스입니다.** 설정·상태는 한 번에 워드 하나, 실행 전후에만 오가므로 주소 디코드만 되면 충분합니다(APB). 배열 적재는 연속 주소를 죽 읽는 일이라 버스트가 필요합니다(AHB 마스터). 두 성격을 한 버스에 욱여넣으면 한쪽이 손해를 봅니다 ([17.3절](../study_references/17_RVX_SoC_통합.md#173-왜-apb와-ahb를-같이-쓰나)).

계층별로 누가 무엇을 하는지 한 표로 모으면 이렇습니다.

| 계층 | 구현체 | 하는 일 | 하지 않는 일 |
|---|---|---|---|
| 호스트 PC | `software/host/grover_cli.py` | 사람이 읽는 명령 → ASCII 라인, 결과 파싱·집계·그래프 | 알고리즘 판단 일절 없음. 배열 전송 없음 |
| 펌웨어 | `app/grover_search/src/main.c` | 라인 파싱, 값 검증, CSR 기록, 폴링, 결과 출력, 열거 종료 정책 | `j_cur` 추적, 캐시 무효화 판단 |
| CSR | `grover_mmio.v` (생성) | 주소 디코드, 설정 보관, 명령 펄스, 상태 반사, **쓰기 스트로브 OR → 캐시 무효화** | 연산 |
| IP | `grover_top.v` | 샷 루프, 캐시 판정, 진폭 갱신, 측정, 검증, DMA | 술어 선택, 재시도 정책 |

## 2. 호스트가 조작하는 방법과 형식

### 2.1 왜 ASCII 라인인가

바이너리 프레임이 더 빠르지만, 이 경로로 오가는 것이 원래 몇십 바이트뿐이라 속도가 문제가 되지 않습니다. 대신 얻는 것이 큽니다. 터미널을 열어 손으로 쳐 볼 수 있고, 로그가 그대로 사람이 읽는 실험 기록이 되며, 무엇보다 **파싱이 어긋났는지 값이 틀렸는지가 눈으로 구분됩니다.** 브링업 단계에서 이 차이가 며칠을 좌우합니다.

### 2.2 명령 문법 (초안)

[17.6절](../study_references/17_RVX_SoC_통합.md#176-호스트-uart-프로토콜)의 초안에 데이터 소스 선택과 통계 조회를 더한 형태입니다. 모든 명령은 개행으로 끝나고, 응답의 첫 토큰이 결과 종류입니다.

| 방향 | 라인 | 뜻 |
|:-:|---|---|
| → | `SET MODE=LT THR_A=1234` | 술어와 임계값. `MODE` 는 `LT` `GT` `EQ` `RANGE` |
| → | `SET MODE=RANGE THR_A=10 THR_B=90 N=15` | 범위 술어는 `THR_B` 필수, `N` 은 유효 큐비트 수 |
| → | `DATA GEN SEED=0xACE1` | 온칩 xorshift 생성기로 `data_mem` 채우기 (벤치마크용) |
| → | `DATA LOAD ADDR=0x20010000 WORDS=16384` | SoC SRAM에서 AHB DMA로 적재 (실사용) |
| → | `RUN` | 해 하나 탐색 |
| → | `ENUM` | 열거 모드 시작 |
| → | `STAT` | 마지막 실행의 카운터 조회 |
| ← | `OK` | 설정 수용 |
| ← | `ERR BAD_MODE` / `ERR RANGE_NEEDS_THR_B` / `ERR BUSY` | 거절. 이유를 토큰으로 |
| ← | `HIT idx=12045 val=87 shots=23 cycles=372104 passes=554` | 검증을 통과한 해 |
| ← | `MISS shots=64 reason=CAP` | 상한까지 못 찾음 |
| ← | `END count=17` / `END count=17 truncated=1` | 열거 종료. `truncated` 는 `M_max` 초과 |

숫자는 10진수를 기본으로 하고 `0x` 접두사를 허용합니다. `THR_A` `THR_B` 는 16비트 signed이므로 음수를 받아야 합니다 — 파서가 부호를 빠뜨리면 `LT` 술어의 절반이 조용히 죽습니다.

### 2.3 호스트 쪽에서 고려할 것

**흐름 제어가 없습니다.** UART는 8N1 원시 스트림이고 하드웨어 흐름 제어를 쓰지 않으므로, 호스트가 명령을 연달아 밀어 넣으면 펌웨어가 폴링 루프에 갇혀 있는 동안 RX FIFO가 넘칠 수 있습니다. 호스트 CLI는 **응답을 받은 뒤에 다음 명령을 보내는** 것을 규약으로 삼습니다.

**타임아웃이 반드시 필요하고, 그 값은 알고리즘이 정합니다.** 정답이 하나도 없으면($M=0$) BBHT는 원리적으로 끝나지 않습니다. 그래서 호스트 타임아웃은 임의로 고르는 값이 아니라 펌웨어의 샷 상한과 짝을 이뤄야 합니다 — 이 항목은 [16.9절](../study_references/16_반복제어와_재개캐시.md#169-아직-정하지-않은-것)의 미정 1번과 같은 문제입니다(§7 참조).

**결과 스트림과 로그가 같은 UART를 씁니다.** `printf` 디버그 출력이 `HIT` 줄 사이에 끼어들면 호스트 파서가 깨집니다. 응답 라인에 접두사를 붙이거나(`< HIT ...`), 디버그 출력을 컴파일 타임 스위치로 끄는 규약이 필요합니다.

## 3. 제어 경로 — 명령이 CSR까지 가는 길

### 3.1 RVX MMIO 생성기의 규약

CSR 맵을 설계하기 전에 도구가 정해 놓은 것부터 알아야 합니다. `lec_ahb` 예제의 생성 결과에서 확인한 규약입니다 ([17.4절](../study_references/17_RVX_SoC_통합.md#174-csr-맵)).

- **레지스터 간격은 8바이트입니다.** 데이터는 32비트인데 오프셋이 `0x0, 0x8, 0x10, …` 으로 나갑니다. 절반이 비지만 주소 디코드가 단순해지는 대가입니다. 정렬되지 않은 접근과 미할당 주소는 `rpslverr` 로 떨어집니다.
- **명령형 레지스터는 저장 공간이 없습니다.** 쓰기가 들어오면 **한 사이클 펄스**만 나가고 읽으면 0입니다. 무엇을 썼는지는 무시되며, 예제 API도 그냥 0을 씁니다 — "쓰는 행위" 자체가 명령입니다.
- **상태 레지스터는 입력 포트를 그대로 반사합니다.** 저장하지 않고 IP가 내보내는 와이어를 읽기 응답에 실어 보냅니다.
- **설정 레지스터는 MMIO 블록 안에 저장되고** 리셋값이 매크로로 같이 생성되며, 값은 출력 와이어로 상시 나갑니다. `rpready` 는 상수 1이라 대기 상태가 없습니다.

### 3.2 두 초안의 차이

CSR 맵 초안이 두 벌 있고 서로 어긋납니다.

| 쟁점 | [개발계획.md §6](개발계획.md#6-csr-맵-초안) | [17.4절](../study_references/17_RVX_SoC_통합.md#174-csr-맵) |
|---|---|---|
| 명령 | `ctrl` 한 워드에 비트로 (`start`/`force_init`/`clear_mask`/`load_data`/`auto_shot`) | `clear_mask`·`load_start`·`force_init`·`start` 각각 W1P 레지스터 |
| 데이터 소스 | `data_src` 32비트 하나 (주소 또는 시드) | `data_addr` + `data_words` 둘 |
| `auto_shot` | `ctrl` bit4 | 없음 |

### 3.3 통합 권고

**명령은 각각 W1P 레지스터로 나눕니다.** 근거가 둘입니다. 첫째, 명령형 레지스터는 저장 공간이 없는 펄스이므로 **쓰기 데이터가 바깥으로 나오는지 자체가 확인되지 않았습니다** — 예제 API가 값 0을 쓰는 것으로 미루어 데이터는 무시된다고 보는 편이 안전하고, 그러면 `ctrl` 의 비트로 명령을 구분하는 방식이 성립하지 않습니다. 둘째, 그리고 이쪽이 결정적인데, **`auto_shot` 은 명령이 아니라 모드입니다.** 샷 루프를 누가 도는지를 정하는 설정이라 `start` 이후에도 값이 남아 있어야 하는데, 펄스 레지스터에 넣으면 쓴 그 사이클에만 존재합니다. 펄스와 유지형을 한 레지스터에 섞는 것은 [개발계획.md](개발계획.md) Phase 2가 리스크로 적어 둔 바로 그 오해입니다.

**데이터 소스는 나눕니다.** DMA는 시작 주소와 길이가 둘 다 필요하고, 생성기는 시드가 필요합니다. 하나의 32비트 레지스터에 주소와 시드를 겹쳐 두면 브링업 중 레지스터 덤프를 읽을 때 그 값이 무엇인지 알 수 없게 됩니다. 8바이트 간격이라 주소 공간은 넉넉하므로 아낄 이유가 없습니다.

통합안입니다. **오프셋은 생성기가 다시 매길 수 있으므로 순서만 의미가 있습니다.**

| 오프셋 | 이름 | 폭 | 접근 | 뜻 | 무효화 |
|--:|---|:-:|:-:|---|:-:|
| `0x00` | `mode` | 2 | RW | 0:`LT` 1:`GT` 2:`EQ` 3:`RANGE` | ● |
| `0x08` | `thr_a` | 16 | RW | 임계값 A (signed) | ● |
| `0x10` | `thr_b` | 16 | RW | 임계값 B — 범위 술어 상한 (signed) | ● |
| `0x18` | `n_qubits` | 5 | RW | 유효 큐비트 수 | ● |
| `0x20` | `enum_mode` | 1 | RW | 0:하나만 1:열거 | ● |
| `0x28` | `auto_shot` | 1 | RW | 0:펌웨어 구동 1:BBHT 자율 | |
| `0x30` | `j_target` | 16 | RW | **절대** 목표 반복 횟수. `auto_shot=1` 이면 무시됨 | |
| `0x38` | `data_addr` | 32 | RW | DMA 원본 주소 | ● |
| `0x40` | `data_words` | 32 | RW | 적재할 32비트 워드 수 (16의 배수) | ● |
| `0x48` | `data_seed` | 32 | RW | 온칩 생성기 시드 | ● |
| `0x50` | `data_sel` | 1 | RW | 0:AHB DMA 1:온칩 생성기 | ● |
| `0x58` | `clear_mask` | — | W1P | `mask_mem` 전체 클리어 | ● |
| `0x60` | `load_start` | — | W1P | 적재 시작 | ● |
| `0x68` | `force_init` | — | W1P | 캐시를 버리고 초기화부터 | ● |
| `0x70` | `start` | — | W1P | 실행 시작. `done`·`verify_hit`·카운터를 같이 클리어 | |
| `0x78` | `status` | 6 | RO | bit0 `busy` · bit1 `done` · bit2 `verify_hit` · bit3 `cache_valid` · bit4 `sat_sticky` · bit5 `too_many` | |
| `0x80` | `cand` | 15 | RO | 검증을 통과한 후보 인덱스 | |
| `0x88` | `j_cur` | 16 | RO | 지금 `amp_mem` 에 실려 있는 반복 횟수 | |
| `0x90` | `cycle_cnt` | 32 | RO | 벽시계 — 마지막 `start` 이후 소비 사이클 | |
| `0x98` | `passes_run` | 32 | RO | 알고리즘 지표 — 마지막 `start` 이후 누적 패스 | |

**`j_target` 이 절대값인 이유**는 재개 캐시 판정식이 `j_target < j_cur` 이라 두 값이 같은 원점을 공유해야 하기 때문입니다. 상대값 $\Delta j$ 를 받으면 펌웨어가 `j_cur` 을 따로 추적해야 하고, 그 순간 원칙 2가 무너집니다.

**`auto_shot=1` 일 때 `j_target` 을 하드웨어가 갱신하지는 않습니다.** [17.4절](../study_references/17_RVX_SoC_통합.md#174-csr-맵) 본문은 "LFSR이 매 샷 이 레지스터를 갱신한다"고 적었지만, 생성된 MMIO 블록의 설정 레지스터는 APB 쓰기로만 값이 바뀌므로 IP가 거꾸로 써 넣을 포트가 없습니다. 구현은 IP 안에서 먹스 하나로 정리됩니다 — `j_req = auto_shot ? lfsr_draw : csr_j_target` 이고, 실제로 무엇을 돌았는지는 `j_cur`(RO)이 알려 줍니다. CSR 맵에 미치는 영향은 없고 결선만 이렇게 됩니다.

### 3.4 무효화 배선 — 통신 구조와 캐시가 만나는 지점

표 오른쪽 ● 열이 이 절에서 가장 중요합니다. **● 가 붙은 레지스터에 쓰기가 들어오면 그 자리에서 `cache_valid` 가 0으로 떨어집니다.** 주소 디코더가 이미 레지스터별 쓰기 스트로브를 만들고 있으므로, 그 스트로브들의 OR를 `cache_valid` 의 클리어 입력에 물리면 끝입니다.

```
 mode_we ─┐
 thr_a_we ┤
 thr_b_we ┤
 n_we ────┼──► OR ──► cache_valid.clear
 enum_we ─┤
 data_*_we┤
 clr_msk ─┤
 load_st ─┘
```

게이트 몇 개가 "낡은 진폭 위에 새 오라클이 얹혀 조용히 틀린 답이 나오는" 종류의 버그를 통째로 없앱니다. 이것을 펌웨어에 맡기면 안 되는 이유는 [16.7절](../study_references/16_반복제어와_재개캐시.md#167-무효화는-하드웨어가-한다)에 있습니다 — 나중에 술어를 하나 더 추가한 사람이 무효화를 빼먹는 순간, 크래시도 타임아웃도 아닌 그럴듯한 인덱스 하나가 나옵니다.

여기에 도구 쪽 확인이 하나 걸립니다. 예제의 생성된 MMIO 블록이 **바깥으로 내보내는 쓰기 스트로브는 명령형 레지스터의 것 하나뿐**이고, 일반 설정 레지스터의 `we` 는 모듈 안에 갇혀 있습니다. 그러니 (a) 생성기 입력 XML에서 설정 레지스터도 스트로브를 내보내게 하거나, (b) `test1_apb.v` 처럼 APB 디코드를 손으로 쓰거나 둘 중 하나입니다. 생성기 입력 XML의 스키마가 아직 확인되지 않았으므로 **(b)를 기본안**으로 둡니다 — 손으로 써도 100줄이고 스트로브를 전부 우리가 쥡니다.

## 4. 명령 하나가 지나는 전체 순서

`RUN` 한 줄이 도착해서 `HIT` 한 줄이 나갈 때까지입니다. BBHT 자율 모드(`auto_shot=1`) 기준이고, 펌웨어 구동 모드는 §4.3에서 갈라집니다.

```
  호스트          펌웨어(rvc_orca)              CSR              IP
    │                  │                        │                │
 1  │─ "RUN\n" ───────►│                        │                │
    │                  │ uart_getc 루프로 라인 수집, 파싱, 검증  │
 2  │                  │─ status 읽기 ─────────►│                │   busy면 ERR BUSY
 3  │                  │─ mode/thr/n 쓰기 ─────►│─ we OR ───────►│   cache_valid ← 0
 4  │                  │─ auto_shot=1 쓰기 ────►│                │
 5  │                  │─ start (W1P) ─────────►│─ 펄스 ────────►│   busy←1, done←0
    │                  │                        │                │   카운터 클리어
 6  │                  │                        │        ┌───────┴────────┐
    │                  │  (폴링)                │        │ 샷 루프 시작   │
    │                  │─ status 읽기 ─────────►│        │ m←1           │
    │                  │◄─ busy=1 ──────────────│        │ j 추첨        │
    │                  │                        │        │ 캐시 판정     │
    │                  │                        │        │ INIT? / Δj 전진│
    │                  │                        │        │ 측정 → 검증   │
    │                  │                        │        │ 실패면 m 확대 │
    │                  │                        │        │  → 다음 샷    │
 7  │                  │◄─ busy=0, done=1 ──────│◄───────┤ 성공/상한      │
 8  │                  │─ cand/status/카운터 ──►│                │
 9  │◄ "HIT idx=..." ──│                        │                │
```

### 4.1 핸드셰이크 규약 — 브링업에서 반드시 물리는 것

**규약 1. `start` 는 `done`·`verify_hit`·`cycle_cnt`·`passes_run` 을 같이 클리어합니다.** 그렇지 않으면 폴링이 직전 실행이 남긴 `done=1` 을 보고 곧바로 통과해 **낡은 `cand` 를 읽습니다.** 결과가 그럴듯한 인덱스라 시뮬레이션에서 잡기 어려운 부류입니다.

**규약 2. 완료 판정은 `done` 이 서는 것이 아니라 `busy` 가 내려가는 것으로 합니다.** 예제 API도 같은 모양입니다(`while(get_state()!=0);`). `done` 은 "왜 끝났는지"를 나누는 용도로만 씁니다.

**규약 3. 결과는 `busy=0` 인 동안에만 읽습니다.** `cand`·`status`·`cycle_cnt`·`passes_run` 은 APB 트랜잭션 네 번에 나눠 읽히므로, 그 사이에 새 실행이 시작되면 서로 다른 시점의 값이 섞인 스냅샷을 얻습니다.

**규약 4. 적재 중에는 `start` 를 받지 않습니다.** `load_start` 뒤에는 `busy` 가 서고 그동안 들어온 `start` 펄스는 무시됩니다. 절반만 채워진 `data_mem` 위에서 오라클을 돌리면 아무 경고 없이 틀린 답이 나옵니다. 펄스가 조용히 버려지므로, **펌웨어가 `start` 전에 `busy` 를 확인하는 것이 규약**입니다(§4 순서 2번).

**규약 5. 두 카운터는 `start` 로 클리어되고 `done` 까지 셉니다.** 자율 모드에서는 한 번의 `start` 가 샷 여러 번을 덮으므로 이 정의만으로 "탐색 한 번"의 값이 됩니다. `cycle_cnt` 는 벽시계($\sum|\Delta j|$ 에 대응), `passes_run` 은 알고리즘 지표($\sum j_k$ 에 대응)이고, 이 둘을 갈라 두는 이유는 §6.4에 있습니다.

### 4.2 열거 모드

`ENUM` 은 라운드 반복입니다. 펌웨어가 `clear_mask` → `enum_mode=1` 로 시작하고, 한 라운드가 해 하나를 찾으면 그 인덱스의 `found` 비트가 서고 캐시가 무효화되며 다음 라운드가 돕니다. 정답이 남지 않으면 종료합니다. 호스트에게는 `HIT` 줄이 계속 오다가 `END` 로 닫히는 스트림으로 보입니다.

**종료 판단은 펌웨어가 쥡니다.** 해를 몇 개까지 받을지, 못 찾으면 몇 번 더 시도할지는 응용마다 다른 정책이고 정책은 재합성 없이 바뀌어야 하기 때문입니다. 하드웨어는 판단 재료(`status.too_many`, `cand`, `passes_run`)만 정확히 제공합니다.

### 4.3 펌웨어 구동 모드

`auto_shot=0` 이면 §4 순서의 6번이 펌웨어로 올라옵니다. 앱이 BBHT 수열을 직접 계산해 매 샷 **절대값** `j_target` 을 쓰고 `start` → 폴링 → `verify_hit` 확인을 반복합니다. 샷 하나마다 멈춰 세워 골든 모델과 대조할 수 있어 디버깅이 쉽고, 그래서 [개발계획.md](개발계획.md) Phase 5a가 이쪽을 먼저 만듭니다. 완성한 뒤에도 이 모드는 남습니다 — 캐시 정확성 증명, $M$ 을 아는 비교 모드, 골든 모델 비트정확 재생 세 자리에서 계속 쓰입니다.

두 모드가 공존해도 상태가 갈라지지 않는 것은 **어느 쪽이든 `j_cur` 과 `cache_valid` 를 하드웨어가 소유하기 때문**입니다. 펌웨어는 "무엇을 요청했는가"만 알고, "지금 배열이 어떤 상태인가"는 물어봅니다.

## 5. 데이터패스

"데이터패스"가 이 프로젝트에서 두 가지를 가리키므로 나눠 적습니다. 하나는 **탐색 대상 배열이 어디서 와서 어디로 가는가**(§5.1)이고, 다른 하나는 **진폭이 한 사이클에 어떤 산술을 통과하는가**(§5.2)입니다.

### 5.1 시스템 데이터패스 — 배열이 들어오는 두 갈래

```
   (A) 실사용                          (B) 벤치마크
   호스트 or SPI 플래시                 CSR: data_seed
        │                                   │
        ▼                                   ▼
   SoC 시스템 SRAM (128 kB)            grover_data_gen (xorshift/LFSR)
        │                                   │
        │ AHB INCR16, HSIZE=4B              │ 시프트와 XOR만
        │ 버스트당 64 B                      │
        ▼                                   ▼
   grover_ahb_master  ──────────► data_mem (32뱅크 × 1024 × 16b)
```

**(A) AHB DMA.** $n=15$ 면 32,768개 × 16비트 = 64 KB입니다. `HBURST=INCR16` · `HSIZE=4바이트`, 즉 32비트 전송 16개짜리 증가 버스트라 버스트당 64바이트이고, 64 KB면 32비트 워드 16,384개 · 버스트 1,024개입니다. 이상적으로 사이클당 한 전송이면 16,384사이클, 100 MHz에서 **약 0.16 ms** — 탐색 한 번(3.7 ms)의 4% 남짓입니다. 전송 하나가 16비트 데이터 두 칸을 실어 나르므로 폭도 딱 맞습니다.

규약 셋을 못 박아 둡니다. **적재 중 `start` 금지**(§4.1 규약 4), **워드 수는 16의 배수**(INCR16 버스트를 끊지 않기 위해서이고, $N/2$ 워드는 $n \ge 5$ 이면 자연히 만족합니다), **적재는 캐시를 무효화**(데이터가 바뀌면 술어가 같아도 정답 집합이 달라집니다).

여기에 시스템 층 제약이 하나 걸립니다. **배열 64 KB는 RVX 시스템 SRAM에 그냥 얹기에는 큽니다.** 예제의 기본값이 64 kB라 배열 하나로 SRAM 전체를 다 씁니다. 프로그램과 스택 자리를 만들려면 최소 128 kB로 올려야 하고, 그러면 SoC 쪽 BRAM 몫도 대략 두 배가 되어 IP 소계 33개와 합친 값이 보드의 75개에 훨씬 가까워집니다. 정확한 증분은 Phase 0의 구현 리포트로만 확정됩니다 ([17.5절](../study_references/17_RVX_SoC_통합.md#175-데이터-적재--ahb-마스터)).

**(B) 온칩 생성기.** 시드 하나로 `data_mem` 을 채웁니다. 호스트와 SoC SRAM을 아예 건너뛰고, 시드가 같으면 배열이 같으므로 재현성도 확보됩니다. 선형 합동 생성기(LCG)를 쓰지 않는 것은 32비트 곱셈이 DSP를 물어와 "확산 경로의 곱셈기 0개"라는 점검 기준을 흐리기 때문이고, 시프트와 XOR만 쓰는 xorshift/LFSR로 짜면 그 기준이 그대로 유지됩니다. $M$ 을 바꿔 가며 샷 수를 재는 종류의 실험에는 이쪽이 압도적으로 편합니다.

### 5.2 연산 데이터패스 — 32레인이 한 사이클에 하는 일

주소 구조부터 봅니다. `amp_mem` 과 `data_mem` 은 32뱅크로 쪼개져 있고 **인덱스의 하위 5비트가 뱅크 번호, 상위 10비트가 뱅크 내 주소**입니다($n=15$). 사이클 $c$ 에는 32뱅크가 **모두 같은 주소 $c$** 를 읽으므로 뱅크 충돌이 원리적으로 0이고, 크로스바나 순열망이 필요 없습니다. 진폭을 임의로 재배치해야 하는 범용 게이트 시뮬레이터가 순열망 하나에 로직의 3분의 1을 쓰는 것과 대조됩니다 ([13.7절](../study_references/13_오라클_확산_측정_데이터패스.md#137-32레인-데이터패스와-누산-순서)).

**1패스 (`S_PASS1`) — 오라클과 누산이 같은 사이클에.**

```
 data_mem[c] ─┬─► 17b 감산기 (부호확장) ─► MSB ─┐
              └─► XOR-NOR (EQ 전용) ──────────┤
 thr_a/thr_b ─┘                               ├─► hit
 mask_mem[c] ─────────► ~found[i] ────────────┘   (열거 모드에서만)
                                                │
 amp_mem[c] ──────────────────────────────────► XOR + carry-in ──► amp_mem[c]
                                                │  (조건부 2의 보수 부정)
                                                └──► 5단 가산 트리 ──► sum_accum (35b)
```

비교기 IP를 부르지 않습니다. **비교는 뺄셈의 부호비트 하나**입니다. `GT` 는 피연산자를 바꿔 넣기만 하면 되어 공짜이고, `EQ` 는 감산기조차 필요 없이 XOR 한 층과 NOR 한 층이며, `RANGE` 만 감산기가 둘입니다. 부호확장을 빠뜨리면 $v = -32768$, $t = 1$ 같은 입력에서 뺄셈이 오버플로해 부호비트가 뒤집히므로 17비트로 넓히는 한 줄이 필수입니다 ([13.3절](../study_references/13_오라클_확산_측정_데이터패스.md#133-oracle--술어-4종이-감산기-하나를-공유한다)).

**오라클은 사이클을 한 개도 쓰지 않습니다.** 진폭을 읽어 되쓰는 김에 부호를 뒤집으므로 독립된 패스가 없습니다.

**중간 (`S_MEAN`) — 1사이클.** 누산기를 $n-1$ 칸 한 번에 밀어 $2\bar a$ 를 만듭니다. 평균을 만든 뒤 2를 곱하는 2단 구현은 금지입니다 — 떨어져 나간 최하위 비트가 0으로 채워지고 반올림 지점이 두 곳으로 갈라져 골든 모델과 영원히 어긋납니다. **한 번의 그로버 반복에서 소수부가 깎이는 곳은 여기 한 순간뿐**이고, round-half-to-even이 적용되는 자리도 오직 여기입니다 ([13.5절](../study_references/13_오라클_확산_측정_데이터패스.md#135-diffusion--2mean--amp가-회로가-되는-순간)).

**2패스 (`S_PASS2`).** 확정된 $2\bar a$ 가 32레인에 브로드캐스트되고 각 레인이 뺄셈 하나씩을 합니다. 포화 처리를 붙입니다 ([12.5절](../study_references/12_고정소수점과_정밀도.md#125-오버플로-정책--포화랩-금지재정규화-없음)).

**측정 (`S_MEAS`) — 2단 병렬.** 패스 1에서 제곱기 32개로 뱅크별 제곱합과 전체를 구하고(1,024사이클), 32항 prefix-sum으로 난수가 떨어지는 뱅크를 고르고(32사이클), 패스 2에서 그 뱅크만 직렬로 훑습니다(1,024사이클). 합쳐 **2,080사이클**로 직렬 스캔의 32,768사이클에서 약 16배 줄었습니다. 뱅크 우선 순회가 분포를 바꾸지 않는 것은 결합확률에서 뱅크 합이 약분되기 때문이고, 더 근본적으로는 역변환 샘플링이 순회 순서에 무관하기 때문입니다 ([14.5절](../study_references/14_다중정답과_최솟값탐색.md#145-2단-병렬-측정)).

**검증 (`S_VERIFY`) — 한두 사이클.** 측정이 뱉은 `cand` 하나로 `data_mem[cand]` 를 읽어 술어를 다시 판정합니다. 1패스가 쓰는 것과 **완전히 같은 술어 유닛**을 적용 범위만 바꿔 재사용합니다. 이 한 칸 확인이 IP의 출력을 "틀릴 수도 있는 확률적 답"에서 "맞다고 확인된 답, 또는 아직 못 찾음"으로 바꿉니다.

**사이클 예산** ($n=15$, $P=32$, 100 MHz):

| 구간 | 사이클 | 시간 |
|---|--:|--:|
| `S_INIT` | 1,024 | 10.2 µs |
| 그로버 반복 1회 (2패스) | 2,048 | 20.5 µs |
| 측정 (2단 병렬) | 2,080 | 20.8 µs |
| 검증 | ~2 | — |
| 데이터 적재 (AHB, 64 KB) | 16,384 | ~0.16 ms |
| 탐색 전체 ($M=1$, 캐시 켬) | 370,812 | **3.7 ms** |

곱셈기 분포는 이렇습니다. **INIT·오라클·확산 경로에는 곱셈기가 0개**입니다 — 초기화는 상수 우시프트, 오라클은 감산기와 XOR, 확산은 가산 트리·산술 우시프트·뺄셈뿐입니다. **측정 경로에만 제곱기 32개(DSP 32/120)**가 잡히고, 그것이 정상입니다. 합성 리포트를 볼 때는 총 DSP 수가 아니라 **어느 모듈에서 잡혔는지**를 봐야 합니다 ([13.8절](../study_references/13_오라클_확산_측정_데이터패스.md#138-곱셈기는-어디에-있고-어디에-없는가)).

## 6. 캐시 — 어디에 어떤 자원으로 붙는가

### 6.1 자리

캐시는 **바깥 샷 FSM과 안쪽 반복 FSM 사이**에 놓인 판정 블록입니다(`grover_cache_ctrl.v`). 데이터패스 안에 있지 않고, 데이터패스를 **몇 번 돌릴지**를 정할 뿐입니다.

```
 [샷 FSM] ── j_target ──►┌──────────────┐
                         │ cache_ctrl   │── init_req ──►[ctrl_fsm]
 [CSR] ── force_init ───►│              │── delta ─────►
 [CSR we OR] ── clear ──►│ j_cur (16b)  │
                         │ cache_valid  │──► status.cache_valid
                         └──────────────┘
```

### 6.2 자원

**`j_cur`(16비트 레지스터)과 `cache_valid`(1비트 레지스터) 둘이 전부입니다. BRAM은 한 개도 늘지 않습니다.** 진폭 배열의 사본을 뜨는 것이 아니라 이미 거기 있는 배열을 **지우지 않는 것**이기 때문입니다.

### 6.3 규칙

```
if (!cache_valid || force_init || j_target < j_cur)   INIT 후 j_target 회 전진
else                                                  (j_target - j_cur) 회만 전진
j_cur <= j_target;  cache_valid <= 1'b1;
```

성립 근거는 **`amp_mem` 에 쓰는 주체가 셋뿐**이라는 관찰입니다 — INIT, 오라클, 확산. Born 측정은 진폭을 읽어 제곱을 누적할 뿐 한 글자도 쓰지 않고, 검증은 `data_mem` 의 한 칸만 봅니다. 그래서 샷이 실패해 돌아온 시점에도 `amp_mem` 에는 $j_{cur}$ 회 반복한 상태가 고스란히 남아 있습니다 ([16.5절](../study_references/16_반복제어와_재개캐시.md#165-재개-캐시--측정이-읽기-전용이라는-사실에서)).

결과가 달라지지 않는 이유는 $(DO)^{j}$ 의 결합법칙입니다. 재개 경로가 만드는 연산열은 새로 INIT해서 $j_{target}$ 회 돌린 것과 **문자 그대로 같은 연산열**이고, 산술이 결정적이므로 근사적으로가 아니라 **비트 단위로 동일**합니다. 측정 난수는 샷마다 새로 뽑으므로 각 샷은 여전히 독립 시행이고 BBHT 통계도 그대로입니다 ([16.6절](../study_references/16_반복제어와_재개캐시.md#166-왜-결과가-달라지지-않는가)).

되감기($j_{target} < j_{cur}$ 일 때 뒤로 감기)는 채택하지 않았습니다. 실측상 오히려 **1% 더 느리고**($j$ 가 절반 넘게 줄어드는 경우가 흔해 INIT 후 전진이 더 쌉니다) 고정소수점에서 $OD$ 가 $DO$ 의 정확한 역이 아니라 가역성 증명 부담이 붙습니다 ([16.8절](../study_references/16_반복제어와_재개캐시.md#168-기각한-대안)).

### 6.4 통신 구조가 캐시에 지는 책임

내 역할과 캐시가 맞물리는 지점이 정확히 셋입니다.

**첫째, 무효화 배선(§3.4).** CSR 쓰기 스트로브의 OR가 `cache_valid` 를 내립니다. `cache_valid` 는 한 비트지만 실제로는 "지금 배열에 든 것은 어떤 술어·임계값·마스크·$n$ 으로 $j_{cur}$ 회 돌린 결과인가"라는 튜플 전체를 요약한 비트입니다.

**둘째, `j_target` 을 절대값으로 넘기는 것(§3.3).** 상대값을 받으면 펌웨어가 `j_cur` 사본을 갖게 되고 원칙 2가 무너집니다.

**셋째, 카운터를 둘로 가르는 것(§4.1 규약 5).** 재개 캐시는 **벽시계만 줄이고 알고리즘 지표는 줄이지 않습니다.** 이걸 섞어 "그로버 반복을 35% 줄였다"고 쓰면 거짓말이 됩니다 — 줄어든 것은 에뮬레이션 시간이지 알고리즘이 오라클에 던진 질의 횟수가 아닙니다. `cycle_cnt` 와 `passes_run` 을 따로 읽을 수 있어야 보고할 때 정직하게 갈라 적을 수 있습니다.

### 6.5 효과와 한계

$n=15$ · $M=1$ 에서 554패스가 362패스로, **35%** 줄어듭니다(몬테카를로 20,000회). $M$ 이 커지면 애초에 샷 수가 줄어 절감률도 완만히 낮아집니다 — $M{=}4$ 에서 34%, $M{=}32$ 에서 32%, $M{=}256$ 에서 29%입니다.

**캐시와 측정 병렬화는 한 쌍입니다.** 측정을 직렬 CDF로 두면 캐시가 아낀 반복이 측정에 묻혀 절감이 15%로 떨어집니다(1,296 → 1,103패스). 2단 병렬 측정과 함께 써야 35%입니다(554 → 362패스. 둘 다 $n=15$·$M=1$·몬테카를로 20,000회).

**열거 모드에서는 캐시 이득이 0입니다.** 라운드마다 `found` 마스크가 바뀌어 오라클 자체가 달라지므로 매 라운드가 무효화로 시작합니다. 캐시는 한 라운드 안의 샷들 사이에서만 일합니다.
