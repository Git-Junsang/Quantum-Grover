## 0. 왜 다시 잘라야 하는가

[개발계획.md](개발계획.md)는 Phase 0 → 7의 **선형 순서**로 쓰여 있습니다. 혼자 만들 때는 맞지만, 넷이 그대로 따르면 세 명이 Phase 0과 Phase 1이 끝나기를 기다리며 놉니다.

병렬화의 열쇠는 하나입니다. **골든 모델을 한 사람이 쓰지 않고, 각자 자기 영역의 골든을 쓴 다음 같은 영역의 RTL을 그것과 대조하는 것.** 그러면 네 사람이 각자 "골든 → RTL → tb 통과"라는 닫힌 고리를 따로 돌릴 수 있고, 서로를 기다리는 지점이 **통합 지점 세 곳**으로 줄어듭니다.

여기에 이 프로젝트만의 유리한 조건이 하나 더 있습니다. **원격 서버가 필요한 사람은 한 명뿐입니다.** RVX 생성·ModelSim·Vivado는 전부 원격(`cau01.rvx.coreicc.net`)이지만, `iverilog`·`vvp`·`verilator`는 로컬에 있습니다. 즉 A를 뺀 셋은 원격이 막혀도 계속 일할 수 있고, 이 프로젝트 최대 일정 리스크가 한 사람에게 격리됩니다.

## 2. 스프린트 0 — 계약 동결 (전원, 가장 먼저)

**이 단계를 건너뛰면 병렬이 성립하지 않습니다.** 각자 만든 것을 나중에 붙일 때 포트 폭이 다르고 반올림 지점이 다르고 난수 순서가 달라서, 통합에 쓰는 시간이 병렬로 아낀 시간을 넘습니다.

동결 대상 여덟입니다.

|:-:|---|:-:|:-:|---|

## 3. 스프린트 1 — 골든 모델 (완전 병렬, 서로 안 기다림)

각자 자기 영역의 골든을 씁니다. **의존이 0인 이유**를 각 줄에 적어 둡니다.

| | 하는 일 | 의존 | 왜 안 기다려도 되나 |
|:-:|---|:-:|---|
| **A** | **Phase 0 전체** — RVX 원격 접속, `hello`(VP·RTL), `make imp_fpga` 리포트, **UART RX 에코**, `SYSTEM_CLK_HZ` 확인 / `gen_vectors.py` 포맷, `run_all.py` 뼈대 | 없음 | 리스크 최전선이라 가장 먼저 찔러야 합니다 |
| **B** | `golden/predicate.py` — 술어 4종 + 경계값 진리표(`thr_a`, `thr_a±1`, MIN, MAX) / `sweep_predicate.py` | 없음 | 순수 조합 함수입니다 |
| **C** | `golden/grover_float.py` → `grover_fixed.py` / `sweep_bitwidth.py` · `sweep_qformat.py` (D1·D2 확정) | 없음 | 오라클은 **정답 인덱스를 못 박은 형태**로 시작합니다. B의 술어는 나중에 갈아 끼웁니다 |
| **D** | `golden/bbht.py` — BBHT 수열·샷 통계 / `sweep_cache.py` 몬테카를로 20,000회 | 없음 | 샷 통계는 성공확률의 **해석식**으로 나옵니다. C의 진폭 배열이 필요 없습니다 |

C가 오라클을 "정답 인덱스 하드코딩"으로 시작하는 것은 임시방편이 아니라 **검증 발판**입니다. 판정 로직이 없으면 확산과 반복만 남아서 [9.4절](../study_references/09_그로버_알고리즘.md#94-진짜로-한-번-돌려보기--n4)의 손계산과 한 칸씩 대조할 수 있습니다.

D가 C를 안 기다려도 되는 것이 이 분할의 가장 큰 이득입니다. 재개 캐시의 **절감률**은 샷 수열의 문제라 진폭 산술과 무관하고, 진폭이 실제로 같은지는 나중에 RTL tb에서 확인합니다.

**닫는 조건** — A: 원격 왕복 성공 + 자원 리포트 확보. B: 경계값 진리표 통과. C: float 모델이 [반복횟수_결정.md](반복횟수_결정.md) 3절 표와 소수 4자리 일치 + Q2.16·half-even에서 포화 0회. D: 평균 24.5샷(n=15·M=1·몬테카를로 20,000회) 재현.

## 4. 스프린트 2 — RTL, P=1 (병렬, 각자 자기 tb)

| | 하는 일 | 대조 대상 |
|:-:|---|---|
| **A** | **Phase 2** — mmio XML/수기 CSR, `grover_soc_top.v` 래퍼, 더미 `grover_top`, `grover_api.c`, app 파서, `grover_cli.py` | `tb_grover_csr.v` 라운드트립 |
| **B** | `grover_predicate.v` | 자기 `golden/predicate.py` 진리표 |
| **C** | `grover_lane.v`, `grover_two_mean_calc.v`, `adder_tree`(P=1 통과), `sum_accum`, mem 래퍼, `grover_ctrl_fsm.v` | 자기 `grover_fixed.py`. **tie 케이스 1000개 포함** |
| **D** | `grover_lfsr.v`, `grover_iter_rom.v`, 카운터 / `grover_cache_ctrl.v` 로직 | 자기 `bbht.py` 수열 |

A의 **철칙** 하나를 여기서 못 박습니다 — `grover_top.v` 는 `ervp_*.vh` 를 include하지 않습니다. RVX 의존성을 SoC 래퍼에 가둬야 B·C·D가 iverilog 단독으로 계속 돌릴 수 있습니다. 이 한 줄이 깨지면 셋이 원격 서버에 묶입니다.

D의 `cache_ctrl` 은 아직 붙일 데이터패스가 없지만, 입력(`j_target`·`j_cur`·`cache_valid`·`force_init`)과 출력(`init_req`·`delta`)만 있으면 단독 tb로 규칙 세 줄을 다 검증할 수 있습니다.

### 통합 지점 1 — P=1 코어 (B + C + A)

B의 `predicate` 를 C의 `lane` 에 결선하고 A의 `top` 에 넣습니다. **합격 기준**: n=8,10,12 × 술어 4종 × j=0..R 전부에서 `amp` 배열이 `golden/vectors/expect_amp_j*.hex` 와 **전 워드 일치**.

여기가 진짜 병목입니다. B와 C가 **둘 다** 끝나야 열리고, 여기서 막히면 스프린트 3의 전원이 멈춥니다. 그래서 B·C는 스프린트 2 중반에 한 번 미리 붙여 보는 편이 안전합니다(포트만 맞춰 본 "드라이 런").

## 5. 스프린트 3 — 병렬화·측정·캐시 (병렬)

| | 하는 일 |
|:-:|---|
| **A** | **Phase 6** — `grover_ahb_master.v`(INCR16), `grover_data_gen.v`(xorshift), 플랫폼 XML에 AHB 심 추가 |
| **B** | `grover_mask_mem.v` + 열거 라운드 로직 (`predicate ∧ ¬found[i]`) |
| **C** | P=32 뱅킹, 32입력 5단 `adder_tree`, **`grover_born_sampler.v`** (제곱기 32 · prefix-sum · 안전망) |
| **D** | `grover_cache_ctrl.v` 정식 결선, `grover_shot_fsm.v`(Phase 5b), `tb_cache_bbht.v` · `tb_cache_invalidate.v` |

D의 Phase 5a(펌웨어 구동 모드)는 A의 앱을 기다리는 것처럼 보이지만, **기다릴 필요가 없습니다.** 앱이 하는 일은 CSR에 `j_target` 을 쓰는 것뿐이고 그것은 tb가 그대로 할 수 있습니다. `cache_walk.txt` 를 재생하는 `tb_cache_bbht.v` 로 캐시 정확성을 먼저 닫고, A의 앱은 나중에 같은 레지스터를 두드리면 됩니다.

### 통합 지점 2 — P=32 + 측정 + 캐시 (전원)

**합격 기준** 넷입니다.

- 같은 seed에서 **P=1 결과와 P=32 결과가 비트 동일** (P가 성능 파라미터일 뿐임을 증명)
- 반복 1회 = 정확히 `2·(N/P)` 사이클 (n=12·P=32 → 256)
- `tb_born_dist.v`: n=10, 고정 amp 배열 10⁵ 샘플 → 이론 분포 대비 χ² p > 0.01
- 캐시 on/off가 **같은 seed에서 동일한 `cand` 수열**을 내고 사이클만 다름 / `passes_run` 총합은 on·off에서 동일

마지막 줄이 이 프로젝트의 핵심 주장입니다. `cycle_cnt` 는 줄고 `passes_run` 은 안 줄어야 합니다.

## 6. 스프린트 4 — SoC 통합·구현·평가 (A 주도)

여기서는 병렬도가 떨어집니다. A가 원격 왕복을 쥐고, 나머지는 자기 블록에서 올라온 문제를 받아 고칩니다.

- B: 열거 모드 end-to-end (발표자료 6p 예시 재현)

## 7. 의존 관계와 크리티컬 패스

```
 A ─ Phase0(원격) ──────────► Phase2(SoC 껍데기) ──────► Phase6(AHB) ──► Phase7(구현)
        │ 실패해도 B·C·D는 안 멈춤                            ▲
        └─ 로컬 iverilog 로 tb·CLI 계속                        │
                                                              │
 B ─ predicate 골든 ─► predicate.v ─┐                          │
                                    ├─► 통합1 (P=1) ─► 통합2 ──┤
 C ─ fixed 골든 ─────► lane/fsm ────┘        │                 │
                                             │                 │
 D ─ bbht 골든 ──────► lfsr/rom/cache_ctrl ──┴─────────────────►
```

**크리티컬 패스는 A의 Phase 0이 아니라 통합 지점 1입니다.** 원격이 막혀도 B·C·D는 로컬에서 P=1 코어까지 갈 수 있고, 거기서 막히면 넷이 다 멈춥니다.

리스크와 대응입니다.

| 리스크 | 누가 | 대응 |
|---|:-:|---|
| 원격 빌드 서버 접속·큐 (로컬 폴백 없음) | A | 스프린트 1 첫날에 확인. 막히면 A도 로컬 tb·CLI 쪽으로 돌림 |
| mmio 생성기가 원격 전용 / XML 스키마 미확인 | A | `test1_apb.v` 방식으로 **손수 작성**을 기본안으로 (100줄) |
| C의 골든이 늦어져 B·D가 벡터를 못 받음 | C | 벡터 포맷(계약 8번)만 있으면 각자 가짜 벡터로 tb를 먼저 씀 |
| 난수 규약이 안 정해진 채 진행 | D·C | 계약 5번. 스프린트 0을 넘기지 말 것 |
| DW=18이 성공률을 못 내 19~20으로 올라감 | C | BRAM 예산이 깨지므로 P를 16으로 낮추는 것이 대안. **전원에게 즉시 알릴 것** |
| 각자 tb만 통과하고 붙이면 안 됨 | 전원 | 통합 지점의 합격 기준을 **골든 대조**로 잡은 이유 |

---

## 8. 운영 규칙

**브랜치** — `main` + `feat/<이름>-<주제>`. 통합 지점에서만 `main` 으로 머지하고, 머지 전 `make -C hardware/testbench regress` 통과가 조건입니다.

**빈 모듈 스텁을 스프린트 0에 미리 커밋합니다.** 남의 모듈이 아직 없어서 컴파일이 안 되는 상황을 없앱니다. 각자 자기 모듈의 본문만 채워 나갑니다.

**회귀는 하나로 묶습니다.** `hardware/testbench/Makefile`(A 소유)이 네 사람의 tb를 전부 돌립니다. 자기 tb만 통과하는 것은 통과가 아닙니다.

**계약 변경은 공지 대상입니다.** §2의 여덟 항목 중 하나라도 바꾸려면 전원에게 알리고, 바뀐 뒤에는 통합 지점 tb를 다시 돌립니다.

**주간 동기** — 각자 "닫은 것 / 막힌 것 / 남에게 필요한 것" 세 줄. 세 번째 줄이 없으면 병렬이 아니라 각자 다른 프로젝트를 하는 것입니다.
