이 장에서는 호스트가 `RUN`을 전송한 뒤 결과를 받을 때까지의 전체 처리 순서와 각 단계의
사이클 비용을 설명합니다.

---

## 15.1 `RUN` 처리 순서

| 단계 | 누가 | 무엇을 | 장 |
|:-:|---|---|:-:|
| 1 | 호스트 → 코어 | 술어 · 임계값 · 시드 · 모드를 한 줄로 보냄 | 14 |
| 2 | 코어 | 데이터셋을 시스템 SRAM에 배치하고 CSR에 설정값을 씀 | 13 |
| 3 | 코어 → mmio | `DMA_COMMAND`로 적재 시작 | 7 |
| 4 | loader | AHB SINGLE로 16비트 워드를 순서대로 읽어 데이터 메모리를 채움 | 7 |
| 5 | 코어 → mmio | `COMMAND`로 탐색 시작. 조건이 안 맞으면 거절 | 5 |
| 6 | Main IP | 진폭을 균일 상태로 `S_INIT` | 9 |
| 7 | Main IP | `m` 범위에서 `j`를 뽑음 (J-LFSR, 7스텝 점프) | 8 |
| 8 | Main IP | Grover 반복을 `j` 번: 오라클 → 평균 → 반사 | 9 |
| 9 | Main IP | Born 측정으로 인덱스 하나를 뽑음 | 10 |
| 10 | Main IP | 그 인덱스의 데이터 값을 술어로 고전적으로 재검사 | 10 |
| 11 | Main IP | 맞으면 결과 확정. 틀리면 `m`을 키워 7로 되돌아감 | 8 |
| 12 | Main IP → mmio | 카운터 갱신, `done_sticky` | 13 |
| 13 | 코어 → 호스트 | CSR을 읽어 응답 줄을 만들어 보냄 | 14 |

7~11이 BBHT 한 샷입니다.

확정 설계에서 8번은 매번 처음부터 돌지 않습니다. 체크포인트가 있으면 이미 돌려 둔
상태에서 차이만큼만 이어 돌립니다([11장](11_체크포인트와_정책_엔진.md)).

열거 모드에서는 결과를 하나 찾을 때마다 `found_mask`에 표시하고 `m`을 1로 되돌려 다음
라운드를 시작합니다. 체크포인트는 무효화됩니다.

## 15.2 반복 관련 카운터

| 이름 | CSR | 뜻 | 체크포인트가 줄이나 |
|---|---|---|:-:|
| 논리 반복 `L_BBHT` | `0x030` | 뽑힌 `j`의 합 | 아니오 |
| 물리 반복 `ACTUAL_ITER` | `0x034` | 실제로 돌린 반복 수 | 예 |
| 시도 수 `TRIAL_COUNT` | `0x02C` | 샷 수 | 아니오 |

2026-09-17 보드 세션의 한 워크로드에서 세 카운터의 차이를 확인할 수 있습니다.

| 실행 | `trials` | `l` (논리) | `iters` (물리) | `cyc` |
|---|---:|---:|---:|---:|
| Normal (`BURST=0`) | 21 | 119 | 119 | 41,310 |
| 체크포인트 (첫째) | 21 | 119 | 38 | 20,935 |
| 체크포인트 (둘째) | 21 | 119 | 38 | 17,847 |

논리 축 셋(`trials` · `l`)이 같고 물리 반복만 119 → 38로 줄었습니다. 체크포인트는
탐색 궤적을 바꾸지 않고 계산만 재활용하기 때문입니다. 이것이 회귀의 핵심 불변식이고,
500/500으로 검증되어 있습니다([16장](16_검증_체계.md)).

같은 설정·데이터·시드인데 체크포인트 두 줄의 사이클이 다른 것은 실행 이력 차이입니다
(20,935 − 17,847 = 3,088). 리셋 뒤 첫 탐색만 memo 청소를 치릅니다
([11장 11.5절](11_체크포인트와_정책_엔진.md)).

## 15.3 단계별 사이클 비용

| 자리 | 비용 | 근거 |
|---|---|---|
| 데이터셋 적재 | 워드당 3사이클 × 8,192워드 = 24,576사이클 (약 246 us) | [6장 6.8절](06_데이터_표현과_메모리_맵.md#68-시스템-sram-과-적재) |
| 물리 반복 한 번 (E1) | PASS1 512 + PASS2 512 = 1,024 발행 + 드레인 | [9장](09_연산_경로와_E4.md) |
| 물리 반복 한 번 (E4) | PASS1 128 + PASS2 128 = 256 발행 | [9장 9.4절](09_연산_경로와_E4.md) |
| 측정 BUILD (M0 → M1) | 512 → 256사이클 | [10장 10.3절](10_측정_경로와_M1_M2.md) |
| 측정 SELECT (M1 → M2) | 최악 512 → 48회 비교 | [10장 10.4절](10_측정_경로와_M1_M2.md) |
| 정책 memo 청소 | 3,279사이클 (리셋 뒤 첫 탐색과 epoch 한 바퀴) | [11장 11.5절](11_체크포인트와_정책_엔진.md) |

적재는 탐색에 비하면 작습니다. Q14 전체 적재가 246 us 인데 Normal 탐색 500개가
425,502 us입니다. AHB를 버스트로 올리지 않은 이유가 이것입니다
([7장 7.3절](07_통신_계층.md)).

## 15.4 6단계 분해

같은 500 워크로드를 여섯 구성으로 돌려 RTL 사이클을 쟀습니다
([publication_6stage](../../hardware_bram/results/2026-09-08_publication_6stage/evidence.md)).

| 단계 | 총 사이클 | 직전 대비 | 무엇이 바뀌었나 |
|---|---:|---:|---|
| Normal-E1 | 42,308,335 | — | 기준. 체크포인트 없음 |
| K4/H4-E1 | 18,349,320 | -56.63% | 체크포인트 도입 |
| K4/H4-E4 | 11,246,755 | -38.71% | 연산기 4벌 |
| K3/H3-E4 | 10,385,795 | -7.66% | K·H를 줄임 |
| K3/H3-E4-M1 | 8,500,620 | -18.15% | 측정 BUILD 두 행 |
| K3/H3-E4-M2 | 6,890,470 | -18.94% | 계층적 SELECT |

전체 6.1401x입니다.

결과를 요약하면 다음과 같습니다.

- 체크포인트 도입으로 사이클이 56.63% 감소했습니다. 나머지 다섯 단계의 효과를 합친
  것보다 큰 폭입니다.
- M1과 M2를 함께 적용하면 K3/H3-E4 대비 33.7% 감소합니다. 측정 경로도 512개 행을 두 번
  순회하므로 주요 병목에 해당합니다.
- K·H를 줄이면 사이클이 7.66% 감소하며 자원 사용량도 함께 줄어듭니다
  ([11장 11.6절](11_체크포인트와_정책_엔진.md)).

## 15.5 성능 지표 구분

위 표는 RTL 사이클 축입니다. 보드 실경과 시간 축의 배수는 7.626x로 다릅니다.

| 축 | 값 |
|---|---|
| RTL 사이클 | 6.1401x |
| 보드 실경과 시간 | 7.626x |
| ORCA 1코어 대비 | 116,426x (단서 필요) |

서로 다른 세 지표를 섞어 배수를 계산하지 않습니다. 보드와 RTL은 궤적이 500/500 같지만 사이클
값 자체는 다릅니다: M2의 473/500이 정확히 3,279 사이클 차이입니다. 6단계 캠페인은
워크로드마다 새로 시작해서 memo 청소를 매번 치르고, 보드와 `bench500`은 연달아 돌아 한
번만 치르기 때문입니다.

`bench250`과 `bench500` 하네스는 드라이버를 통해 워크로드를 연속 실행하므로 보드 실행
조건에 더 가깝습니다. 같은 250개 워크로드에서 논리 결과는 250/250, 사이클은 230/250건
일치합니다.

ORCA 배수에 붙일 단서는 [1장 1.5절](01_프로젝트_개요.md)에 있습니다.
