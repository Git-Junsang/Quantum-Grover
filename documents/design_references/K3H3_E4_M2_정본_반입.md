# K3/H3-E4-M2 정본 반입 — 2026-09-09 (모드 이름 정리 2026-09-10)

## 1. 무엇이 바뀌었나

`hardware_bram` 의 정본이 K4/H4 에서 **K3/H3-E4-M2** 로 바뀌었습니다. 출처는
서버에서 받은 재현 패키지 `BBHT_Grover_Reproduction_Package_v1.0_20260909`
한 벌이고, 반입 범위와 출처 대응은
`hardware_bram/results/2026-09-09_repro_package_v1.0/evidence.md` 에 있습니다.

이름 넷을 먼저 풀어 둡니다. 전부 **RTL 빌드에 컴파일되는 값**이고 CSR 로 고르는
것이 아닙니다.

| 기호 | 뜻 | 정본 값 |
|---|---|---:|
| K | 체크포인트를 몇 벌 들고 있는가 | 3 |
| H | 정책이 몇 단계 앞을 내다보는가 | 3 |
| E | 물리 Grover 반복 한 번에 협력하는 P=32 연산기 수 | 4 |
| M | 측정 경로 최적화 단계 | 2 |

## 2. 소스 구조

이 절은 2026-09-09 반입 당시의 기록입니다. 2026-09-13 에 `src_comm/` 과 6단계
ablation 공통소스를 `src/` 한 벌로 합쳐 main 에는 최신판만 두었고, 아래 표의 배치는
태그 `board-k3h3-e4-m2` 에 그대로 남아 있습니다.

`src_v2/`(K4/H4 freeze)와 `src_v3/`(PASS2 융합 포크)를 없애고, 보드에 구워진
소스 한 벌만 `src/` 에 둡니다. 통신 계층은 두 벌이 됐습니다.

| 트리 | 무엇 | 누가 씁니까 |
|---|---|---|
| `src/` | 보드 정본 17개. wrapper·mmio·loader·Main IP 10개·헤더 2개 | freeze. 고치지 않습니다 |
| `src_comm/` | 우리가 쓴 wrapper·mmio·loader + 어댑터 + user region | 고쳐도 됩니다 |

두 wrapper 는 겉으로 같은 19신호를 냅니다. 다른 점은 안쪽입니다.

- 정본 wrapper 는 `bbht_grover_main_ip` 를 **어댑터 없이 직접** 뭅니다
  (`CKPT_K(3) POLICY_H_FUTURE(3) INTRA_ENGINES(4)`, 리셋은 `rstn`).
- 우리 wrapper 는 계약 이름 `bbht_grover_core` 를 물고,
  `src_comm/bbht_grover_core_adapter.v` 가 모듈 이름과 리셋 이름만 바꿔
  같은 Main IP 에 이어 줍니다. 포트 61개는 1:1 이고 폭 변환도 논리도 없습니다.
- 정본 mmio 는 CSR 오프셋을 자기 안에 localparam 으로 적고, 우리 mmio 는
  생성 헤더 `bbht_grover_csr.vh` 를 include 합니다. **두 오프셋 표는 38개가
  전부 일치**합니다 — CSR 계약은 v0.9.8 이후 바뀌지 않았습니다.

### 확인한 것

- `src/` 17개 파일의 sha256 이 패키지 매니페스트, 그리고 비트스트림 빌드가
  남긴 `meta/source_sha256.txt` 와 전부 일치합니다
- 포트 계약이 네 갈래(`stub` `real` `final` `dram`) 전부 wrapper 19 + core 61
  로 통과합니다. `final` 은 이번에 추가한 갈래로, 보드 정본을 인수인계 계약과
  직접 대조합니다 (매크로 폭 ``GP_INDEX_W-1` 같은 것을 `grover_param.vh`
  에서 풀어 비교합니다)
- 통신 계층 두 벌이 같은 테스트벤치에서 T1~T9 · D1~D11 을 똑같이 통과하고,
  D5 단일 탐색 사이클이 **63,963 으로 같습니다**

## 3. 성능 — 세 축을 구분하십시오

같은 500 워크로드(M = 1/4/16/64/256 × 시드 100)를 세 가지 방식으로 쟀습니다.
셋은 **서로 다른 근거축**이라 섞어 배수를 만들면 안 됩니다.

| 축 | Normal | 정본 | 배수 |
|---|---:|---:|---:|
| 보드 실경과 시간 | 425,502 us | 55,798 us | 7.626x |
| RTL 사이클 (6단계 ablation) | 42,308,335 | 6,890,470 | 6.1401x |
| 같은 보드 ORCA 1코어 | 6,496,338,005 us | 55,798 us | 116,426x |

### 왜 섞으면 안 되는가

보드와 RTL 은 **탐색 궤적이 500/500 일치**합니다 — `result_index`,
`trial_count`, `L_BBHT` 가 워크로드마다 같습니다. 그런데 `cycle_count` 는
다릅니다.

| | 보드 합 | RTL 합 | 워크로드별 차이 |
|---|---:|---:|---|
| Normal | 42,300,932 | 42,308,335 | RTL 이 1~31 사이클 더 큼 |
| K3/H3-E4-M2 | 5,328,877 | 6,890,470 | 473/500 이 정확히 3,279 사이클 |

M2 쪽 3,279 는 거의 모든 워크로드에 똑같이 붙는 고정 항이고 첫 워크로드에서만
0 입니다. 보드는 연속 실행이라 이 비용을 한 번만 내고 RTL 은 매 실행 내는
것으로 보이지만 **원인을 확인하지는 않았습니다.** 보드에서는 실경과 시간을,
RTL 에서는 사이클을 인용하십시오.

ORCA 비교는 십만 배가 넘는데, 이는 N = 16,384 상태벡터를 32비트 코어 하나로
반복마다 훑는 것과 P = 32 레인으로 훑는 것의 차이이고 클럭도 절반입니다.
알고리즘 우위가 아니라는 단서를 항상 붙이십시오.

**첫째, 체크포인트를 줄였는데 빨라졌습니다.** K4/H4 → K3/H3 에서 슬롯이 하나

결정 비용입니다.** 2026-09-04 묶음이 K4/H8 대 K4/H4 에서 본 것과 같은 방향입니다.

**둘째, 이득의 절반이 측정 경로에 있었습니다.** M1 과 M2 를 합치면 K3/H3-E4
대비 -33.7% 입니다. 측정은 오라클·확산과 달리 눈에 잘 안 띄는 자리인데,
512행을 두 번 훑는 구조라 실제로는 반복만큼 비쌌습니다.

## 5. 우리가 시도했던 것과의 관계

2026-09-06 에 우리도 같은 두 병목을 공격했습니다. 결과는 다른 답이었습니다.

- **연산기 병렬화** — 우리 F2 는 논리 요청 열을 두 트랙으로 갈랐고, 분할 비용
  +50% 와 슬롯 소유권 문제로 탈락했습니다. 정본 E4 는 요청 열을 건드리지 않고
  물리 반복 **안에서** 512행을 4행씩 나눕니다. 그래서 반복 수가 그대로입니다.
- **측정 경로** — 우리 PASS2 융합은 512행 재스캔을 없앴고(-9.99%), 정본 M1·M2
  는 재스캔을 남긴 채 싸게 만듭니다. 기준선이 달라 직접 비교는 안 됩니다.
- **K3 정책** — 우리가 "K3 은 policy 를 다시 유도해야 한다" 며 막혔던 자리를
  정본이 풀었습니다. `STATE_RANKS = 1093` 보폭을 그대로 두어 K4/H4 를 비트
  동일하게 유지하면서 K3 은 좁은 구간만 방문합니다.

자세한 대조는 [PASS2_융합과_다중엔진_탐색_실측.md](PASS2_융합과_다중엔진_탐색_실측.md)
6절에 있습니다.

  빌드가 바뀔 때마다 이름이 틀려집니다 — 실제로 K4/H8 에서 K4/H4 를 거쳐
