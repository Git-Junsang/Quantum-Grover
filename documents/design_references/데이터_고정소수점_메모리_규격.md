# LPSoC BBHT/Grover 데이터·고정소수점·P32 메모리 매핑 규격

## 1. 적용 범위 및 핵심 규격

보드에서 검증된 정본 RTL(`hardware_bram/src/` 의 Main IP)과 bit-exact 소프트웨어 기준모델(`software/models/rtl_reference_model/`)이 공통으로 사용하는 확정 프로파일이다. 아래 값은 `grover_param.vh` 에서 직접 뽑았다.

| 항목 | 값 |
| --- | ---: |
| 상태 수 | 16,384 |
| 병렬도 | P32 |
| row 수 | 512 |
| 입력 | signed16 |
| 저장 진폭 | signed 23-bit, raw/`2^22` |
| 초기 진폭 raw | 32,768 |
| 평균 반올림 | nearest, ties-to-even |
| 진폭 범위 | `[-4194303, 4194303]` |
| 측정 | 정수 제곱 + LFSR rejection + row/lane CDF |

## 2. 폐기된 프로파일

아래 둘은 **폐기됐다.** 옛 문서나 `trash_bin/` 에서 마주치면 무시한다.

| 출처 | 프로파일 | 폐기 이유 |
| --- | --- | --- |
| GitHub `7b96551` | Q15/P32/Q2.16, runtime qubits | 전달 RTL 세대가 다르다. 진폭 상수를 섞으면 bit-exact 판정이 깨진다 |
| 골든 모델 Q16 | Q16/P32/F22 | Q14 로 freeze 했다. RTL·합성·포트 폭 어느 것도 만들지 않았다 |

Q16 사례는 열거 벡터의 `q16_eq_m2` 한 케이스(`software/rtl_vectors/enumeration/`)에 기록으로만 남아 있다. 확장 후보로 인용하지 않는다.

## 3. 입력 데이터 표현

입력은 signed16 2의 보수다.

| 실제 값 | 16-bit HEX |
| ---: | --- |
| 0 | `0000` |
| 1 | `0001` |
| 32767 | `7FFF` |
| -1 | `FFFF` |
| -32768 | `8000` |

골든벡터 파일은 global index 순서로 한 줄에 4자리 HEX 하나를 사용한다.

```text
0003
FFF8
0000
7FFF
```

`index >= data_count`는 메모리에 어떤 값이 남아 있어도 Oracle과 candidate verification에서 항상 비타겟이다.

## 4. P32 bank/row 매핑

전역 index `i`의 매핑:

$$
\operatorname{bank}=i\bmod 32,
\qquad
\operatorname{row}=\left\lfloor\frac{i}{32}\right\rfloor
$$

Q14 RTL bit slice:

```text
bank = index[4:0]
row  = index[13:5]
```

| Index | Bank | Row |
| ---: | ---: | ---: |
| 0 | 0 | 0 |
| 31 | 31 | 0 |
| 32 | 0 | 1 |
| 63 | 31 | 1 |
| 16383 | 31 | 511 |

한 row에서 lane과 bank는 1:1이다.

```text
lane b = row_bus[b*WIDTH +: WIDTH]
```

lane 0은 packed row bus의 최하위 bit slice다.

## 5. 논리 메모리 구조

| 메모리 | 논리 구성 | raw 용량 | 용도 |
| --- | --- | ---: | --- |
| `data_mem` | 32 banks x 512 x 16-bit | 32 KiB | Oracle 입력과 candidate 재검증 |
| 진폭 · checkpoint 메모리 | 상태 한 벌 = 512 row x 32 lane x 23-bit, 물리 슬롯 4벌 | 46 KiB x 4 | 계산 중인 상태벡터와 되돌아갈 진폭 상태. `CKPT_K` = 3 은 슬롯 3개를 쓴다 |
| row-weight memory | 512 x 51-bit | 약 3.2 KiB | Born row CDF |

E4 구성에는 따로 떨어진 작업용 `amp_mem` 이 없다. 계산은 슬롯 안에서 제자리로(in-place) 하거나, 한 반복만 다른 슬롯으로 건너 쓰는(bridge) 방식이다 (`grover_checkpoint.v` 의 executor · segment router 주석).

이 수치는 논리 bit 수다. 실제 개수는 커밋된 구현 리포트(`route_util_hier.rpt`)로 확인한다. 풀 SoC 가 BRAM 116 tile 이고 그중 Main IP 가 84 tile(RAMB36 52 + RAMB18 64)이다. 진폭 상태 한 벌은 10 x (512 x 69-bit) + 1 x (512 x 46-bit) 로 packing 되어 RAMB36 11개이고, E4 는 행 위상 뱅크 4개(각 512 x 736-bit)에 물리 슬롯 4벌을 담아 44개를 쓴다. 나머지 RAMB36 은 policy memo 4, found mask 2, row-weight 2 이고 `data_mem` 이 RAMB18 64개다. 물리 슬롯 수가 K 와 무관하게 4라서 K4 → K3 에서 BRAM 이 줄지 않는다(자원 ablation 83.0 → 83.0 tile).

측정은 `amp_mem` 을 read-only 로 쓰므로 측정 직전 상태가 그대로 남는다. 슬롯은 그 상태를 되돌아갈 지점으로 복사해 두는 것이고, 관리 규칙은 [Main_IP_포트_규격.md](Main_IP_포트_규격.md) 8절에 있다.

## 6. 진폭 raw 형식

저장 진폭은 다음 관계를 사용한다.

$$
A_{\mathrm{real}}=\frac{A_{\mathrm{raw}}}{2^{22}}
$$

이 문서에서 Q1.22-like라는 이름보다 **signed 23-bit, fractional bits 22**라는 정의를 우선한다. Q 표기 관례가 달라도 raw 해석은 변하지 않는다.

| 값 | Raw | 23-bit code를 6자리 HEX로 표시 |
| ---: | ---: | --- |
| Q14 초기 진폭 `1/128` | 32768 | `008000` |
| `1/64` | 65536 | `010000` |
| legal 최대 | 4194303 | `3FFFFF` |
| legal 최소 | -4194303 | `400001` |
| 제외한 2의 보수 최솟값 | -4194304 | `400000` |

대칭 saturation을 위해 `-4194304`는 legal amplitude로 사용하지 않는다.

Q14 초기값은 정확히 표현된다.

$$
\frac{1}{\sqrt{16384}}=\frac{1}{128},
\qquad
A^{(0)}_{\mathrm{raw}}=2^{22}/128=32768
$$

## 8. 한 번의 Grover iteration

```text
PASS1
  amp_mem + data_mem row read
  -> padding gate + signed predicate
  -> target amplitude sign flip
  -> Oracle 결과를 amp_mem에 write
  -> 32-lane sum과 global accumulation

MEAN
  global_sum -> rounded two_mean

PASS2
  Oracle amplitude row read
  -> two_mean - oracle_amp
  -> symmetric saturation
  -> next amplitude를 amp_mem에 write
```

### Oracle

$$
A_i^{\mathrm{oracle}}=
\begin{cases}
-A_i,& i<\mathrm{DATA\_COUNT}\ \text{and predicate is true}\\
A_i,& \text{otherwise}
\end{cases}
$$

### 평균

RTL은 mean을 반올림한 뒤 두 배하지 않는다. 전체 합에서 `2*mean`을 한 번만 ties-to-even 반올림한다.

$$
\mathrm{two\_mean}
=\operatorname{roundEven}
\left(\frac{\sum_i A_i^{\mathrm{oracle}}}{2^{Q-1}}\right)
$$

Q14에서는 signed global sum을 13비트 오른쪽 shift하고 nearest-even을 적용한다.

### Diffusion과 saturation

$$
D_i=\mathrm{two\_mean}-A_i^{\mathrm{oracle}}
$$

$$
A_i^{\mathrm{next}}
=\operatorname{clip}(D_i,-4194303,4194303)
$$

한 번이라도 saturation이 발생하면 `amp_overflow`가 다음 accepted search start까지 유지된다.

## 9. 파이프라인과 메모리 접근

### INIT/PASS2

```text
t   : row issue
t+1 : BRAM response/datapath
t+2 : amp_mem write
```

### PASS1

```text
t   : amp/data row issue
t+1 : BRAM response, predicate metadata register
t+2 : padding + Oracle, amplitude row register
t+3 : amp_mem write, adder tree 전반
t+4 : adder tree 후반, global accumulator
```

PASS1 뒤에는 최종 partial sum을 받기 위한 drain state가 있다. 전달 JSON의 `cycle_count`는 이 구체적 pipeline을 포함한 회귀 관측값이며, 향후 pipeline 변경에도 고정되는 외부 포트 계약은 아니다.

## 10. Born 측정과 candidate 검증

진폭을 float 확률로 바꾸지 않고 raw 정수를 직접 제곱한다.

$$
w_i=A_{\mathrm{raw},i}^2,
\qquad
W=\sum_i w_i
$$

```text
1. 512개 amplitude row를 읽어 32개 square와 row weight 계산
2. 모든 row weight를 합해 W 계산
3. LFSR_MEAS 두 draw를 {high, low} 64-bit 난수로 결합
4. rejection sampling으로 0 <= r < W 생성
5. 첫 cumulative row weight > r인 row 선택
6. 선택 row를 다시 읽고 첫 lane cumulative > local_r 선택
7. candidate = {row, lane}
8. data_mem Port-B로 candidate 값을 다시 읽음
9. Oracle과 동일한 padding+predicate로 성공 여부 검증
```

1~2단계의 512행 재스캔이 측정 경로의 병목이다. 정본은 이 재스캔을 남겨 두고 두 단계로 싸게 만든다 — M1 이 체크포인트 4행 quad 를 받아 한 사이클에 두 행씩 제곱하고, M2 가 512행 선형 탐색 대신 16×32 계층으로 행을 고른다. 우리가 2026-09-06 에 시도했던 PASS2 융합은 재스캔 자체를 없애는 다른 접근이었고, 그 기록은 [PASS2_융합과_다중엔진_탐색_실측.md](PASS2_융합과_다중엔진_탐색_실측.md) 6.2절에 있다. 어느 쪽이든 반복·policy·탐색 궤적은 바뀌지 않는다
([PASS2_융합과_다중엔진_탐색_실측.md](PASS2_융합과_다중엔진_탐색_실측.md)).

동일 seed에서 RTL과 같은 index를 얻으려면 다음이 모두 같아야 한다.

- LFSR polynomial과 fallback seed
- draw 시점과 소비 개수
- 64-bit 결합 순서
- rejection rule
- strict `cumulative > threshold`
- row 우선, lane 후 순서

## 11. BBHT와 cache 값의 의미

| 값 | 의미 |
| --- | --- |
| `j_req` | 현재 attempt가 요구한 절대 Grover 반복 위치 |
| `L_BBHT` | 모든 attempt의 `j_req` 누적합; 논리 비용 |
| `actual_grover_iterations` | cache 적용 후 실제 실행한 iteration 합 |
| `cache_j` | 현재 `amp_mem`이 나타내는 절대 반복 위치 |

Normal은 항상 INIT부터 `j_req`회 실행한다. Burst는 cache가 유효하고 `j_req>=cache_j`일 때 차이만 실행한다. 측정은 read-only이므로 측정 전 상태가 유지된다.

실패했던 `j`를 선택 후보에서 제거하지 않는다. 같은 `j`가 다시 선택되면 같은 진폭 상태에서 **새 measurement 난수**로 독립적으로 다시 측정한다.

## 12. SoC SRAM packing과 loader

`bbht_ahb_loader` 의 packing:

```text
word[15:0]  = data[2*k]
word[31:16] = data[2*k+1]
```

현행 loader 는 32비트 **SINGLE** 읽기를 single outstanding 으로 돌린다. 워드당 3사이클(주소 1 + 데이터 1 + 쓰기 1)이고, Q14 전체 16,384항목 = 8,192워드면 24,576사이클, 100 MHz 에서 약 246 µs 다. 옛 GitHub 세대의 `HSIZE=16-bit` · `INCR16` 버스트 경로는 폐기됐다.

`DATA_COUNT`가 홀수이면 마지막 upper halfword 처리 정책을 loader 가 명시해야 한다.

- 권장: 마지막 padding halfword를 `data_wr_en`으로 전달하지 않음
- 허용: 전달하되 `addr>=data_count`이므로 Main IP loader가 무시

Main IP loader는 주소 중복을 검출하지 않으므로 adapter는 `0..data_count-1`을 정확히 한 번씩 생성해야 한다.

## 13. 정답 벡터와 TB 비교 순서

현재 기준 벡터:

```text
software/rtl_vectors/requested_j_bit_exact/requested_j_bit_exact_256_cases.zip
```

256케이스(방향성 28 · 앵커 1 · 무작위 227)이고 케이스마다 폴더 하나다.

| 파일 | 비교 대상 |
| --- | --- |
| `config.json` | 술어·임계값·`DATA_COUNT`·`j_target` 과 프로파일 |
| `data_signed16.hex` · `data_ahb_words.hex` · `data_memory_image.hex` | signed16 loader 입력의 세 표현 |
| `target_mask_p32.hex` | Oracle target mask |
| `initial_amp.hex` | 초기 23-bit amplitude |
| `iter_###_after_oracle.hex` | PASS1 이후 23-bit amplitude (FULL trace 56케이스) |
| `iter_###_row_partial_sum.hex` | row partial sum |
| `iter_###_after_diffusion.hex` | PASS2 이후 amplitude |
| `expected_final_amp.hex` | 최종 amplitude |
| `expected_core.json` | target 인덱스·물리 반복·포화 횟수·최종 진폭 해시 |

범위는 수동 j 코어의 bit-exact 다. 자동 BBHT 의 J·측정 난수, policy 텔레메트리, `cycle_count` 는 이 벡터가 주장하지 않는다(`excluded_from_claim`). 그쪽은 Common500 비교가 맡는다([소프트웨어_기준모델과_Common500.md](소프트웨어_기준모델과_Common500.md)).

권장 비교 순서:

```text
loader data
-> initial amplitude
-> after Oracle
-> partial/global sum
-> two_mean
-> after Diffusion
-> Born total weight/threshold
-> selected row/lane/index
-> verification
-> L_BBHT/physical iteration/cycle count
```

최종 index만 맞는 것으로 bit-exact PASS를 선언하지 않는다. 첫 불일치 단계에서 loader, predicate, rounding, saturation, LFSR 또는 CDF 문제를 구분한다.
