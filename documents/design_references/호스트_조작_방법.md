# 호스트 PC에서 BBHT/Grover 가속기를 조작하는 방법

> 담당: 통신·명령·시스템 (SJS) · 2026-09-02 작성 · 2026-09-13 갱신
> Main IP는 PJK 소유이고 구성은 K3/H3-E4-M2 입니다. 이 문서는 그 IP를
> **바깥에서 어떻게 부리는가**만 다룹니다.
> 통신 계층과 펌웨어는 `hardware_bram/` 에 있습니다. 호스트 쪽은 시리얼 터미널이면 됩니다
> (호스트 CLI `software/bbht_cli.py` 는 2026-09-13 저장소에서 빠졌습니다).

---

## 0. 먼저 알아야 할 것 — 조작 경로가 둘입니다

| | 방식 A — 기존 proof app | 방식 B — 콘솔 앱 |
|---|---|---|
| 설정이 있는 곳 | C 코드 안 (`#define`) | UART 명령 |
| 조건을 바꾸려면 | 앱 재빌드 → 재다운로드 | 명령 한 줄 |
| 만든 사람 | PJK | SJS (이 문서) |
| 검증 상태 | **실보드 5/5 PASS + 50seed 벤치 250/250** | 시뮬·빌드까지 확인, **보드 미검증** |
| 쓰는 자리 | 회귀 게이트, 논문용 증거 | 실험, 브링업, 조건 스윕 |

**방식 A를 지우지 마십시오.** PJK가 보드에서 통과시킨 다섯 시나리오(APB /
DMA / Single / Enumeration / K4H8)가 회귀의 기준선이고, 통신 계층을 고칠
때마다 그 다섯을 다시 통과해야 baseline 교체를 논의할 수 있습니다
(인수인계 §4.2 마지막 줄). 여기서 `K4H8`은 그 시절 **proof app 의 이름**이고,
가리키는 것은 체크포인트 경로입니다. CSR 실행 모드 쪽 이름은 지금
`CKPT_SINGLE` · `CKPT_ENUM` 이며, 실제 K·H 는 RTL 빌드 상수라 현재 정본은
K3/H3 입니다 (8절).

방식 B는 그 위에 얹는 것입니다. 비트스트림도 Main IP도 건드리지 않고
**앱만 바꿔 끼웁니다.** PJK가 2026-09-01 벤치마크를 돌린 방법과 같습니다.

## 1. 준비 — 한 번만 하면 되는 것

### 1.1 툴체인

```bash
source /opt/rvx/rvx_setup.sh
```

RVX는 `/opt/rvx`에 전체 설치되어 있고 원격 서버가 필요 없습니다. Vivado
2026.1은 그냥 `vivado`로 부르면 되고, 라이선스와 `xc7a100tcsg324-1` 부품이
모두 잡혀 있습니다. 화면이 없으므로 `-mode batch` 전용입니다.

### 1.2 플랫폼 설치

저장소의 통신 계층과 Main IP를 RVX 플랫폼에 넣습니다.

```bash
cd hardware_bram/rvx
./install_to_platform.sh                 # $RVX_MINI_HOME/platform/bbht_grover_upgrade
```

무엇이 어디로 가는지는 스크립트 안에 다 적혀 있습니다. 요약하면

| 저장소 | 플랫폼 |
|---|---|
| `hardware_bram/rvx/bbht_grover_upgrade.xml` | `<플랫폼이름>.xml` (`<name>` 을 폴더 이름에 맞춰 넣습니다) |
| `hardware_bram/src/` Main IP 10개 + `grover_param.vh` | `user/rtl/src/` · `include/` |
| `hardware_bram/src/` 통신 계층 3개 + 어댑터 | `user/rtl/src/` |
| `hardware_bram/src/bbht_grover_user_region.vh` | `user/rtl/include/<플랫폼이름>_user_region.vh` |
| `software/csr/generated/bbht_grover_csr.vh` **(지금 없음)** | `user/rtl/include/` |
| `hardware_bram/firmware/bbht_grover_driver.{c,h}` | `user/api/` |
| `software/csr/generated/bbht_grover_regs.h` **(지금 없음)** | `user/api/` |
| `hardware_bram/firmware/bbht_console/` · `bbht_paper_bench/` · `orca_sw_baseline/` | `app/` |
| (스크립트가 만듦) | `user/env/set_rtl_syn_env.tcl` — `user/rtl` 을 합성 경로에 등록 |

**생성 헤더 둘이 지금 저장소에 없습니다.** 2026-09-13 `software/` 재편 때 CSR 생성기와
함께 빠져서, 스크립트가 `gen_csr.py` 를 부르는 줄에서 멈춥니다. 설치하려면 커밋
`7d5455c` 의 `software/csr/` 를 먼저 되살리십시오 (`CLAUDE.md` 5절 끝).

**`hardware_bram/src/` 는 최신판 한 벌입니다** — 우리 통신 계층이 어댑터를 거쳐
계약 이름 `bbht_grover_core` 로 Main IP 를 뭅니다. 스크립트가 합성 대상만 골라
옮깁니다(`grover_policy_ooc_top.v` · `grover_policy_impl_wrapper.v` 는 OOC 전용이고,
`bbht_bram_top.v` 는 wrapper 와 같은 자리에 들어가는 다른 최상단이라 빠집니다).

2026-09-07 비트스트림에 들어간 판은 태그 `board-k3h3-e4-m2` 에 있습니다. 그 판은
PJK 통신 계층이 Main IP 를 어댑터 없이 직접 물었고, user region 이 가속기 클럭을
`clk_accel` 로 물었습니다. 지금 판은 `gclk_accel` 입니다. **다시 굽기 전에 이 차이를
먼저 확인하십시오.**

Main IP 없이 통신 계층만 돌려 볼 때는 `hardware_bram/testbench/bbht_grover_core_stub.v`
가 자리를 채웁니다. 그것은 선형 스캔이지 그로버가 아니므로 **탐색 결과를
인용하면 안 됩니다.**

### 1.3 플랫폼 생성

```bash
cd $RVX_MINI_HOME/platform/bbht_grover_upgrade
make syn
```

여기서 나오는 것 중 **반드시 확인할 값**입니다.

```bash
grep -E "I_GROVER_CSR_SLAVE_BASEADDR|I_SYSTEM_SRAM" arch/ssw/src/memorymap_info.h
grep SYSTEM_CLK_HZ arch/ssw/src/hw_info.h
```

이 환경에서 실측한 값입니다 (2026-09-02).

| 무엇 | 값 |
|---|---|
| `I_GROVER_CSR_SLAVE_BASEADDR` | `0xE2020000` (size `0x1000`) |
| `I_SYSTEM_SRAM` | `0xE0000000` ~ `0xE001FFFF` (128 KiB) |
| `SYSTEM_CLK_HZ` | **50 MHz** — SoC 쪽 |
| `clk_accel` | **100 MHz** — 가속기 도메인, PLL0에서 나옴 |

**클럭이 둘이라는 점이 자주 헷갈립니다.** RISC-V 코어와 UART는 50 MHz에서
돌고, 가속기와 CSR·loader는 100 MHz에서 돕니다. `CYCLE_COUNT`는 후자 기준이라
**시간 = 사이클 / 100 µs** 입니다. 50으로 나누면 두 배 틀립니다.

C 코드에서 base address를 숫자로 박지 마십시오. `bbht_grover_regs.h`가
`I_GROVER_CSR_SLAVE_BASEADDR`를 쓰도록 되어 있고, 플랫폼 XML이 바뀌면
주소가 옮겨갑니다.

## 2. 보드 없이 — 시뮬레이션으로 먼저

보드는 실측 때만 붙입니다. 평소 작업 자리는 여기입니다.

### 2.1 통신 계층만 (가장 빠름, 몇 초)

```bash
cd hardware_bram/sim
make ports       # 포트 계약 대조 (wrapper 19 + core 61)
make lint        # verilator lint
make regress     # RTL 회귀 (T1~T9)
make driver      # 드라이버 + RTL 공동 시뮬 (D1~D11)
```

> 2026-09-13 부터 이 네 타깃은 빠진 파일(CSR 생성 헤더 · 포트 계약표) 때문에 멈춥니다.
> 되살리는 법은 `CLAUDE.md` 5절 끝에 있습니다. 아래는 파일이 있을 때의 설명입니다.

`make regress`가 보는 것: CSR 라운드트립 · W1P 펄스 · `rpslverr` · DMA 정상/거절 ·
Single 결과 · `done_sticky` 클리어 규칙 · 열거 FIFO read-to-pop.

`make driver`가 보는 것: **실제 펌웨어가 쓸 `bbht_grover_driver.c`를 그대로
컴파일해 RTL에 붙입니다.** 오프셋 하나가 어긋나거나 폴링 순서가 틀리면
여기서 잡힙니다.

두 회귀 모두 Main IP 자리에 스텁이 들어갑니다. 통과했다는 것은 **통신 계층이
계약을 지킨다**는 뜻이지 **탐색이 맞다**는 뜻이 아닙니다. 탐색까지 보려면
실물 코어를 물린 `make -C hardware_bram/sim bench250` 쪽입니다 — 보드 실측과
같은 250쌍 workload 를 돌립니다.

`make ports` 는 `software/contract/port_contract.tsv`(인수인계 docx 에서 뽑은
계약)와 RTL 을 대조합니다 — 그 tsv 가 지금 빠져 있습니다. 스텁을 물린 상태가
`ports`, 실물 코어를 물린 상태가 `ports-real` 입니다. 네 검사를 실물로 한 번에
돌리려면 `make real` 입니다.

> 빌드 디렉터리가 `/tmp`로 나가는 이유가 있습니다. 저장소 경로에 공백
> (`중앙대학교 학부인턴`)이 있는데 GNU Make가 공백 있는 디렉터리에서
> verilator 생성 makefile을 돌리지 못합니다. `--Mdir`로 피해 갑니다.

### 2.2 SoC 전체 RTL 시뮬 (Questa, 수십 초~수 분)

```bash
cd $RVX_MINI_HOME/platform/bbht_grover_upgrade
make sim_rtl
cd sim_rtl
make bbht_console.sim
```

RISC-V 코어가 앱을 돌리고 APB·AHB를 통해 IP를 두드리는 전체 경로를 봅니다.
PJK가 5개 proof app을 통과시킨 것이 이 경로입니다.

**주의: `bbht_console`은 UART 입력을 기다립니다.** RTL 시뮬에는 사람이 없어서
`read_line`에서 멈춥니다. 시뮬로 확인할 때는 PJK의 proof app
(`bbht_apb` / `bbht_dma` / `bbht_single` / `bbht_enum` / `bbht_k4h8`)을 쓰거나,
콘솔 앱을 명령이 박힌 형태로 잠깐 고쳐 쓰십시오.

### 2.3 보드 없이 명령 문법을 연습하려면

호스트 CLI `software/bbht_cli.py` 의 `--port mock` 이 이 역할(콘솔 앱의 문법과 응답
모양을 흉내 내는 파이썬 모델)을 했는데, CLI 가 2026-09-13 저장소에서 빠졌습니다.
지금은 2.2절처럼 콘솔 앱에 명령을 박아 넣어 SoC RTL 시뮬로 돌리는 방법뿐입니다.
mock 이 내던 숫자는 원래 지어낸 값이라 인용하면 안 되는 것이었습니다.

## 3. 보드에 올리기

### 3.1 비트스트림 만들기

```bash
cd $RVX_MINI_HOME/platform/bbht_grover_upgrade
make arty-100t
cd imp_arty-100t_<날짜>
make imp
```

나오는 것: `imp_result/bbht_grover_fpga.arty-100t.bit`

참고 기준은 저장소에 커밋된 K3/H3-E4-M2 구현 리포트입니다
(`hardware_bram/vivado/vivado_bbht_grover_fpga/reports/`, 풀 SoC, 2026-09-07 빌드).

| 자원 | 사용 | 전체 | 비율 |
|---|--:|--:|--:|
| Slice LUT | 45,284 | 63,400 | 71.4% |
| Slice Register | 45,223 | 126,800 | 35.7% |
| Block RAM Tile | 116 | 135 | 85.9% |
| DSP | 132 | 240 | 55.0% |

그중 Main IP(`u_main_ip`)가 LUT 32,242 / FF 28,223 / BRAM 84 tile / DSP 128 입니다.
타이밍은 100 MHz에서 CLOSED입니다 (WNS +0.126 ns, 실패 endpoint 0). 통신 계층을 고친
뒤에는 이 리포트를 다시 뽑아 비교하십시오 — 특히 `route_timing_summary.rpt`의 WNS.

### 3.2 보드 연결

Arty A7-100T의 마이크로 USB 하나가 JTAG과 UART를 겸합니다(FT2232). 꽂으면
호스트에 시리얼 포트가 **둘** 잡힙니다.

```bash
ls -l /dev/serial/by-id/          # 안정적인 이름
dmesg | tail -20                  # 방금 잡힌 ttyUSB 번호
```

보통 `/dev/ttyUSB0`이 JTAG 채널, `/dev/ttyUSB1`이 UART 채널입니다.
**둘 중 뒤 번호가 UART입니다.** 앞 번호에 터미널을 붙이면 아무것도 안 나옵니다.

권한이 없으면:

```bash
sudo usermod -aG dialout $USER    # 로그아웃 후 다시 로그인
```

### 3.3 UART 설정

| 항목 | 값 |
|---|---|
| 보율 | **115200** |
| 데이터 | 8 |
| 패리티 | 없음 |
| 정지 | 1 |
| 흐름 제어 | **없음** |

보율은 RVX의 `ervp_uart.c` 기본값(`UART_BAUD_RATE 115200`)이고 `UART_CLK_HZ`
50 MHz에서 분주됩니다. `SYSTEM_CLK_HZ`를 바꾸면 보율 분주비가 같이 바뀌므로
클럭을 건드린 뒤에는 반드시 다시 확인하십시오 — 안 맞으면 깨진 글자만 나옵니다.

**UART RX가 물려 있는가**는 이 프로젝트의 오래된 미결 항목이었는데,
확인됐습니다. `imp_class_info/arty-100t/pinmap/uart_printf.xdc`가
`printf_rx`를 **A9** 핀(`uart_txd_in`)에 배정하고, RVX SSW에
`uart_check_rx_data_ready()` / `uart_read_rx_buffer()` API가 있습니다.
즉 표준 핀맵 그대로 **양방향입니다.**

### 3.4 비트스트림 다운로드

```bash
cd imp_arty-100t_<날짜>
make download        # 또는 vivado -mode batch -source download.tcl
```

화면이 없으므로 Vivado GUI는 못 씁니다. `-mode batch` 전용입니다.

## 4. 방식 A — 기존 proof app 돌리기

설정이 C에 박혀 있으므로 **조건을 바꾸려면 앱을 고쳐 다시 빌드**합니다.

```bash
cd $RVX_MINI_HOME/platform/bbht_grover_upgrade/imp_arty-100t_<날짜>

```

터미널에 이런 것이 나옵니다 (PJK의 2026-08-31 로그).

```
BBHT SINGLE SEARCH E2E TEST START
dataset addr = 0xe000597c
DMA_STATUS = 0x00000080
DMA LOAD PASS
SEARCH CONFIGURED
SEARCH START issued
STATUS = 0x0000080c
RESULT_INDEX = 120
TRIAL_COUNT  = 1
L_BBHT       = 1
ACTUAL_ITER  = 1
CYCLE_COUNT  = 2126
```

`STATUS = 0x0000080c` 읽는 법: bit2 `done_sticky`, bit3 `result_valid`,


## 5. 방식 B — 콘솔 앱으로 호스트에서 직접 몰기

### 5.1 앱 올리기

```bash
cd $RVX_MINI_HOME/platform/bbht_grover_upgrade/imp_arty-100t_<날짜>
make bbht_console.run
```

비트스트림은 그대로 두고 앱만 바뀝니다.

### 5.2 손으로 쳐 보기

터미널을 붙이면 (`screen /dev/ttyUSB1 115200` 또는 `minicom -D /dev/ttyUSB1 -b 115200`)

```
# bbht_console -- HELP 를 치면 명령 목록이 나옵니다
OK
```

한 번 돌려 보는 순서입니다.

```
ID
GEN COUNT=16384 TARGETS=1 VAL=12345
LOAD
SET MODE=EQ A=12345 AUTO=1 BURST=0 SEEDJ=0x7b1dcdaf SEEDM=0x24370df2
RUN
SET BURST=1
RUN
STAT
```

`GEN`은 보드 위에서 데이터셋을 만듭니다. 시드가 같으면 배열이 같으므로
재현성이 있고, 32 KB를 UART로 밀어 넣지 않아도 됩니다(115200 8N1로 보내면
약 3초 — 탐색 자체보다 훨씬 깁니다).

`BURST=1` 로 돈 두 번째 `RUN` 의 응답 예입니다. 수치는 같은 조건으로 2026-09-08 보드
벤치 앱이 낸 K3/H3-E4-M2 실측값(M = 1 첫 워크로드)을 옮긴 것이고, 콘솔 앱 자체의 보드
출력은 아직 없습니다. 첫 번째 `RUN`(Normal)은 같은 `idx` · `trials` · `l` 에
`iters=308 cyc=351394` 입니다.

```
HIT idx=507 val=12345 trials=25 l=308 iters=70 cyc=30913 us=309
OK
```

읽는 법입니다.

| 필드 | 뜻 |
|---|---|
| `idx` | 찾은 인덱스 |
| `val` | 그 자리의 데이터 값 (보드가 자기 버퍼에서 읽어 붙여 줍니다) |
| `trials` | logical trial 수 |
| `l` | `L_BBHT` = Σ requested j. **알고리즘 지표** |
| `iters` | `ACTUAL_ITER` = 물리 그로버 반복. **checkpoint가 줄이는 대상** |
| `cyc` | `CYCLE_COUNT`, clk_accel(100 MHz) 기준 |
| `us` | `cyc / 100` |

**`l`과 `iters`를 섞지 마십시오.** checkpoint는 `iters`를 줄이고 `l`은
그대로 둡니다. 둘을 합쳐 "그로버 반복을 71% 줄였다"고 쓰면 거짓말이 됩니다 —
줄어든 것은 에뮬레이션 시간이지 알고리즘이 오라클에 던진 질의 횟수가 아닙니다.
짝맞춤 검증도 이 성질 위에 서 있습니다: 같은 시드에서 Normal과 checkpoint 모드가
**같은 `idx`와 같은 `l`**을 내고 `iters`만 달라야 정상입니다.

### 5.3 여러 명령을 한 번에

호스트 CLI(`software/bbht_cli.py`)가 스크립트 파일 실행 · 로그 · 짝 비교 벤치를
맡았는데, 2026-09-13 저장소에서 빠졌습니다 (커밋 `7d5455c` 에 있음). 지금 방법은
둘입니다.

- **스크립트를 직접 짭니다.** [UART_명령_프로토콜.md](UART_명령_프로토콜.md) 규약대로
  한 줄 보내고 `OK`/`ERR` 을 받을 때까지 기다리는 루프면 됩니다. 파이썬이라면
  `software/requirements.txt` 에 있는 `pyserial` 을 씁니다.
- **짝 비교 벤치는 방식 A 의 `bbht_paper_bench` 로 돌립니다.** 보드 실측 500런을
  낸 앱입니다.

짝 비교에서 두 모드의 결과가 하나라도 다르면 **결과를 쓰지 마십시오.** 같은
시드에서 두 모드가 다른 답을 냈다는 뜻이고, 그건 checkpoint 구현이나 통신 계층이
의미를 바꿨다는 신호입니다.

## 6. 잘 안 될 때

| 증상 | 먼저 볼 것 |
|---|---|
| 터미널에 아무것도 안 나옴 | 포트를 잘못 골랐습니다. `/dev/ttyUSB1`(뒤 번호) 쪽입니다 |
| 깨진 글자만 나옴 | 보율 불일치. `SYSTEM_CLK_HZ`를 바꿨는지 확인하십시오 |
| `# 경고: CSR 응답이 이상합니다` | 비트스트림이 안 올라갔거나 base address가 다릅니다. `make syn` 후 `memorymap_info.h`를 다시 보십시오 |
| `ERR NOT_LOADED` | `LOAD`를 안 했습니다. `GEN`이나 `POKE` 뒤에는 반드시 `LOAD` |
| `ERR DMA_ERROR` | `REG`로 `0x060`(DMA_STATUS)을 보십시오. 비트 의미는 6.2절 |
| `ERR TIMEOUT` | 탐색이 콘솔의 폴링 상한을 넘었습니다. `SET CAP=...`를 조정하십시오 |
| `MISS reason=SHOT_CAP` | 정상 동작입니다. 정답이 없거나 shot 상한에 걸린 것입니다 |
| 호스트 스크립트가 응답을 못 받음 | 탐색이 길면 대기 시간을 `SHOT_CAP` 에 맞춰 늘리십시오 |
| 명령을 연달아 보냈더니 깨짐 | 흐름 제어가 없습니다. **응답을 받은 뒤 다음 명령**이 규약입니다 |

### 6.1 STATUS 비트 읽는 법

`REG` 명령이나 `STAT`의 `status=0x...`를 이렇게 읽습니다.

| bit | 이름 | 뜻 |
|--:|---|---|
| 0 | `busy` | 실행 중 |
| 1 | `load_busy` | 적재 중 |
| 2 | `done_sticky` | 완료. `COMMAND` 쓰기로 클리어 |
| 3 | `result_valid` | Single 결과 유효 |
| 4 | `config_error` | 설정 오류 |
| 5 | `shot_limit` | shot 상한 도달 |
| 6 | `budget_limit` | logical budget 도달 |
| 7 | `amp_overflow` | 진폭 포화. **진단용이고 결과 무효가 아닙니다** |
| 8 | `zero_weight_error` | Born total-weight 오류 |
| 9 | `load_error` | loader 검증 오류 |
| 10 | `enum_done` | 열거 종료 |
| 11 | `fifo_empty` | Result FIFO 비었음 |

자주 보게 될 조합입니다.

| 값 | 뜻 |
|---|---|
| `0x080c` | 완료 + 결과 유효 + FIFO 빔 → 정상 Single |
| `0x0404` | 완료 + 열거 종료, FIFO에 결과 남음 → **아직 뽑아야 함** |
| `0x0c04` | 완료 + 열거 종료 + FIFO 빔 → 다 뽑았음 |
| `0x0844` | 완료 + budget 도달 + FIFO 빔 → 못 찾고 끝남 |

### 6.2 DMA_STATUS 비트

| bit | 이름 | 원인 |
|--:|---|---|
| 0 | `dma_busy` | 진행 중 |
| 1 | `dma_error` | 아래 것들의 OR |
| 2 | `align_error` | `DATA_ADDR`이 4바이트 정렬이 아님 |
| 3 | `count_error` | `DATA_COUNT`가 1~16384 밖 |
| 4 | `resp_error` | AHB 응답 오류 |
| 5 | `busy_error` | Main IP가 busy라 거절 |
| 6 | `range_error` | System SRAM 범위 밖 |
| 7 | `dma_done_sticky` | 완료 |

`0x00000080`이면 완료만 선 정상 상태입니다.

## 7. 지켜야 하는 규약 다섯

RTL과 드라이버가 이미 강제하지만, 직접 CSR을 두드릴 때는 사람이 지켜야 합니다.

1. **`COMMAND`를 쓰기 전에 `STATUS`를 확인합니다.** start 큐가 없어서 조건이
   안 맞으면 펄스가 조용히 버려집니다. 시작한 줄 알고 폴링하면 직전 실행의
   `done`을 보고 낡은 결과를 읽습니다.
2. **완료 판정은 `done_sticky`로 합니다.** 그리고 그것을 지우는 것은
   `COMMAND` 쓰기뿐입니다 — `STATUS`를 읽어도, 설정을 바꿔도 안 지워집니다.
3. **결과는 `busy`가 내려간 뒤에 읽습니다.** `RESULT_INDEX`·카운터·텔레메트리는
   APB 트랜잭션 여러 번에 나눠 읽히므로, 그 사이에 새 실행이 시작되면 서로
   다른 시점의 값이 섞인 스냅샷을 얻습니다.
4. **적재 중에는 시작하지 않습니다.** 절반만 채워진 배열 위에서 오라클을
   돌리면 아무 경고 없이 그럴듯한 오답이 나옵니다.
5. **`FIFO_DATA`는 읽는 것 자체가 pop입니다.** 그리고 **인덱스 0이 정상
   결과일 수 있으므로 값 0을 empty로 해석하면 안 됩니다.** 비었는지는
   `STATUS.fifo_empty`나 `FIFO_COUNT`로 봅니다. 열거에서는 `done`만
   기다리면 안 되고, 실행 중에도 계속 뽑아야 합니다 — FIFO가 256칸이라
   그보다 많은 해가 나오면 full stall에 걸립니다.

## 9. 실물 RTL과 대조한 결과

통신 계층 RTL은 인수인계 문서의 계약(§1.4 CSR 맵, §1.5 비트 정의, §3.3 포트,
§3.4 Main IP 인터페이스, §3.5 동작)만 보고 쓴 별도 구현이었습니다. 실물이
`hardware_bram/src/` 로 들어오면서 아래가 정리됐습니다.

| # | 항목 | 우리 구현 | 실물과 대조한 결과 |
|:-:|---|---|---|
| 1 | `pending_valid`의 의미 | mmio의 `done_sticky`. 직전 완료가 안 읽힌 상태에서 새 start를 막습니다 | 계약에 정의가 없어 우리 해석을 유지. 회귀 T1~T9가 이 의미로 고정 |
| 2 | `done` / `enum_done`이 펄스인가 레벨인가 | 상승 에지로 latch — 어느 쪽이든 같게 동작 | 실물이 1클록 펄스. 그대로 동작 |
| 3 | 코어 module 이름 | 계약 이름 `bbht_grover_core` | 실물은 `bbht_grover_main_ip`. `src/bbht_grover_core_adapter.v` 가 흡수 |
| 4 | `search_busy` | 계약에 없어서 `busy & ~load_busy`로 유도 | 실물도 따로 안 내보냄. 유도 유지 |
| 5 | `clk` / `rstnn` 이름 | 계약표가 적지 않아 RVX 관례를 따랐습니다 | 이름·리셋 차이도 어댑터가 흡수 |
| 6 | AHB 세션당 사이클 | 워드당 3사이클 (SINGLE + 16비트 쓰기 2회) | 정본 통신 계층과 같은 TB 에서 같은 사이클 |
| 7 | `rpaddr`이 전체 주소인가 오프셋인가 | `rpaddr[11:0]`만 디코드 — 어느 쪽이든 동작 | 보드 E2E 통과로 확인 |

배선이 계약과 어긋나지 않는지는 `make -C hardware_bram/sim ports ports-real` 가
대조해 왔습니다. 대조 기준 tsv 가 빠진 지금은 멈춰 있습니다.

## 11. 옛 설계안과 실물이 다릅니다

이것을 모르면 몇 시간을 날립니다. 왼쪽 열은 **전부 폐기된 값**이고, 옛 문서나
`trash_bin/` 에서 마주치면 무시하십시오.

| 항목 | 폐기된 옛 설계안 | **보드에서 검증된 정본** |
|---|---|---|
| 큐비트 | n = 15 (N = 32,768) | **Q = 14 (N = 16,384)** |
| CSR 간격 | 8바이트 | **4바이트** |
| CSR 이름 | `mode` `thr_a` `start` `cand` … | **`CONTROL` `THRESHOLD_A` `COMMAND` `RESULT_INDEX` …** |
| AHB | INCR16 버스트 | **SINGLE, single outstanding** |
| 모듈 | `grover_mmio` `grover_ahb_master` | **`bbht_grover_mmio` `bbht_ahb_loader`** |
| 재개 캐시 | `j_cur` + `cache_valid` | **K3/H3 checkpoint policy** |

**보드에서 검증된 K3/H3-E4-M2 가 정본입니다.** 이 저장소의 코드와 문서는 전부
그 계약을 따릅니다. CSR 계약 자체는 v0.9.8 이후 바뀌지 않았습니다 — 38개
레지스터의 주소도 비트 배치도 그대로입니다. 옛 설계안의 RTL과 펌웨어 헤더는 `trash_bin/` 으로 내려갔고,
거기서는 아무것도 인용하지 마십시오.
