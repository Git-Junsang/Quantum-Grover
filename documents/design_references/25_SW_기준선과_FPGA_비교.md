가속기를 쓰지 않는 C 코드로 같은 탐색을 돌려 FPGA 와 맞댄 장입니다. 같은 소스를 두 곳에서 돌렸습니다.

1. 200T 보드(AX7A200B)의 ORCA 코어(RV32IM, 50 MHz)
2. 서버의 x86 코어 하나

비교 상대는 같은 보드에서 잰 K3/H3-E4-M2 의 Predicate500 입니다(2026-10-08,
[18장 18.5절](18_보드_확인과_실측.md#185-2026-10-08-200t-보드의-여섯-모델)). 워크로드는 셋 모두 네 술어 × M 5종
× seed 100 = 2,000개로 같습니다. 근거 묶음은
[sw_baseline_predicate500](../../hardware_bram/results/2026-10-11_sw_baseline_predicate500/evidence.md) 입니다.

이 비교는 성능 세 축의 정본([1장 1.5절](01_프로젝트_개요.md#15-성능-지표와-인용-기준))과 보드 · 워크로드 ·
기준선 코드가 다릅니다. 섞지 않는 규칙은 25.7절에 있습니다.

## 25.1 세 모델

소스는 [`software/orca_sw/`](../../software/orca_sw/) 의 세 폴더입니다. 세 폴더의 소스는 같고,
`src/baseline_config.h` 의 `BBHT_MODEL` 한 줄만 다릅니다. 폴더 하나가 RVX 앱 하나입니다.

| 모델 | 폴더 | 계산 | 체크포인트 | SRAM 사용 |
|---|---|---|---|--:|
| ① naive | `orca_bbht_naive` | 오라클은 대각 행렬, 확산은 `(2/N)J − I` 밀집 행렬로 그대로 곱합니다. 반복 1회에 곱셈-누산이 N² ≈ 2.7억 번입니다. 측정은 행을 처음부터 훑습니다 | 없음 | 173.4 KB |
| ② 최적화 + K3H3 | `orca_bbht_opt_k3h3` | ③ 과 같은 코어에 체크포인트를 더했습니다 | K3H3 (최대 3개 보관, 다음 요청 3개를 보고 결정) | 227.2 KB |
| ③ 최적화 Normal | `orca_bbht_opt_normal` | 반복 1회에 배열을 한 번 훑고, 타겟(최대 256개)만 앞뒤로 보정합니다. 측정은 행 누적 가중치를 이진 탐색합니다 | 없음 | 108.5 KB |

SRAM 사용은 RVX release 빌드 ELF 의 끝 주소입니다(1 KB = 1,024바이트, 스택 8 KB 포함).
② · ① 은 128 KB 를 넘으므로 SRAM 256 KB 플랫폼이 필요합니다(25.3절).

① 은 **일부러 최적화하지 않은 기준선**입니다. 모든 행의 내적이 사실 같은 값이지만 행마다 다시
계산하고, 컴파일러가 재사용하지 못하게 막아 두었습니다. 최적화 효과를 보이는 보조 기준이고,
FPGA 와 맞대는 주 기준은 ② · ③ 입니다. 이 구성은 같은 RVX SoC 와 ORCA 코어에서 naive C 와
최적화 C 를 기준선으로 둔 Choi & Lee (AIMS Mathematics, 2024) 를 따랐습니다.

② · ③ 은 결과를 바꾸지 않는 계산을 생략합니다. ① 은 일부러 그대로 둡니다.

| 경우 | 생략하는 것 | 2,000개에서 |
|---|---|--:|
| ③ 요청 `j = 0` | 균일 상태 초기화와 CDF 계산 패스. 균일 상태를 바로 측정하고 CDF 는 식으로 채웁니다 | 시도 29,382번 중 8,870번 |
| ② 정확히 적중 (요청한 `j` 상태를 이미 보관) | 다음 `j` 예측과 정책 계산. 적중이면 정책 결과를 쓰지 않습니다 | 16,173번 |
| ② 보관 상태를 다시 측정 | CDF 계산 패스. 체크포인트마다 CDF(4 KB)를 같이 보관해 다시 씁니다. 측정 난수는 매번 새로 뽑습니다 | 14,754번 |

## 25.2 FPGA 와 같게 맞춘 조건

모두 정수 연산이라, 같은 입력이면 결과 인덱스 · 시도 수 · L · 실제 반복이 FPGA 와 같습니다(25.5절).

| 항목 | 값 |
|---|---|
| 상태 | 진폭 N = 16,384개, Q1.22 부호 있는 int32 (균일 상태 32768) |
| 2 × 평균 | 오라클 적용 후 합을 2¹³ 으로 한 번에 반올림 (정확히 반이면 짝수 쪽) |
| 포화 | ±(2²² − 1) 대칭 |
| BBHT | m 시작 1, λ = 6/5, 상한 128 (28단계 정수 표), 논리 예산 576, 샷 상한 100 |
| 종료 검사 순서 | 성공 → 샷 상한 → 예산 (L + 1 ≥ 576) |
| `j` 난수 | 32비트 LFSR (탭 31 · 21 · 1 · 0), 한 번 뽑을 때 7단계 진행, 하위 바이트 & mask, 범위 밖이면 다시 |
| 측정 난수 | xorshift64 (13, 7, 17), seed 확장 {s, s ^ 0x9E3779B9} |
| 측정 | 32 lane 행 단위 누적 가중치 \|a\|², 임계값보다 큰 첫 행 → 그 행에서 첫 lane |
| 워크로드 | Predicate500 2,000개, 보드 실험과 같은 seed |

다른 점은 오라클 하나입니다. SW 는 데이터셋 값 16,384개 대신 "조건을 만족하는 인덱스 목록"
(`p500_workloads.h`)을 받고, 그 준비 시간은 측정 구간에서 빠집니다. FPGA 는 반복마다 데이터를 비교하므로
SW 쪽이 조금 유리합니다.

## 25.3 실행 환경

| 항목 | ORCA 보드 | 서버 | FPGA |
|---|---|---|---|
| 하드웨어 | AX7A200B `xc7a200tfbg484-2`, 100T 예산 구현([17장 17.9절](17_보드_운용.md#179-원격-200t-보드-ax7a200b)) | Intel Core i5-14600K, P 코어 하나에 고정 (`taskset`) | 같은 보드, K3/H3-E4-M2 |
| 클럭 | ORCA 50 MHz | 실측 5.26~5.28 GHz (터보) | 가속기 100 MHz |
| 컴파일 | RVX release, `riscv64-unknown-elf-gcc -O2 -march=rv32im` | `gcc 13.3.0 -O2`, `-march` 없음. 나머지 코드 생성 옵션은 RVX 와 같음 | — |
| 시간 | `bbht_search()` 앞뒤, RVX 실시간 클럭(1 us 틱) | 같은 구간, `CLOCK_MONOTONIC_RAW` | `wall_us`: 같은 보드 실시간 클럭, `COMMAND` 직전 ~ DONE ([14장](14_호스트_인터페이스와_UART_프로토콜.md)) |
| 사이클 | 시간 × 50 (환산) | 같은 구간의 사용자 공간 코어 사이클 (perf_event, 실측) | 가속기 `cycle_count` |
| 반복 측정 | 1회 | ③ · ② 10회(워크로드별 중앙값), ① 1회 | 1회 |
| 측정일 | 2026-10-11 | 2026-10-11~12 | 2026-10-08 |

### ORCA 보드의 두 플랫폼

③ 은 FPGA 측정에 쓴 M2 비트스트림(`bbht_grover_upgrade`, SRAM 128 KB)에 앱만 올려 쟀습니다. 가속기 CSR 은
건드리지 않습니다. ② · ① 은 SRAM 이 모자라, 가속기 없이 ORCA 하나와 SRAM 256 KB 만 둔 플랫폼
[`software/orca_sw/rvx/orca_sw.xml`](../../software/orca_sw/rvx/orca_sw.xml) 을 따로 구현했습니다. 200T 구현은
WNS +6.688 ns 이고, 100T 예산으로 Available 이 100T 와 같습니다.

두 플랫폼에서 ③ 의 SMOKE 와 CALIBRATE 를 각각 돌려 보니 시간이 같았습니다(25.5절). 코어와 클럭이 같으면
가속기 유무와 SRAM 크기는 SW 시간에 영향이 없습니다.

### 서버 빌드

소스는 손대지 않고, `main.c` 가 쓰는 RVX 헤더 셋만 [`software/orca_sw/host/stub/`](../../software/orca_sw/host/stub/)
로 바꿔 끼웁니다.

| 헤더 | 보드 | 서버 |
|---|---|---|
| `platform_info.h` | 플랫폼 정보 | 빈 헤더 |
| `ervp_printf.h` | UART printf | `<stdio.h>` |
| `ervp_real_clock.h` | 1 us 틱 카운터 | `CLOCK_MONOTONIC_RAW` us 를 돌려주고, 같은 구간의 코어 사이클을 모아 끝에 `HOST_CYCLES,<순번>,<사이클>` 로 찍음 |

시간과 사이클은 **한 실행 파일, 한 실행**에서 같이 잽니다. 시간용 · 사이클용을 따로 빌드했을 때 `main.c` 에
들어가는 헤더 차이만으로 함수 배치가 바뀌어, 같은 계산이 ③ 0.644 / 0.553 초, ② 0.242 / 0.297 초로 달랐기
때문입니다. 서버 시간은 코드 배치에 따라 이 정도(±15~20%) 흔들릴 수 있습니다.

## 25.5 검증

- **궤적**: ORCA ③ · ②, 서버 ①, 서버 ③ · ② 각 10회가 모두 FPGA 와 `seed_j` · `seed_meas` · `result_index` ·
  `trial_count` · `L_BBHT` · 실제 반복에서 2,000/2,000 같습니다. ② 의 실제 반복은 FPGA ckpt 의 물리 반복과
  워크로드마다 같습니다. SW 의 K3H3 정책이 하드웨어 정책 엔진([11장](11_체크포인트와_정책_엔진.md))과 같은 반복
  수를 낸다는 뜻입니다.
- **플랫폼 사이**: 같은 모델이면 ORCA 와 서버의 시간 열을 뺀 모든 열(종료 사유, 포화 수 포함)이 같습니다.
- **ORCA 플랫폼 차이**: ③ 을 두 플랫폼에서 돌린 값입니다. SMOKE 는 762,498 us 로 같고, 반복 20회도
  1,283,366 us 로 같습니다. 측정 1회만 54,178 대 54,177 us 로 1 us 틱 차이입니다.
- **① 추정식**: ORCA 에서 두 워크로드(M = 256, seed 0 의 GT · RANGE)를 끝까지 돌린 실측과 +0.0029% 차이입니다.
  서버에서는 2,000개 전체 실측이 서버 단가 추정과 +0.81% 차이입니다.

## 25.6 해석

- **ORCA ÷ FPGA 의 만 단위 배수는 알고리즘 우위가 아닙니다.** 16,384 상태벡터를 32비트 코어 하나로 훑는
  것과 P = 32 레인으로 훑는 것의 차이에 클럭 2배가 곱해진 값입니다. 오라클 준비가 SW 쪽에서 빠지므로 SW 가
  조금 유리한 조건입니다.
- **서버 한 코어는 FPGA 와 시간이 비슷합니다.** 전체로 서버 ③ 은 FPGA normal 의 1.15배, ② 는 FPGA ckpt 의
  1.34배 걸립니다. M = 64 · 256 에서는 서버가 FPGA 보다 빠릅니다. 서버는 가속기보다 클럭이 약 53배 높은
  범용 코어이고, `-O2` 에서 `bbht_core.c` 의 코어 루프 셋이 16바이트(SSE2) 벡터로 자동 벡터화됩니다(gcc
  `-fopt-info-vec` 보고. ① 의 `bbht_naive.c` 는 벡터화되지 않음). 사이클로 보면 FPGA 가 같은 일을 62~74배
  적은 클럭으로 끝냅니다.
- **체크포인트 효과가 환경마다 다릅니다.** 실제 반복은 세 환경 모두 125,106 → 37,659 로 같이 줄지만, 시간은
  ORCA 2.709배 · FPGA 2.167배 · 서버 1.859배 줄었습니다. 반복 1회와 측정 1회의 상대 비용이 환경마다 다르고,
  SW ② 는 측정용 CDF 도 재사용합니다(25.1절). 어느 쪽이 얼마를 차지하는지는 나눠 재지 않았습니다.

## 25.7 인용할 때

- **성능 세 축의 정본과 섞지 않습니다.** 정본은 2026-09-07 빌드 · 100T 보드 · EQ 500 이고, 그 ORCA 116,426x 는
  옛 기준선 `hardware_bram/firmware/orca_sw_baseline` (반복 1회에 배열을 두 번 훑음, 체크포인트 없음) 대 M2
  체크포인트 모드입니다. 이 장은 200T 보드 · 네 술어 2,000개 · 새 기준선이고 같은 모드끼리 맞댑니다.
- **서버 비교를 함께 적습니다.** 가속 효과를 말할 때 ORCA 배수만 쓰지 말고, 서버 한 코어가 FPGA 와 비슷한
  시간에 끝난다는 25.4절 값을 같이 밝힙니다.
- ORCA ① 은 추정값입니다. 실측과 같은 열에 둘 때는 표시합니다.
- 사이클 축과 시간 축을 섞어 배수를 만들지 않습니다. 고전 선형 스캔과는 비교하지 않습니다.

| `tools/board_run.sh` | 200T 보드에 굽고 앱을 올려 UART 를 캡처. 원격 쪽을 떼어 놓아 ssh 가 끊겨도 측정이 계속됩니다 |
| `host/build_host.sh` · `host/stub/` | 같은 소스를 서버에서 빌드 |
| `tools/compare.py` | ORCA · 서버 로그를 FPGA CSV 와 워크로드마다 맞대고 합계 · 검증을 냄 |

```bash
# ORCA 보드 (② 예시). 먼저 rvx/orca_sw.xml 을 $RVX_MINI_HOME/platform/orca_sw/ 에 두고
# 앱 세 폴더를 그 플랫폼의 app/ 에 복사한 뒤 200T 로 구현합니다.
.claude/skills/fpga-syn-rvx/scripts/fpga_syn_rvx.sh start orca_sw --budget-100t --threads=1
software/orca_sw/tools/build_app.sh <imp폴더> orca_bbht_opt_k3h3 PROFILE=1
software/orca_sw/tools/board_run.sh start k3h3_full <bit> <imp폴더> orca_bbht_opt_k3h3 10800
software/orca_sw/tools/board_run.sh fetch k3h3_full
.claude/skills/fpga-flash/scripts/sdsl_fpga.sh restore --pcie      # 끝나면 반드시

# 서버 (③ 예시)
software/orca_sw/host/build_host.sh orca_bbht_opt_normal normal_full PROFILE=1
taskset -c 4 /tmp/orca_host_bin/normal_full > normal_full_1.log
```

- RVX `make <앱>` 의 기본은 debug(`-O1 -g`)입니다. `build_app.sh` 는 release(`-O2`)를 강제하고 로그에서 확인합니다.
- 200T 구현은 메모리를 3~4 GB 씁니다. 서버의 다른 작업과 겹치면 Vivado 가 OOM 으로 죽으니 `--threads=1` 로 돌립니다.
- 보드 점유는 ③ FULL 2시간 39분, ② FULL 59분, ① CALIBRATE 39분, ① 두 워크로드 58분이었습니다.

### 프로필과 설정

`src/baseline_config.h` 의 매크로입니다. `build_app.sh` · `build_host.sh` 에는 `BBHT_` 를 뗀 이름으로 넘깁니다.

| 매크로 | 기본값 | 뜻 |
|---|---|---|
| `BBHT_MODEL` | 폴더마다 1 · 2 · 3 | 모델. 폴더와 맞춰져 있으니 바꾸지 않습니다 |
| `BBHT_PROFILE` | 0 | 0 SMOKE · 1 FULL · 2 CALIBRATE · 3 SUBSET |
| `BBHT_SEED_COUNT` | 100 | FULL 에서 seed 0 ~ (값 − 1) |
| `BBHT_CALIB_ITERS` | 2 | CALIBRATE 에서 잴 반복 횟수 |
| `BBHT_SUBSET_PRED_MASK` | 0xF | 비트 0 LT · 1 GT · 2 EQ · 3 RANGE |
| `BBHT_SUBSET_M_MASK` | 0x10 | 비트 0 M=1 · 1 M=4 · 2 M=16 · 3 M=64 · 4 M=256 |
| `BBHT_SUBSET_SEED_FIRST` · `_END` | 0 · 1 | SUBSET seed 범위 [FIRST, END) |

| 프로필 | 실행 내용 |
|---|---|
| SMOKE | EQ, M = 256, seed 0 하나. 기대값 result 15288 · trial 8 · L 7 · 실제 반복 7 (② 는 3) |
| FULL | 네 술어 × M 5종 × seed `BBHT_SEED_COUNT` 개 |
| CALIBRATE | EQ, M = 1 에서 반복 `BBHT_CALIB_ITERS` 회와 측정 1회의 시간. `SW_CALIB_ITER` · `SW_CALIB_MEASURE` 줄 |
| SUBSET | 마스크와 seed 범위로 고른 일부. 워크로드는 서로 독립이라 나눠 돌려도 FULL 과 결과가 같습니다 |

### 출력 줄

워크로드 하나에 `SW_RUN` 한 줄입니다. 열은 `model, predicate, target_count, seed_index, seed_j, seed_meas,
success, result_index, trial_count, L_BBHT, actual_grover_iterations, termination, saturations, timer_hi, timer_lo`
이고, 시간은 `timer_hi × 2³² + timer_lo` us 입니다. `termination` 은 0 성공 · 1 샷 상한 · 2 예산입니다. 옛
`orca_sw_baseline` 과 달리 앞에 `model` · `predicate` 두 열이 있고 seed 가 16진수라 옛 파싱 스크립트를 그대로
쓰지 않습니다. 끝 표시는 `[RVX/END] ORCA_BBHT_BASELINE` 입니다.

## 25.9 소스 구조

```
main()
 ├─ 오라클 준비 (타겟 비트셋)                         ← 시간 밖
 ├─ 타이머 시작
 ├─ bbht_search()
 │    시도마다: j 뽑기 → 상태 계산 → 측정 → 종료 검사
 │      상태 계산  ③ j = 0 이면 균일 상태 그대로, 아니면 bbht_core_opt_iterate × j
 │                 ① bbht_core_naive_iterate × j
 │                 ② bbht_k3h3_lookup: 적중이면 보관 상태 그대로
 │                    아니면 bbht_k3h3_execute (정책 → 보관 상태에서 이어서 반복)
 │      측정       CDF 준비 (계산, 식, 또는 보관본 재사용) → bbht_sample_rows
 ├─ 타이머 끝
 └─ SW_RUN 출력                                       ← 시간 밖
```

| 파일 | 내용 |
|---|---|
| `main.c` | 진입점. 프로필별 실행, 시간 측정, 출력. RVX 헤더는 이 파일만 씁니다 |
| `baseline_config.h` | 모델과 프로필 설정 |
| `bbht_q14.h` | 상수, 자료형, 함수 선언 |
| `bbht_core.c` | `j` 난수 · 측정 난수, m 상한 표, 반올림, 오라클 비트셋, 최적화 코어, 측정 |
| `bbht_naive.c` | ① 코어: 오라클 적용 뒤 행마다 16,384개 내적 |
| `bbht_k3h3.c` | ② 적중 확인, 정책, 메모리(24비트 압축, 작업 버퍼 상주, 균일 상태 재생성, 체크포인트별 CDF) |
| `bbht_search.c` | BBHT 탐색 루프. 세 모델 공통이고, ② 는 적중하지 않았을 때만 다음 `j` 3개를 미리 계산해 정책에 넘깁니다 |
| `p500_workloads.h` | 생성 파일: 타겟 인덱스 1,364개(데이터셋 20개), seed 100쌍. 손으로 고치지 않습니다 |

힙(`malloc`)과 부동소수점은 쓰지 않습니다. 큰 배열은 모두 전역입니다.
