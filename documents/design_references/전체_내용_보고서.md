## 2. 프로젝트 목표

FPGA에서 Grover 상태벡터 연산을 에뮬레이션하고, 다음 조건을 만족하는 입력
인덱스를 탐색한다.

| Oracle | 타겟 조건 |
|---|---|
| LT | `data < threshold_a` |
| GT | `data > threshold_a` |
| EQ | `data == threshold_a` |
| RANGE | `threshold_a < data < threshold_b` |

단일 검색은 후보 인덱스 하나를 반환한다. 열거는 이미 찾은 인덱스를 오라클에서
제외하며 중복 없는 목록을 만든다.

## 4. 검증 수준 구분

수치를 인용할 때 어느 칸인지 밝히지 않으면 나중에 반드시 어긋난다.

| 수준 | 의미 |
|---|---|
| 보드 실측 | 실물 FPGA 에서 잰 값. 최종 근거 |
| RTL 시뮬 | verilator 회귀에서 잰 값. 보드와 0.00% 일치를 확인한 하네스가 있다 |
| 비트 단위 골든 모델 | 정수 연산·반올림·saturation·LFSR·Born 측정을 Python 으로 재현 |
| 소프트웨어 추정 | 합성 없이 정확도·저장량·이상적 cycle·정책 이득을 계산 |

현재 실제 RTL 기준은 **Q14 / P32 / signed DATA16 / 소수부 22 / AMP_W 23** 이다.
Q15·Q16·P64 확장은 폐기했다.

## 5. 전체 실행 구조

```text
signed16 dataset + predicate + threshold + DATA_COUNT
        |
        v
Oracle target 판정과 패딩 제외
        |
        v
내부 BBHT scheduler가 j 선택
        |
        v
균일 진폭 초기화 또는 checkpoint 슬롯에서 재개
        |
        v
Grover j회: Oracle 위상 반전 -> 평균 계산 -> Diffusion
        |
        v
정수 Born 측정: 진폭 제곱 -> 누적 가중치 -> LFSR 추첨
        |
        v
측정 후보를 predicate로 고전 검증
        |
        +-- 성공: result_index 반환 (열거면 FIFO 에 넣고 계속)
        |
        `-- 실패: m 증가 후 새 j로 다음 shot
```

## 6. 데이터와 패딩

- dataset 은 index 0부터 `DATA_COUNT-1` 까지 signed 16비트로 저장한다.
- `index >= DATA_COUNT` 인 상태는 메모리 값과 무관하게 항상 비타겟이다.
- Q14 에서 최대 N = 16,384 이고, `DATA_COUNT < N` 이면 남는 상태가 패딩이다.
- 캠페인은 패딩 자리에 조건을 만족하는 값을 일부러 넣는 POISON 조건도 돌렸다.
  671,600회 전부에서 패딩 인덱스가 결과로 나온 경우는 0이었다.

## 7. Grover 정수 데이터패스

초기 진폭은 다음과 같다.

$$
A_i^{(0)}=\frac{1}{\sqrt{N}}
$$

한 Grover 반복은 두 단계다.

1. Oracle: 타겟 진폭의 부호를 반전한다.
2. Diffusion: Oracle 이후 평균 $\mu$ 를 구하고 모든 진폭을 갱신한다.

$$
\mu=\frac{1}{N}\sum_{i=0}^{N-1}A_i^{\mathrm{oracle}}
$$

$$
A_i^{\mathrm{next}}=2\mu-A_i^{\mathrm{oracle}}
$$

진폭은 signed 23비트(소수부 22)다. 평균은 확장 누산기로 구하고 최종 shift 에서
ties-to-even 반올림을 적용한다. 범위를 벗어난 값은 양·음 대칭 범위로 saturate 한다.
자세한 비트폭과 파이프라인은
[데이터_고정소수점_메모리_규격.md](데이터_고정소수점_메모리_규격.md)에 있다.

## 8. Born 측정과 후보 검증

각 상태의 측정 가중치는 정수 진폭의 제곱이다.

$$
w_i=A_i^2,\qquad W=\sum_i w_i
$$

LFSR 난수로 $[0,W)$ 임계값을 만들고 누적합이 그 값을 처음 넘는 index 를 고른다.
고른 index 가 실제 predicate 와 `DATA_COUNT` 조건을 만족하는지 다시 검사한다.

이 고전 검증은 답을 scheduler 에 미리 알려주는 과정이 아니다. 측정된 후보가 실제
타겟인지 확인해 성공·실패를 정하는 표준 BBHT 외부 제어의 일부다.

## 9. BBHT 제어

BBHT 는 실제 타겟 수 M 을 scheduler 에 전달하지 않는다. 반복 상한 m 안에서 j 를
무작위로 고르고, 실패하면 m 을 약 6/5배씩 늘린다.

```text
m_bound 조회
-> j를 [0, m_bound)에서 rejection sampling
-> Grover j회
-> Born 측정과 후보 검증
-> 성공이면 종료
-> 실패이면 다음 m_bound로 이동
```

m 수열은 RTL 의 ROM 과 같은 순서를 쓴다. Q14 에서 `m_max = 128`, 논리 반복 budget
576, 기본 shot 상한 100 이 무한 실행을 막는 보호 한도다.

### 9.1 난수 스트림

| 스트림 | 용도 |
|---|---|
| j LFSR | BBHT 의 j 선택 |
| measurement LFSR | Born 측정 |

두 스트림은 독립이다. `AUTO_SHOT=0` 수동 모드에서는 내부 Born sampler 가 rejection
과정에서 난수를 몇 번 소비했는지 외부에서 알 수 없으므로, 펌웨어가 shot 마다
독립적이고 재현 가능한 `SEED_MEAS` 를 만들어 넣는 계약으로 골든 모델과 C 드라이버를
통일했다.

## 10. Normal과 checkpoint

| 모드 | 시작 상태 | 의미 |
|---|---|---|
| Normal | shot 마다 균일 진폭에서 시작 | 표준 계산 기준 |
| checkpoint | 슬롯에 남은 ψ 에서 차이만 계산 | 결과를 유지하면서 계산량 절감 |

checkpoint 는 실패한 j 를 다음 추첨에서 제거하지 않는다. BBHT 가 만든 j 순서를
그대로 쓰고, 같은 상태에 도달하기 위한 중간 계산만 재사용한다. 그래서 같은 시드에서
두 모드의 `trial_count` · `L_BBHT` · `result_index` 가 같아야 하고, `actual_grover_iterations`
만 달라야 한다. 이 불변량이 짝맞춤 검증의 전부다.

v0.7g 세대는 `amp_mem` 자체를 1-entry checkpoint 로 썼다. v0.9.8 은 슬롯 4개와
정확 DP policy 를 쓰며, horizon 은 H4 다.

## 12. RTL 자동 비교

`software/golden/rtl_output_compare.py` 가 expected JSON 과 RTL 결과를 비교한다.

```text
RTL 실행 결과
-> JSON 또는 key=value 파일 저장
-> rtl_output_compare.py 실행
-> 필드별 expected/actual 비교
-> PASS 또는 FAIL JSON 생성
```

단일 검색 기본 비교 필드는 `result_index`, `trial_count`, `L_BBHT`,
`actual_grover_iterations` 다. 열거는 발견 목록과 라운드별 mask 변화도 함께 본다.

**최종 index 만 맞는 것으로 PASS 를 선언하지 않는다.** BBHT 가 후보를 술어로 자가
검증하기 때문에 진폭이 깨져도 답은 맞을 수 있다. 실제로 다중 엔진 실험에서 공유
슬롯이 깨졌는데 결과 인덱스는 정상이었고, `trial_count` 와 `L_BBHT` 를 보고서야
드러났다.

## 14. 정밀도 분석

Q14/Q15/Q16 과 F20/F21/F22/F24, M = 1, 4, 64, N/2 를 비교했다.

| Q | 확률 L2 ≤ 10⁻³ | 확률 L2 ≤ 10⁻⁵ |
|---:|---:|---:|
| 14 | F20 | F22 |
| 15 | F20 | F24까지 미충족 |
| 16 | F20 | F24까지 미충족 |

Q14/F22 가 기준을 만족한다. Q15·Q16 은 폐기했으므로 이 표는 **왜 Q14 로 굳혔는지의
근거**로만 읽는다.

## 15. 캐시 분석

M=1, seed 30개 기준의 소프트웨어 추정이다.

| Q | 저장 상태 수 | 평균 실제 반복 | 절감률 |
|---:|---:|---:|---:|
| 14 | 0 | 212.77 | 0.00% |
| 14 | 1 | 112.13 | 47.70% |
| 14 | 2 | 97.43 | 55.22% |
| 14 | 4 | 77.77 | 63.69% |

1-entry 는 당시 v0.7g Burst 결과와 모두 일치했다. 4-entry 를 채택한 것이 K4 였고
보드에서 250쌍 −71.46% 로 확인됐다. **현재 정본은 K3 이다** — 슬롯을 4에서 3으로
줄여도 사이클이 0.21% 밖에 안 늘고, 대신 정책 지평을 같이 줄여 2.58% 를 번다
(`hardware_bram/results/2026-09-09_kh_isolated_e1/`). 슬롯을 더 늘리는 쪽은 BRAM
예산에서 막힌다 — 슬롯 하나가 RAMB36 11개다.

## 16. 규모 확장 분석

| 후보 | 진폭 상태 | row/pass | Grover 2-pass 하한 |
|---|---:|---:|---:|
| Q14/P32/F22 | 46 KiB | 512 | 1,024 cycle |
| Q15/P32/F22 | 92 KiB | 1,024 | 2,048 cycle |
| Q16/P32/F22 | 184 KiB | 2,048 | 4,096 cycle |
| Q14/P64/F22 | 46 KiB | 256 | 512 cycle |

이상적 하한이고 FSM·BRAM latency·stall·파이프라인 비용은 빠져 있다. Q15·Q16·P64 는
폐기됐으므로 이 표도 근거 기록이다. 실제로 사이클을 줄인 것은 규모 확장이 아니라
반복 안의 연산기 병렬화(E4)와 측정 경로 최적화(M1·M2)였고, 6단계 ablation 이
단계별 기여를 분리해 두었다.
