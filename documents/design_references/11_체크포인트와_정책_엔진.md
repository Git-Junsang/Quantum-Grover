# 11장. 체크포인트와 정책 엔진

체크포인트는 6단계 ablation에서 사이클을 56.63% 줄여 가장 큰 개선 효과를 보였습니다.
감소 폭은 나머지 다섯 단계의 효과를 합친 것보다 큽니다.

---

## 11.1 상태 재사용 원리

BBHT는 실패하면 `m`을 키워 다시 뽑습니다([3장 3.3절](03_Grover와_BBHT_알고리즘.md)).
그런데 새 `j`가 직전 `j`보다 크면, 이미 돌려 둔 상태에서 차이만큼만 더 돌리면
됩니다. 처음부터 다시 `S_INIT` 할 이유가 없습니다.

```
샷 1:  j = 5   →  균일 상태에서 5번
샷 2:  j = 12  →  샷 1의 5번 상태에서 7번만 더   (12번이 아니라)
```

`m`이 커지는 방향이라 새 `j`가 큰 경우가 잦고, 그래서 이득이 큽니다.

열거에서는 라운드를 넘어 재사용하면 안 됩니다. 결과 하나를 찾을 때마다 오라클의 정답
집합이 바뀌어 다른 탐색 문제가 되기 때문입니다([3장 3.5절](03_Grover와_BBHT_알고리즘.md)).

## 11.2 체크포인트 저장 구조

`grover_ckpt_meta`가 슬롯 K3 개의 유효 비트와 각 슬롯이 몇 번째 반복 상태인지를 들고,
정렬된 논리 집합 S를 유지합니다.

물리 슬롯은 K와 무관하게 4벌입니다([6장 6.7절](06_데이터_표현과_메모리_맵.md#67-메모리-구조)).
`grover_ckpt_mem_interleaved_e4`가 E4의 4행 동시 읽기에 맞춰 뱅크를 교차 배치합니다.

## 11.3 planner와 executor

`grover_ckpt_planner_pipe`가 논리적인 `{source_j, 정렬된 S'}`를 물리 슬롯 계획으로
바꿉니다. 규칙은 넷입니다.

- 출발점은 `j`이하인 체크포인트 중 가장 가까운 것. 없으면 균일 상태에서 시작
- 목적지(엔드포인트)는 반드시 만듭니다
- 중간 체크포인트는 요청 풀 안에서만 고르고, K3에서는 최대 2개
- 기존 체크포인트는 K3 용량이 허락하는 한 최대한 남깁니다

`grover_ckpt_executor`가 그 계획을 경계 시퀀스로 풀어 냅니다. 메타데이터를 지우거나
확정하는 것은 안전한 경계에서만 하고, 한 구간의 경계를 넘을 때는 1반복짜리 out-of-place
다리를 씁니다.

`grover_ckpt_segment_router`의 구간 규약이 이것입니다.

```
PASS1:  src → dst      (읽는 슬롯과 쓰는 슬롯이 다름)
PASS2:  dst → dst      (제자리)
```

이 규약에 따라 전체 상태 메모리를 한 벌 더 둘 필요가 없습니다. 오라클 결과를 목적지
슬롯에 바로 쓸 수 있는 이유도 여기에 있습니다
([9장 9.4절](09_연산_경로와_E4.md)).

## 11.4 정책 엔진 H3

어느 체크포인트를 남길지는 미래에 어떤 `j`가 올지에 달려 있습니다. 지금 당장 좋은
선택이 다음 두 번의 요청에서 나쁠 수 있습니다.

`grover_ckpt_policy_rolling`이 현재 요청 + 결정론적으로 예측되는 미래 요청
`H_FUTURE = 3` 개를 창으로 잡고, 그 창 안에서 총 물리 비용이 최소가 되는 선택을 DP로
풉니다.

DP 결과가 같은 경우를 처리하는 순서도 다음과 같이 고정합니다.

```
비교 순서:  (총 DP 물리 비용, 구간 수, 정렬된 S')
```

이 규칙이 고정되어야 소프트웨어 기준모델이 궤적을 재현할 수 있습니다. 동점에서 아무거나
고르면 모델과 RTL이 갈라지고, 500/500 대조가 성립하지 않습니다.

### Shadow-J를 이용한 미래 `j` 예측

`grover_shadow_j`가 실제 J-LFSR 상태를 복사본으로 돌려서 "이번 샷이 실패한다면 다음에
무엇이 뽑힐까" 를 미리 계산합니다. 진짜 BBHT 난수 상태는 건드리지 않습니다.

그 예측으로 미리 푼 계획은 `grover_ckpt_plan_fifo`에 넣어 두었다가, 실제로 실패가 나면
꺼내 씁니다. 맞았는지 틀렸는지는 `plan_fifo_hit_count` · `plan_fifo_mismatch_count`로
밖에서 셀 수 있습니다([13장](13_CSR_레지스터와_실행_모드.md)).

예측이 맞지 않으면 계획을 다시 계산하므로 논리 결과에는 영향을 주지 않습니다. 현재 샷이
성공하면 다음 `j`를 뽑지 않으므로 이때의 예측 불일치도 정상 동작입니다.

## 11.5 memo와 3,279 사이클

DP의 부분 결과는 memo에 담습니다.

```
MEM_ENTRIES = H_FUTURE × STATE_RANKS = 3 × 1,093 = 3,279
엔트리 = {epoch 8비트, cost 10비트} = 18비트
```

2,048×18 블록 RAM 뱅크 여럿에 나눠 담되, 뱅크 선택을 레지스터로 미리 잘라서 주소
디코드가 BRAM의 EN 경로에 붙지 않게 했습니다. 타이밍 때문입니다.

### memo 초기화 시점

그래서 리셋 뒤 첫 시작과 epoch가 한 바퀴 돌 때, 정책 엔진이 `ST_CLEAR` 상태에서 memo를
한 칸씩 지웁니다. 길이가 정확히 3,279 사이클입니다.

이 초기화 방식 때문에 보드 실행과 RTL 캠페인의 사이클 수를 직접 비교할 수 없습니다.

| 무엇                   | 언제 청소를 치르나                             |
| ---------------------- | ---------------------------------------------- |
| 6단계 ablation 캠페인  | 워크로드마다 새로 시작 → 매번                 |
| 보드 앱 ·`bench500` | 500개를 연달아 실행 → 첫 워크로드에서 한 번만 |

그래서 K3/H3-E4-M2의 473/500이 정확히 3,279 사이클 차이납니다.

원인은 2026-09-16 SoC 콘솔 시뮬에서 확인했습니다. 같은 워크로드를 리셋 직후와 그다음에
연달아 돌려 `cycle` · `policy_cycles` · `policy_stall`이 셋 다 정확히 +3,279이고
`max_latency`가 3,352로 튀는 것을 보았습니다
([soc_rtl_console](../../hardware_bram/models/hardware_bram_K3H3_E4_M2/results/2026-09-16_soc_rtl_console/evidence.md)).

이 원인은 한 워크로드에서 확인했으며 473건 전체를 같은 방식으로 재현하지는 않았습니다.
나머지 21건의 차이는 epoch 순환에 따른 초기화 시점과 관련된 것으로 보이지만 아직
검증하지 않았습니다.

## 11.6 K와 H의 선택

K4/H4에서 K3/H3으로 줄였을 때 사이클이 7.66% 감소했고 자원 사용량도 함께 줄었습니다.

| 구성     |    LUT |     FF | BRAM tile | DSP |
| -------- | -----: | -----: | --------: | --: |
| K4/H4-E4 | 30,294 | 25,822 |      83.0 |  64 |
| K3/H3-E4 | 29,959 | 25,655 |      83.0 |  64 |

둘을 따로 떼어 본 실험
([kh_isolated_e1](../../hardware_bram/results/2026-09-09_kh_isolated_e1/evidence.md))
은 K와 H의 영향을 분리해 측정했습니다.

| 무엇을 줄였나 |    몫 |
| ------------- | ----: |
| K만 줄임      | 0.21% |
| H를 줄임      | 2.58% |

주된 비용은 체크포인트 저장 공간이 아니라 유지할 체크포인트를 결정하는 과정에서
발생합니다. H가
크면 DP 창이 넓어져 풀이가 오래 걸리고, 그동안 데이터패스가 기다립니다(`policy_stall`).
BRAM이 줄지 않는 것도 물리 슬롯이 K와 무관하게 4벌이기 때문입니다
([6장 6.7절](06_데이터_표현과_메모리_맵.md#67-메모리-구조)).

## 11.7 제외한 설계안

| 무엇                            | 왜                                                                         |
| ------------------------------- | -------------------------------------------------------------------------- |
| 5벌 이상의 체크포인트           | 저장 공간보다 체크포인트 선택에 드는 결정 비용이 큽니다                    |
| 전체 상태 scratch 한 벌 더      | 구간 규약이 목적지 슬롯을 그대로 쓰므로 필요 없습니다                      |
| 라운드를 넘는 체크포인트 재사용 | 정답 집합이 바뀌면 다른 탐색 문제입니다                                    |
| 요청 열 분할형 다중 엔진        | 분할 비용 +50%, 슬롯 소유권 문제로 탈락                                    |
| PASS2 융합                      | 측정 재스캔을 없애는 방식. 정본은 재스캔 비용을 줄이는 방식을 채택했습니다 |

정책 알고리즘을 고른 과정과 K·H 를 정한 실험, 마지막 둘의 실측은
[23장](23_설계_근거_실험.md)에 있습니다.
