시스템은 네 계층입니다.

1. 호스트 PC: [`software/host/bbht_cli.py`](../../software/host/bbht_cli.py) 또는 시리얼 터미널.
   ASCII 한 줄을 보내고 한 줄씩 받습니다([14장](14_호스트_인터페이스와_UART_프로토콜.md)).
2. RVX SoC (50 MHz): ORCA RV32 코어가 명령을 파싱하고
   [`bbht_grover_driver.c`](../../hardware_bram/firmware/bbht_grover_driver.c)로 CSR 을
   씁니다. 데이터셋은 코어가 시스템 SRAM 에 두고, 가속기가 AHB 마스터로 직접 끌어갑니다.
3. 통신 계층 (100 MHz): APB 슬레이브 `bbht_grover_mmio`, AHB 마스터 `bbht_ahb_loader`, 계약
   이름과 실물 모듈 이름을 잇는 어댑터([7장](07_통신_계층.md)).
4. Main IP (100 MHz): 진폭과 데이터셋을 BRAM 에 들고 Grover 반복 · Born 측정 · 고전 검증 ·
   BBHT 제어를 전부 합니다([8장](08_Main_IP_최상위와_BBHT_제어.md)~[11장](11_체크포인트와_정책_엔진.md)).

단일 검색과 열거, 결과 FIFO, 체크포인트 정책이 전부 Main IP 안에 있습니다. 바깥에 둔 것은
APB CSR · AHB 적재 · UART 뿐입니다.

## 5.2 모듈 계층과 파일 지도

```
RVX SoC (bbht_grover_upgrade)
├── ORCA RV32 코어 + micro NoC          RVX 생성 (50 MHz)
├── APB NI (sni_apb_asynch)             RVX 생성 · CDC 담당
├── AHB NI (mni_ahbm_asynch)            RVX 생성 · CDC 담당
├── 시스템 SRAM 128 KiB                 RVX 생성
└── user region                         프로젝트 구현 (100 MHz)
    └── bbht_rvx_wrapper                최상위. 계약 이름 bbht_grover_core 에 연결
        ├── bbht_grover_mmio            APB 슬레이브 · CSR 38개
        ├── bbht_ahb_loader             AHB 마스터 · 데이터셋 DMA
        └── bbht_grover_core_adapter    계약 이름과 리셋 차이를 변환
            └── bbht_grover_main_ip     Main IP (8장~11장)
```

공용 RTL 소스 18개는 [`hardware_bram/src/`](../../hardware_bram/src/)에 있고, 모델마다 다른
어댑터 하나는 모델 폴더에 있습니다(아래 "하드웨어 트리와 BRAM 모델"). 아래 표의 어댑터와 플랫폼
정의는 최종 구성 `K3H3_E4_M2` 의 것입니다. 통신 계층은 SJS, Main IP 는 PJK 가 맡았습니다.

| 파일 | 담당 | 역할 |
|---|:-:|---|
| [`bbht_rvx_wrapper.v`](../../hardware_bram/src/bbht_rvx_wrapper.v) | SJS | RVX user region 최상위. 어댑터를 거쳐 Main IP 에 연결 |
| [`bbht_grover_mmio.v`](../../hardware_bram/src/bbht_grover_mmio.v) | SJS | APB CSR. 생성 헤더 `bbht_grover_csr.vh` 를 include |
| [`bbht_ahb_loader.v`](../../hardware_bram/src/bbht_ahb_loader.v) | SJS | AHB 마스터 DMA |
| [`bbht_grover_core_adapter.v`](../../hardware_bram/models/hardware_bram_K3H3_E4_M2/src/bbht_grover_core_adapter.v) | SJS | 계약 이름·리셋(`rstnn` ↔ `rstn`) 차이 흡수. K·H·E·M 기본값이 여기 |
| [`bbht_bram_top.v`](../../hardware_bram/src/bbht_bram_top.v) | SJS | 두 번째 최상위. 어댑터 없이 Main IP 에 직접 연결 |
| [`bbht_grover_user_region.vh`](../../hardware_bram/src/bbht_grover_user_region.vh) | SJS | RVX 에 넘기는 결선. 클럭 assign 두 줄이 여기 |
| Main IP 10개 + `grover_param.vh` | PJK | [8장 8.1절](08_Main_IP_최상위와_BBHT_제어.md#81-모듈-지도) |
| `grover_policy_ooc_top.v` · `grover_policy_impl_wrapper.v` | PJK | 정책 엔진 OOC 합성 전용. 전체 합성 소스에서 제외 |
| `software/contract/generated/bbht_grover_csr.vh` · `bbht_grover_regs.h` | 생성물 | [13장](13_CSR_레지스터와_실행_모드.md) |
| [`firmware/bbht_grover_driver.{c,h}`](../../hardware_bram/firmware/) · `bbht_console/` | SJS | 펌웨어 드라이버와 UART 명령 셸 |
| [`rvx/bbht_grover_upgrade.xml`](../../hardware_bram/models/hardware_bram_K3H3_E4_M2/rvx/bbht_grover_upgrade.xml) | SJS | 플랫폼 정의. `clk_accel` 100 MHz, SRAM 128 KiB |

### 두 최상위의 용도

`bbht_rvx_wrapper` 와 `bbht_bram_top` 은 포트가 같고 둘 중 하나만 합성합니다.

| 최상위 | 쓰임 |
|---|---|
| `bbht_rvx_wrapper` | RVX 플랫폼에 들어가는 것. 어댑터를 거칩니다 |
| `bbht_bram_top` | 저장소 회귀용. mmio · loader 를 Main IP 에 직접 연결합니다 (보드에 구운 정본 wrapper 도 이렇게 물었습니다) |

`bbht_bram_top` 은 DRAM 갈래의 [`bbht_dram_top.v`](../../hardware_dram/src/bbht_dram_top.v)와
짝입니다. 같은 테스트벤치 틀로 두 갈래를 비교하려는 구조입니다.

### 하드웨어 트리와 BRAM 모델

반복 실패 뒤 진폭을 어떻게 재활용하느냐로 갈래가 둘이고, 하드웨어 트리도 둘입니다. 이 문서의
본문(5~20장)은 BRAM 갈래의 최종 구성 `K3H3_E4_M2` 를 기준으로 하고, 체크포인트 없는 비교 기준
판과 DRAM 갈래는 따로 장을 두었습니다.

| 트리 | 무엇 | 장 |
|---|---|:-:|
| [`hardware_bram/`](../../hardware_bram/) | 체크포인트 · 연산기 구성별 모델 열 개. 같은 RTL 을 파라미터만 달리 컴파일 | 5~21 |
| [`hardware_dram/`](../../hardware_dram/) | 모든 `j` 의 진폭을 DDR3 에 저장. RVX 플랫폼 `bbht_grover_dram` | [22](22_DRAM_갈래.md) |

Main IP 의 K · H · E · M 은 전부 컴파일 파라미터라([8장 8.2절](08_Main_IP_최상위와_BBHT_제어.md#82-컴파일-파라미터-8개)),
BRAM 갈래의 모델 사이에 다른 것은 그 기본값을 정하는 어댑터 하나와 그 모델의 산출물뿐입니다.
그래서 `hardware_bram/` 은 공용 소스를 바로 아래에 한 벌만 두고, 모델마다 다른 것을
`models/hardware_bram_<모델>/` 에 둡니다. 2026-10-06 에 옛 `hardware_bram_checkpoint/` ·
`hardware_bram_nocheckpoint/` 를 이렇게 합쳤습니다.

```
hardware_bram/
  src/ testbench/ sim/ synth/ firmware/   모든 모델 공용. sim 은 MODEL=<모델> 로 어댑터를 고름
  rvx/                  공용 설치기 install_model.sh · user region 템플릿
  results/              모델 사이 비교 근거 (6단계 ablation · 자원 5구성 · K/H 단독)
  models/hardware_bram_<모델>/
    src/                bbht_grover_core_adapter.v 하나 (K · H · E · M 기본값)
    rvx/                플랫폼 정의 <플랫폼>.xml · install_to_platform.sh (공용 설치기를 부름)
    results/ vivado/ bitstream/   그 모델의 시뮬 근거 · 구현 리포트와 보드 실측 · 굽기 묶음
    sim/                그 모델에만 있는 회귀 (지금은 nocheckpoint 하나)
```

모델은 지금까지 실험한 조합 열 개입니다. 표의 순서는 6단계 ablation 순서에 K/H 단독 실험과
비교 기준 판을 끼운 것입니다.

| 모델 | CKPT | K/H | E | M1/M2 | RVX 플랫폼 | 어디서 나왔나 | 산출물 |
|---|:-:|:-:|:-:|:-:|---|---|---|
| `Normal_E1` | 0 | - | 1 | 0/0 | `bbht_grover_normal_e1` | 6단계 1단계와 같은 구성 | 없음 |
| `K4H8_E1` | 1 | 4/8 | 1 | 0/0 | `bbht_grover_k4h8_e1` | 첫 체크포인트 보드 실측 | 옛 RTL 보드 실측 (2026-09-01) |
| `K4H4_E1` | 1 | 4/4 | 1 | 0/0 | `bbht_grover_k4h4_e1` | 6단계 2단계, K/H 단독 대조군 | 옛 RTL 보드 실측 (2026-09-04) |
| `K3H4_E1` | 1 | 3/4 | 1 | 0/0 | `bbht_grover_k3h4_e1` | K/H 단독 실험 | 없음 |
| `K3H3_E1` | 1 | 3/3 | 1 | 0/0 | `bbht_grover_k3h3_e1` | K/H 단독 실험 | 없음 |
| `K4H4_E4` | 1 | 4/4 | 4 | 0/0 | `bbht_grover_k4h4_e4` | 6단계 3단계 | 없음 |
| `K3H3_E4` | 1 | 3/3 | 4 | 0/0 | `bbht_grover_k3h3_e4` | 6단계 4단계. nocheckpoint 사이클 대조의 기준 | 없음 |
| `K3H3_E4_M1` | 1 | 3/3 | 4 | 1/0 | `bbht_grover_k3h3_e4_m1` | 6단계 5단계 | 없음 |
| `K3H3_E4_M2` | 1 | 3/3 | 4 | 1/1 | `bbht_grover_upgrade` | **최종 구성**. 6단계 6단계 | 보드 정본 · 비트스트림 · 시뮬 근거 전부 |
| `nocheckpoint` | 0 | - | 4 | 0/0 | `bbht_grover_nocheckpoint` | 비교 기준 Normal-E4 ([21장](21_체크포인트_없는_BRAM_판.md)) | 비트스트림 · 보드 실측 (2026-10-04) |

`CKPT_MANUAL_ENABLE=0` · `AUTO_SPEC_ENABLE=1` 은 모든 모델이 같습니다. 체크포인트를 끈 두 모델은
`burst_enable` 을 Main IP 에 0 으로 넘깁니다(이유는 [21장 21.2절](21_체크포인트_없는_BRAM_판.md#212-소스를-어떻게-나눴나)).

읽을 때 지킬 것이 셋 있습니다.

- 6단계 ablation 과 K/H 단독 실험의 수치는 태그 `board-k3h3-e4-m2` 안의 standalone top 으로
  잰 것입니다. 모델 어댑터는 그 top 들이 넘기던 파라미터를 옮긴 것이고, 그 수치를 모델 폴더에서
  다시 재지는 않았습니다. 6단계의 Normal-E1 은 `K4H4_E1` 빌드를 런타임 NORMAL 로 잰 값이라,
  체크포인트 하드웨어를 뺀 E1 빌드는 `Normal_E1` 모델이 처음입니다.
- `K4H8_E1` · `K4H4_E1` 의 보드 비트스트림은 단일 연산기 시절의 옛 RTL 로 만든 것이라, 현행 Main IP
  에 그 모델 어댑터를 문 것과 바이트가 같지 않습니다. 두 묶음은 250쌍(시드 50)이라 500 워크로드
  캠페인과 총합을 맞댈 수도 없습니다.
- 열 모델 모두 포트 계약 · lint · 실물 코어 통신 계약 T1~T9 를 통과합니다(2026-10-06,
  [16장](16_검증_체계.md)). 비트스트림은 `K3H3_E4_M2` 와 `nocheckpoint` 만 현행 RTL 로 냈습니다.

새 모델은 이미 있는 모델 폴더의 `src/` 와 `rvx/` 를 복사해 어댑터 기본값과 xml 의 첫 `<name>` 만
바꾸면 됩니다. Main IP 를 모델 폴더로 복사하지 마십시오. 같은 RTL 을 파라미터만 달리 컴파일해야
모델 사이 비교가 공정합니다. 한 모델에만 해당하는 결과 묶음은 그 모델의 `results/`, 여러 모델을
맞대는 결과는 `hardware_bram/results/` 에 둡니다.

### 태그와 옛 폴더 이름

태그 안에서는 BRAM 갈래 폴더 이름이 그 시점 이름인 `hardware_bram/` 이고, 내용도 그 시점의
배치입니다. 지금의 공용 `hardware_bram/src/` 와 이름이 같아도 같은 파일이 아닙니다. 태그 안 경로를
말하는 곳은 옛 배치를 그대로 씁니다. 폴더 이름은 2026-09-25 에 `hardware_bram_checkpoint/` 로
바뀌었다가 2026-10-06 에 위의 배치로 돌아왔습니다.

| 태그 | 그 시점의 `hardware_bram/` |
|---|---|
| `board-k3h3-e4-m2` | `src/` = 보드 비트스트림과 바이트 동일한 17개. `src_comm/` · `src_ablation/`(6단계 · K/H 단독 standalone top) 이 따로 있고 `make final` · `anchor` · `publication` · `kh` · `synth/run_resource.sh` 가 돎 |
| `backup-src_comm` | `src_comm` 을 `src/` 로 합친 직후. Main IP 는 보드 정본 그대로 |
| `backup-src_ablation` | ablation 코어까지 합친 최신판. 2026-09-13 정리를 마친 main 과 같은 코드 |

## 5.3 클럭과 리셋 소유권

| 경계 | network 쪽 | user 쪽 | CDC | 소유 |
|---|---|---|---|---|
| APB CSR | `gclk_noc` | `i_grover_csr_clk = gclk_accel` | `sni_apb_asynch` | RVX 생성 |
| AHB DMA | `gclk_noc` | `i_grover_dma_clk = gclk_accel` | `mni_ahbm_asynch` | RVX 생성 |
| 가속기 내부 | — | `gclk_accel` 하나 | 없음 | 프로젝트 구현 |

`user_slaveif_apb_clkout` 과 `user_masterif_ahb_clkout` 을 쓰므로 클럭은 user region 에서
넣어 줍니다. 다음 두 줄이 그것입니다.

```verilog
assign i_grover_csr_clk = gclk_accel;
assign i_grover_dma_clk = gclk_accel;
```

리셋은 두 인터페이스가 같은 reset group(3)에서 나오므로 함께 풀립니다. wrapper 는
`i_grover_csr_rstnn` 하나를 받아 전체에 씁니다. 비동기 assert, 음논리입니다.

wrapper 나 Main IP 안에는 CDC 를 추가하지 않습니다. RVX 가 만든 CDC 가 실보드에서 검증된
구조이고, 중복 삽입하면 그 검증을 적용할 수 없습니다. 2026-09-16 구현 리포트의 Inter Clock
Table 이 비어 있어 도메인 간 경로가 없음을 확인했습니다([20장](20_합성_구현_비트스트림.md)).

### `gclk_accel` 과 `clk_accel`

보드 정본(2026-09-07)의 user region 은 가속기 클럭에 `clk_accel` 을, 현재 main 은
`gclk_accel` 을 연결합니다. RVX 생성 RTL 이 `assign gclk_accel = clk_accel;` 이라 두 신호 사이에
게이팅도 BUFG 도 없는 순수 별칭입니다. 2026-09-16 구현 묶음의 `build_info.txt` 와 2026-09-17
보드 세션에서 확인했습니다.

## 5.4 데이터가 들어오는 길

데이터셋은 CSR 로 넣지 않습니다.

```
  호스트가 만든 배열                보드에서 GEN
        │                                │
        ▼                                ▼
  ┌───────────────────────────────────────────────┐
  │  System SRAM  0xE0000000 ~ 0xE001FFFF (128KiB)│
  │  static unsigned int dataset[8192]            │  32 KiB, 4B 정렬
  └───────────────┬───────────────────────────────┘
                  │ DATA_ADDR / DATA_COUNT / DMA_COMMAND
                  ▼
  ┌───────────────────────────────────────────────┐
  │  bbht_ahb_loader                              │
  │   검사: 정렬 / 개수 / 범위 / main busy         │
  │   32b AHB SINGLE read, single outstanding     │
  │   워드당 3사이클 (주소 1 + 데이터 1 + 쓰기 1)  │
  └───────────────┬───────────────────────────────┘
                  │ data_wr_en / data_wr_addr[13:0] / data_wr_data[15:0]
                  ▼
  ┌───────────────────────────────────────────────┐
  │  Main IP generic loader → data mem            │
  └───────────────────────────────────────────────┘
```

AHB 는 SINGLE 전송, single outstanding 입니다. Q14 전체 적재가 약 246 us 이고 탐색 한 번이
그보다 훨씬 길어서 버스트를 쓰지 않았습니다. 패킹과 홀수 개수 처리는
[6장 6.8절](06_데이터_표현과_메모리_맵.md#68-시스템-sram-과-적재), 적재 전 검사는
[7장 7.3절](07_통신_계층.md#73-loader-의-사전-검사)에 있습니다.

## 5.5 결과가 나오는 길

```
  Single 모드                        Enumeration 모드
  ─────────────                      ────────────────
  result_valid + result_index        Result FIFO 14b x 256
        │                                  │ res_dout / res_empty / res_count
        ▼                                  ▼
  CSR RESULT_INDEX (0x028)           CSR FIFO_DATA (0x040)
        │                                  │  읽기 완료 → res_pop 1사이클
        ▼                                  ▼
  STATUS.result_valid 확인 후 읽기    FIFO_COUNT / STATUS.fifo_empty 로 확인
```

`FIFO_DATA` 는 읽는 것 자체가 pop 입니다. mmio 가 APB access 위상에 `res_pop` 을 한 사이클
내고, `pready` 가 상수 1 이라 읽기 한 번에 pop 한 번입니다. 비어 있으면 pop 하지 않습니다.
인덱스 0 이 정상 결과일 수 있으므로 값 0 을 empty 로 해석하면 안 됩니다.

열거에서는 `done` 만 기다리면 안 됩니다. FIFO 가 256칸이라 그보다 많은 해가 나오면
하드웨어가 full stall 에 걸려 진행이 멈춥니다. `busy` 인 동안에도 계속 뽑아야 하고, 드라이버의
`bbht_search_enum()` 이 그렇게 되어 있습니다.

## 5.6 시작 명령 수락 조건

wrapper 가 실제로 판단하는 것은 셋뿐이고 나머지는 배선입니다. start 수락 조건, 체크포인트
자동 경로 유도(`checkpoint_auto_enable = burst_enable && auto_shot`), manual 체크포인트 입력의
0 tie-off 입니다([7장 7.1절](07_통신_계층.md#71-wrapper-의-제어-로직)).

```
start_accept = cmd_search_start     COMMAND 쓰기가 만든 1사이클 펄스
             && !search_busy        실행 중이 아닐 것
             && !load_busy          적재 중이 아닐 것
             && res_empty           직전 열거 결과가 남지 않았을 것
             && !done_pending       직전 완료가 아직 안 읽혔지 않을 것
```

start 큐는 두지 않습니다. 조건이 안 맞는 펄스는 조용히 버려지므로 펌웨어는 `COMMAND` 를 쓰기
전에 `STATUS` 를 확인해야 합니다. 큐가 있으면 실제 시작 시점이 소프트웨어에서 보이지 않고,
그 상태로 카운터를 읽으면 서로 다른 실행의 값이 섞입니다.

`done_pending` 은 mmio 의 `done_sticky` 입니다. `COMMAND` 쓰기가 그것을 지우고 한 사이클 뒤에
`cmd_search_start` 가 나오므로 정상 순서(설정 → `COMMAND` → 폴링)는 항상 통과합니다. 걸리는
것은 앞 실행을 읽지 않고 곧바로 다음 start 를 밀어 넣는 경우뿐입니다.

`search_busy` 는 코어가 따로 내보내지 않습니다. 계약이 `busy = search_busy | load_busy` 로
정의하므로 `busy & ~load_busy` 로 유도합니다.
