- **틀린 주장**: details/limitations: "n < f 가정에 의존한다 … 실험도 전부 이 영역이다 (n=8~16, f=16~40)"

### 정정 2

- **틀린 주장**: project_relevance: "메모리 예산 = 2^n × (i + f + 1)비트", "n=8, f=17 → 총 25비트(부호 포함이면 26비트)", "n=12 → 4096 × (12+28+1) = 4096 × 41비트 ≈ 168 kbit"

- **문제**: 부호 비트를 i 바깥에 추가로 계산했는데, 논문 Eq.(20)의 표현 범위 −(2^(i−1) − 2^(−f)) ≤ r ≤ 2^(i−1) − 2^(−f)는 정수부 i비트 안에 이미 부호 비트가 포함되어 있음을 의미한다(i비트로 ±2^(i−1) 범위). 논문 어디에도 +1 비트 서술은 없다.

- **바른 서술**: 워드 폭 = i + f (부호는 i에 포함). n=8, f=17 → 25비트. n=12, f=28 → 40비트, BRAM = 4096 × 40 = 163,840비트 ≈ 164 kbit. 추출본이 "25비트"라고 쓴 뒤 "부호 포함이면 26비트"를 덧붙인 것은 근거 없는 이중 계산.

### 정정 3

## 추출본이 놓친 중요 내용

1. **논문 자체의 수치 불일치**: n=12, f=28의 ℓ2가 세 곳에서 다르게 나온다 — Table 2는 7.49×10⁻⁶, 4.2절 본문(a 결정)은 7.492×10⁻⁶, Table 3은 7.493×10⁻⁶. 유효숫자 반올림 차이로 보이지만, 우리가 골든 모델로 재현할 때 어느 값을 목표로 삼을지 정해야 한다. a = 2^(−1.03)을 재유도하면 log2(7.492e−6) = −17.03, n−f = −16 → a = 2^(−1.03) 확인됨.

2. **α_{k,FP,S} ≈ n_s^{−1} (p.17, Eq. 52 직후)**: 논문은 해 진폭의 크기를 n_s^{−1}로 적는다. 정규화 조건상 √(n_s)개 해에 확률이 고루 분산되므로 진폭은 n_s^{−1/2}가 맞다(n_s=1이면 둘 다 1이라 실험에서 드러나지 않음). **논문의 오타로 강하게 의심된다.** 어차피 O(1)로 처리하므로 결론에는 영향 없지만, 우리가 n_s > 1로 확장할 때는 이 부분을 직접 다시 유도해야 한다.

3. **|α_{k,FP,NS}| = O(2^(−n)) 주장 (Eq. 52)**: 논문의 유도는 |cos((2k+1)θ)|/√(2^n − n_s) < sinθ/√(2^n−n_s) = √n_s/(√(2^n)·√(2^n−n_s))이고, 이는 O(2^(−n))이 맞다. 다만 이는 **상한**이지 실제 크기가 아니다(k가 최적일 때만 성립). 추출본이 project_relevance에서 "비해는 O(2^(−n))로 작아서 argmax 판별이 잘 동작할 것"이라고 쓴 추론은 논문 근거가 아니라 추출자의 가설이므로, 우리 프로젝트에서 실측으로 확인해야 한다(추출본도 "success rate 별도 측정" 제안으로 이 점은 잘 짚었다).

4. **Eq. 28과 Eq. 39의 부호 구조**: 해 상태는 `α_scaled + α_S`, 비해는 `α_scaled − α_NS`이다(오라클이 이미 해 진폭을 뒤집었기 때문). Algorithm 1은 이를 오라클 negate 후 `sum » (n−1) − amp`로 통일해 처리한다. 추출본의 architecture 서술은 Algorithm 1 기준이라 맞지만, **Eq. 28/39와 Algorithm 1의 표기가 서로 다른 시점(오라클 전/후)을 가리킨다는 점**을 명시하지 않아 골든 모델 구현 시 부호 버그를 유발할 수 있다. 논문은 3.2절 Setup에서 프라임 표기 규약(′ = 오라클 직후, ″ = G 전체 적용 후)을 별도로 설명하고 있으니 이 규약을 반드시 함께 옮겨야 한다.

5. **Algorithm 2 line 16/17의 비대칭**: ϵ_NS = ϵ_old,NS + ϵ_scaled − …, ϵ_S = 2ϵ_old,NS + ϵ_old,S + ϵ_scaled − … 로 Eq.(40)과 정확히 일치한다. 즉 **해 오차 점화식에는 ϵ_old,S가 그대로 이월되고 거기에 2ϵ_old,NS가 매번 얹힌다**. 추출본의 "k² 누적" 설명은 옳지만, Eq.(44)의 유도가 O(k²·2^(−f)) = O(2^(n−f))인 것은 k ≈ O(2^(n/2))이므로 k² ≈ O(2^n)이기 때문이다 — 이 연결고리를 명시하면 이해가 쉽다.

6. **r_num_q가 정확히 2가 아니라 2.04→2.24로 단조 증가한다**: f가 커질수록 이론값 2에서 점점 멀어진다(2.0442, 2.0285, 2.0981, 2.1220, 2.1067, 2.1724, 2.2415). 논문은 "consistently remains close to 2"라고만 하고 이 드리프트를 설명하지 않는다. Eq.(53)의 부차항(O(2^(n−2f)) 등)이나 잔여 각도 오차 δ의 n 의존성이 원인일 수 있다. **우리 프로젝트가 f_min 공식을 큰 n으로 외삽할 때 이 드리프트가 안전마진을 갉아먹을 수 있으므로 주의해야 한다** — 추출본의 limitations에 이 항목이 빠져 있다.

7. **Fig. 4, Fig. 5의 역할**: Fig. 4는 고정소수점 덧셈/곱셈의 비트 요구량 변화, Fig. 5는 우측 시프트 시 하위 비트가 떨어져 나가는 그림이다. 추출본이 beginner_hooks에서 이 개념을 잘 풀었지만 그림 번호를 인용하지 않아, 나중에 원문을 되짚을 때 찾기 어렵다.

8. **자금 지원 정보**: NRF (MSIT) No. RS-2024-00345668 및 2025년 중앙대 연구장학금. 같은 연구실 후속 과제라면 참고할 만하다.

## 총평

추출본의 **정량적 사실 관계는 매우 정확하다** — Table 2/3의 46개 숫자, 18개 수식, 알고리즘 의사코드 전부가 원문과 일치했고, "논문에 없는 것"(FPGA 자원 수치)을 없다고 정직하게 표시한 점도 좋다. 발견된 문제는 대부분 **추론을 원문 서술처럼 제시한 경우**(소프트웨어 실행 여부, 부호 비트 +1, 절단 지점 개수)이며, 명백한 사실 오류는 "실험도 전부 n < f 영역" 하나뿐이다. project_relevance와 beginner_hooks는 논문 근거와 추출자 해석이 뒤섞여 있으나 대체로 타당하며, 특히 "argmax 성공률을 별도 지표로" 제안과 "n_s > 1이면 상수 1.03 재보정 필요" 경고는 논문의 실제 한계를 정확히 짚었다.
