# software baseline — ORCA board · server · FPGA, Predicate500 2,000개

## 무엇인가

accelerator를 쓰지 않는 같은 C code(`software/orca_grover_develop/`, model ① naive · ② 최적화 + a Checkpoint-Capacity of 3 and 3-shot Lookahead · ③ 최적화 Restart mode)를
두 곳에서 돌려 FPGA accelerator와 workload마다 맞댄 묶음입니다.

1. **ORCA board**: 200T board(AX7A200B)의 ORCA core(RV32IM, 50 MHz). 2026-10-11 benchmark.
2. **server**: 같은 source를 이 server의 x86 core 하나에서. RVX header 셋만 바꿔 끼웠습니다. 2026-10-11~12 benchmark.
3. **FPGA**: 같은 board의 final configuration accelerator, 2026-10-08 benchmark
   ([ax7a200b_board_predicate500](../../../hardware_bram/configurations/final/vivado/vivado_bbht_grover_fpga/2026-10-08_ax7a200b_board_predicate500/evidence.md)).
   ③ · ①은 FPGA `normal` mode, ②는 `ckpt` mode와 짝입니다.

workload는 셋 모두 네 predicate(LT · GT · EQ · RANGE) × 다섯 가지 number of solutions(1 · 4 · 16 · 64 · 256) × 100 seeds = 2,000개이고
seed가 같습니다. integer 연산만 쓰므로 결과 index · shot 수 · requested iterations · executed iterations가 세 곳에서 같아야 하고, 실제로
같습니다(verification 절).

## 조건

| 항목 | ORCA board | server | FPGA (2026-10-08) |
|---|---|---|---|
| hardware | AX7A200B `xc7a200tfbg484-2`, 100T 예산 implementation | Intel Core i5-14600K, P-core 하나에 고정 (③ · ② cpu 4, ① cpu 6) | 같은 board |
| clock | ORCA 50 MHz | benchmark 5.26~5.28 GHz (turbo) | accelerator 100 MHz, ORCA 50 MHz |
| compile | RVX release, `riscv64-unknown-elf-gcc -O2 -march=rv32im` | `gcc 13.3.0 -O2` (x86-64 기본, `-march` 없음). 나머지 code 생성 option은 RVX와 같음 | — |
| RVX platform | ③ `bbht_grover_upgrade` (final configuration bitstream, SRAM 128 KB, accelerator 미사용) · ② ① `orca_sw` (accelerator 없음, SRAM 256 KB) | — | `bbht_grover_upgrade` |
| 시간 구간 | `bbht_search()` 호출 앞뒤, RVX 실시간 clock(1 MHz) | 같은 구간, `CLOCK_MONOTONIC_RAW` µs | `wall_us`: 같은 board 실시간 clock으로 `COMMAND` 직전 ~ DONE |
| cycle | 시간 × 50 (환산) | 같은 구간의 user space core cycle (perf_event) | accelerator `cycle_count` |
| oracle | 미리 만든 solution 목록. 준비 시간 제외 | 같음 | iteration마다 data 16,384개 비교 |
| benchmark 횟수 | 1회 | ③ · ② 10회 (median), ① 1회 | 1회 |

- `orca_sw` platform 정의는 `software/orca_grover_develop/rvx/orca_sw.xml` 입니다. 200T implementation은 WNS +6.688 ns · WHS +0.042 ns,
  100T 예산으로 Available이 100T와 같고, 64 BRAM tiles를 씁니다. bitstream은 저장소에 두지 않고 hash만
  `sha256.txt` 에 남겼습니다.
- ③은 accelerator가 들어 있는 final configuration bitstream에서, ② · ①은 `orca_sw` 에서 쟀습니다. ② · ①은 정적 memory가
  128 KB를 넘기 때문입니다. 두 platform에서 ③의 SMOKE · CALIBRATE 시간이 같아 platform 차이는 시간에 영향이 없습니다(verification 절).
- server 실행 file의 머리줄 `SW_TIMING_SOURCE,RVX_REAL_CLOCK` · `SW_TIMING_CORE_CLK_HZ,50000000` 은 `main.c` 의
  고정 문자열이라 server에서도 그대로 찍힙니다. server 조건은 이 표가 source of truth입니다.

## verification

`validation.txt` 기준입니다.

- **BBHT trajectory**: ORCA ③ · ②, server ①, server ③ · ② 각 10회가 모두 FPGA와 seed_j · seed_meas · result_index ·
  trial_count · L_BBHT · actual_iter에서 2,000/2,000 같습니다. ②의 executed iterations 37,659는 FPGA Checkpoint mode의
  executed iterations와 workload마다 같습니다.
- **platform 사이**: 같은 model이면 ORCA와 server의 시간 열을 뺀 모든 열(종료 사유, saturation 수 포함)이 2,000/2,000
  같습니다. server ①은 ORCA ③과 BBHT trajectory가 같습니다(①도 Restart mode).
- **platform 차이 없음**: ③을 final configuration bitstream과 `orca_sw` bitstream에서 각각 돌린 값입니다.
  SMOKE 762,498 µs = 762,498 µs, CALIBRATE iteration 20회 1,283,366 µs = 1,283,366 µs, measurement 1회 54,178 µs 대 54,177 µs(1 µs tick 차이).
- **① 추정식**: 추정 = requested iterations × iteration 1회 시간 + shot 수 × measurement 1회 시간. ORCA 단가는 iteration 1,154,636,860.5 µs,
  measurement 55,027 µs입니다(`orca/naive_calib.log`). ORCA SUBSET 두 workload(GT · RANGE, 256 solutions, seed 0)를 끝까지
  돌린 benchmark와 +0.0029% 차이, server ① FULL benchmark와 server 단가 추정은 +0.81% 차이입니다.
- board · server 실행 모두 `SW_SUMMARY,pass=2000,total=2000` 입니다.

## 인용할 때

- **성능 세 축의 Board-Verified Build와 섞지 마십시오.** Board-Verified Build는 2026-09-07 build · 100T board · EQ 500입니다
  ([1장 1.5절](../../../documents/design_references/01_project_overview.md#15-성능-지표와-인용-기준)). 이 묶음은 200T board ·
  네 predicate 2,000개라 1.5절의 ORCA 116,426×와 speedup을 맞대지 않습니다. 그 116,426×는 옛 baseline
  (`orca_sw_baseline`, iteration 1회에 array를 두 번 훑음, EQ 500, checkpoint 없음) 대 final configuration의 Checkpoint mode이고, 이 묶음은 같은
  mode끼리 맞댄 값입니다.
- **ORCA ÷ FPGA의 만 단위 speedup은 algorithm 우위가 아닙니다.** 16,384 states의 state vector를 32-bit core 하나로 훑는 것과
  32 lanes로 훑는 것의 차이에 clock 2×가 곱해진 값이고, oracle 준비가 software 쪽에서 빠져 software가 조금 유리합니다.
- **server 한 core는 FPGA와 시간이 비슷합니다.** 전체로 ③은 FPGA Restart mode의 1.15×, ②는 FPGA Checkpoint mode의 1.34×이고,
  64 · 256 solutions에서는 server가 FPGA wall-clock time보다 빠릅니다. clock이 약 53× 높은 범용 core라는 점과 같이 적으십시오.
  가속 주장을 할 때는 이 비교를 빼지 마십시오.
- **server 시간은 code 배치에 ±15~20% 흔들립니다.** 시간용과 cycle용 실행 file을 따로 build했을 때(그 차이는
  `main.c` 가 넣는 header뿐) 같은 계산이 ③ 0.644 / 0.553 초, ② 0.242 / 0.297 초로 달랐습니다. 이 묶음의 값은
  시간과 cycle을 한 실행 file · 한 실행에서 같이 잰 것입니다.
- **ORCA ①은 추정값입니다.** benchmark와 같은 열에 둘 때는 추정임을 표시하십시오.
- cycle 축과 시간 축을 섞어 speedup을 만들지 마십시오. 고전 선형 scan과는 비교하지 않습니다.
